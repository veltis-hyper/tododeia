Configuración y Settings

Cómo personalizar Claude Code a tu medida con archivos de configuración, permisos y variables de entorno

Intermedio

Claude Code se adapta a ti, no al revés. Puedes cambiar cómo se comporta usando archivos de configuración simples. En este capítulo vas a aprender dónde viven esos archivos, qué puedes poner dentro, y cómo controlar los permisos de lo que Claude puede o no puede hacer. Piensa en la configuración como los controles de un coche: volante, espejos, asiento. Todo se ajusta para que tú manejes cómodo.

La Jerarquía de Configuración: Quién Manda Aquí

Claude Code no tiene un solo archivo de configuración. Tiene cinco niveles, organizados como una pirámide. Los de arriba mandan sobre los de abajo.

Imagina una empresa. El CEO da una orden. El gerente puede agregar detalles, pero no puede contradecir al CEO. El empleado puede personalizar su escritorio, pero no puede cambiar las reglas de la empresa.

Así funciona la configuración de Claude Code:

  1. Managed (administrador) — El nivel más alto. Lo configura el equipo de IT de tu empresa. Nadie puede sobreescribirlo.
  2. Argumentos de línea de comandos — Overrides temporales que pasas al ejecutar Claude. Solo duran esa sesión.
  3. Local — Tu configuración personal para un proyecto. No se comparte con nadie.
  4. Project — La configuración del proyecto. Se comparte con todo el equipo vía git.
  5. User — Tu configuración global. Aplica a todos tus proyectos.

Hay una regla importante: las listas (como permisos) se combinan entre niveles. No se reemplazan. Si tu configuración de usuario permite npm run test y la de proyecto permite npm run lint, ambas quedan permitidas.

Cómo ver qué configuración está activa

Escribe /status dentro de Claude Code. Te muestra todas las fuentes de configuración activas y de dónde vienen.

Esto es muy útil cuando algo no funciona como esperas. Siempre revisa /status primero.

Los Archivos de Configuración y Dónde Viven

Cada nivel de configuración tiene su propio archivo. Es como tener cajones diferentes para cosas diferentes.

Settings de usuario (global)

Archivo: ~/.claude/settings.json

Este archivo aplica a todo lo que hagas con Claude Code. No importa en qué proyecto estés. Es tu configuración base.

Ejemplo básico:

{
    "$schema": "https://json.schemastore.org/claude-code-settings.json",
    "permissions": {
      "allow": ["Bash(npm run *)", "Bash(git commit *)"],
      "deny": ["Bash(curl *)", "Read(./.env)"]
    },
    "model": "claude-sonnet-4-6"
}

El campo $schema es opcional pero muy recomendado. Le dice a tu editor (VS Code, Cursor) que te ayude con autocompletado.

Settings de proyecto (compartido)

Archivo: .claude/settings.json (dentro de tu proyecto)

Este archivo va dentro de git. Todos los del equipo lo comparten. Sirve para que todos trabajen con las mismas reglas.

Ejemplo:

{
    "permissions": {
        "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
        "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"],
        "additionalDirectories": ["../docs/"]
    },
    "env": {
        "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
    }
}

Con env puedes definir variables de entorno que se aplican a todo el equipo. Así no cada persona tiene que configurarlas manualmente.

Con additionalDirectories puedes dar acceso a carpetas fuera del directorio del proyecto. También puedes agregar directorios con --add-dir al iniciar o /add-dir durante la sesión. Los archivos de directorios adicionales siguen las mismas reglas de permisos.

Settings locales (solo para ti)

Archivo: .claude/settings.local.json

Este archivo está en el proyecto pero no se sube a git. Es solo tuyo. Perfecto para preferencias personales que no quieres imponer al equipo.

Ejemplo:

{
    "permissions": {
        "defaultMode": "acceptEdits"
    },
    "language": "japanese",
    "prefersReducedMotion": true
}

Settings administrados (para empresas)

Estos los configura el equipo de IT. El usuario normal no los toca.

Hay tres mecanismos para entregar managed settings, cada uno con su propia precedencia:

  1. Server-managed settings — Se configuran desde la web en Claude.ai (Admin Settings > Claude Code > Managed settings). Tienen la mayor precedencia de todos.
  2. MDM / Políticas del sistema operativo — Para empresas que usan herramientas de gestión de dispositivos:
    • macOS: Dominio com.anthropic.claudecode. Se despliega con Jamf, Kandji u otro MDM.
    • Windows: Registro en HKLM\SOFTWARE\Policies\ClaudeCode con valor Settings (tipo REG_SZ con JSON). Se despliega con Group Policy o Intune.
    • Windows (usuario): HKCU\SOFTWARE\Policies\ClaudeCode — tiene la menor precedencia de los mecanismos managed.
  3. File-based — Archivos JSON en ubicaciones del sistema operativo:
    • macOS: /Library/Application Support/ClaudeCode/managed-settings.json
    • Linux/WSL: /etc/claude-code/managed-settings.json
    • Windows: C:\Program Files\ClaudeCode\managed-settings.json

La precedencia dentro de managed es: server-managed > MDM/OS-level > file-based > HKCU registry (Windows).

Los settings administrados son como las reglas del edificio. Tú puedes decorar tu oficina, pero no puedes tirar una pared.

Otros archivos importantes

Además de los settings, Claude Code usa estos archivos:

  • ~/.claude.json — Preferencias de usuario, tokens OAuth y estado interno. No lo edites manualmente. Importante: algunos settings viven aquí y no en settings.json (ver nota abajo).
  • .mcp.json — Servidores MCP del proyecto (ver capítulo de MCP).
  • ~/.claude/CLAUDE.md — Tu memoria global. Instrucciones que Claude sigue en todos los proyectos.
  • CLAUDE.md o .claude/CLAUDE.md — Memoria del proyecto. Instrucciones específicas para ese proyecto.
  • ~/.claude/agents/ — Subagentes personales.
  • .claude/agents/ — Subagentes del proyecto.

Settings que van en ~/.claude.json, NO en settings.json:

  • editorMode — Modo de key binding: "normal" o "vim".
  • autoConnectIde — Conectar automáticamente al IDE al iniciar.
  • autoInstallIdeExtension — Instalar extensión IDE automáticamente.
  • showTurnDuration — Mostrar duración de cada respuesta.
  • terminalProgressBarEnabled — Barra de progreso visual.
  • teammateMode — Cómo se muestran teammates del agent team ("auto", "in-process", "tmux").

Si pones estos settings en settings.json, no tendrán efecto. Es un error común.

Nota de migración (v2.1.119)

Las versiones anteriores a v2.1.119 guardaban autoScrollEnabled, editorMode, showTurnDuration, teammateMode y terminalProgressBarEnabled en ~/.claude.json. Desde v2.1.119 estos settings ya viven en settings.json (con la excepción de los marcados arriba que siguen en ~/.claude.json). Si actualizas desde una versión vieja, revisa que tus configuraciones estén en el archivo correcto.

Control de actualizaciones y versión mínima

Por defecto, Claude Code se actualiza automáticamente a la última versión disponible. Puedes controlar este comportamiento con dos settings:

{
    "autoUpdatesChannel": "stable",
    "minimumVersion": "2.1.100"
}
  • autoUpdatesChannel — Acepta "latest" (default) o "stable". El canal stable retrasa una semana las nuevas versiones para evitar regresiones. Si una versión tiene problemas reportados, no llega al canal stable.
  • minimumVersion — Bloquea cualquier ejecución y el comando claude update si la versión instalada está por debajo de este valor. Útil para empresas que necesitan asegurar features de seguridad recientes. Lo fija el cambio de canal en /config y actúa como suelo que impide downgrades.

Suelos y techos duros para administradores (v2.1.163): en managed settings hay dos claves que van un paso más allá que minimumVersion porque bloquean el arranque de Claude Code:

  • requiredMinimumVersion — Suelo duro. Si la versión instalada es menor, Claude Code no arranca.
  • requiredMaximumVersion — Techo. Si la versión instalada es mayor, Claude Code tampoco arranca.

La diferencia con minimumVersion: este último es una preferencia que evita downgrades, mientras que los required* son políticas managed que IT impone como límites infranqueables para mantener a toda la organización en una ventana de versiones concreta.

En entornos enterprise, los administradores suelen poner autoUpdatesChannel: "stable" en managed settings y un minimumVersion coherente con su política de soporte.

Cambiar settings al vuelo con /config

No siempre quieres abrir un archivo JSON para cambiar un setting. Desde la v2.1.181 puedes fijar cualquier setting directo desde el prompt con /config key=value:

/config thinking=false
/config editorMode=vim
/config verbose=true

Funciona en sesión interactiva, en modo -p (print) y en Remote Control. Para ver la lista de claves cortas disponibles, usa /config --help (v2.1.183).

Si escribes /config sin argumentos, se abre la interfaz de Settings con pestañas, donde puedes navegar y ajustar opciones visualmente (incluido el tema claro/oscuro, que también se gestiona con /theme).

Diagnóstico de la jerarquía con claude doctor: además de /status, el comando claude doctor revisa toda la jerarquía de configuración y te muestra las entradas inválidas junto con el archivo de donde vienen. Es la mejor herramienta cuando un setting no surte efecto o cuando todo un archivo dejó de aplicarse por un error de JSON.

El Sistema de Permisos: Qué Puede y Qué No Puede Hacer Claude

Los permisos son como las llaves de tu casa. Tú decides qué puertas puede abrir Claude y cuáles están cerradas con llave.

Hay tres tipos de reglas:

  • allow — Claude puede hacerlo sin preguntar. Es como darle una llave.
  • ask — Claude te pregunta cada vez. Es como un timbre: pide permiso para entrar.
  • deny — Claude NO puede hacerlo. Punto. Es como un candado que nadie abre.

Las reglas se evalúan en este orden: primero deny, luego ask, luego allow. La primera que coincida, gana. Si algo está en deny, ningún otro nivel puede permitirlo.

Tipos de herramientas y cuándo piden permiso

No todas las herramientas de Claude necesitan tu aprobación:

  • Solo lectura (leer archivos, buscar con Grep) — No pide permiso. Solo mira, no toca.
  • Comandos Bash (ejecutar en terminal) — Pide permiso. Si dices "no preguntes más", se guarda permanentemente para ese directorio y comando.
  • Editar archivos — Pide permiso. Si dices "no preguntes más", solo dura hasta que cierres la sesión.

Para ver todas tus reglas activas, escribe /permissions en Claude Code.

Cómo escribir reglas de permisos

Las reglas siguen un formato simple: Herramienta(especificador).

Ejemplos claros:

  • Bash(npm run build) — Permite exactamente ese comando.
  • Bash(npm run test *) — Permite cualquier comando que empiece con npm run test. El * significa "cualquier cosa después".
  • Bash(* --version) — Permite cualquier comando que termine en --version.
  • Read(./.env) — Controla la lectura del archivo .env.
  • Read(./secrets/**) — Controla todos los archivos dentro de la carpeta secrets, incluyendo subcarpetas.

Un detalle importante sobre los wildcards (los asteriscos): el espacio antes del * importa.

  • Bash(ls *) — Coincide con ls -la pero no con lsof.
  • Bash(ls*) — Coincide con ls -la y también con lsof.

Claude Code es inteligente con los operadores del shell. Si permites Bash(safe-cmd *), Claude no podrá ejecutar safe-cmd && rm -rf /. Detecta el && y lo bloquea.

Reglas específicas por tipo de herramienta

Para archivos (Read/Edit): Los patrones siguen las reglas de gitignore.

  • //path — Ruta absoluta desde la raíz del sistema. Ejemplo: //tmp/build.
  • ~/path — Relativo a tu carpeta home. Ejemplo: ~/.kube.
  • /path — Relativo a la raíz del proyecto. Ejemplo: /src/**/*.ts.
  • path o ./path — Relativo al directorio actual.

Para WebFetch: Filtra por dominio.

  • WebFetch(domain:example.com) — Solo permite ese dominio.

Para MCP servers:

  • mcp__servername — Cualquier herramienta de ese servidor.
  • mcp__servername__toolname — Una herramienta específica.

Para subagentes:

  • Agent(Explore), Agent(Plan), Agent(mi-agente-custom).

Para skills: Skill es una tool más a efectos de permisos.

  • Skill(commit) — Invocaciones exactas del skill commit.
  • Skill(review-pr *) — El skill review-pr con cualquier argumento.
  • Skill — Cualquier skill.

Setting agent (ejecutar el hilo principal como subagente): el setting agent hace que la sesión principal arranque con el system prompt, restricciones de tool y modelo de un subagente concreto. Útil para sesiones especializadas (ej. revisión de seguridad).

{
    "agent": "code-reviewer"
}

Matching por parámetros de herramienta

Desde la versión v2.1.178, las reglas de permisos pueden mirar dentro de los parámetros de cada herramienta, no solo su nombre. El formato es Herramienta(parametro:valor).

Esto te da un control mucho más fino:

  • Agent(model:opus) — Bloquea (o permite) que se lancen subagentes con el modelo Opus. Útil para controlar costes.
  • WebFetch(domain:*.example.com) — Aplica la regla solo a las peticiones web hacia subdominios de example.com.
  • Edit(src/**) — Aplica la regla solo a las ediciones dentro de la carpeta src.

Ejemplo: para impedir que ningún subagente use Opus pero permitir el resto:

{
    "permissions": {
        "deny": ["Agent(model:opus)"]
    }
}

Glob en la posición del nombre de la herramienta (v2.1.166): las reglas deny ahora aceptan comodines en el nombre de la tool, y * a secas deniega todas las herramientas. Es una forma rápida de bloquear todo y luego ir abriendo con allow.

Read deny oculta archivos de la búsqueda (v2.1.162): cuando un archivo está cubierto por una regla Read en deny, ya no solo se bloquea su lectura: además queda oculto en los resultados de Glob y Grep. Así un secreto bloqueado tampoco aparece listado por accidente.

Modos de Permisos: Seis Velocidades

Claude Code tiene seis modos de permisos. Son como las marchas de un coche: cada una te da un nivel diferente de control.

  1. default — El modo normal. Claude pide permiso la primera vez que usa cada herramienta.
  2. acceptEdits — Acepta automáticamente las ediciones de archivos. Ya no te pregunta antes de cambiar código.
  3. plan — Modo solo lectura. Claude puede analizar tu código pero no puede modificar nada. Útil para explorar sin riesgo.
  4. auto — El piloto automático. Usa un clasificador de seguridad en segundo plano para decidir si una acción es segura. Si lo es, la ejecuta sin preguntar. Si tiene dudas, te pregunta. Es un research preview: funciona bien pero sigue mejorando.
  5. dontAsk — Rechaza automáticamente todo lo que no esté pre-aprobado en tus reglas de permisos.
  6. bypassPermissions — Salta todos los permisos. Solo úsalo dentro de containers o máquinas virtuales aisladas. Nunca en tu máquina personal.

Para cambiar de modo durante una sesión, presiona Shift+Tab. Cicla entre los modos disponibles.

Para configurar el modo por defecto al iniciar:

{
    "permissions": {
        "defaultMode": "acceptEdits"
    }
}

Los administradores pueden bloquear modos específicos con managed settings:

{
    "disableBypassPermissionsMode": "disable",
    "disableAutoMode": "disable"
}

Auto Mode: El Piloto Automático

El modo auto es como tener un copiloto que conoce las reglas de tráfico. En vez de preguntarte cada vez que quiere girar, evalúa si es seguro y lo hace. Solo te consulta cuando hay duda.

Por dentro, un clasificador de seguridad analiza cada acción que Claude quiere ejecutar. Si la acción es rutinaria y segura (como leer un archivo o correr tests), la aprueba automáticamente. Si es potencialmente peligrosa (como borrar archivos o hacer push a producción), te pregunta.

Configurar Auto Mode

Puedes personalizar el comportamiento del clasificador con el setting autoMode:

{
    "autoMode": {
        "environment": [
            "Organization: Acme Corp. Primary use: software development",
            "Source control: github.example.com/acme-corp",
            "Trusted cloud buckets: s3://acme-build-artifacts",
            "Trusted internal domains: *.corp.example.com"
        ]
    }
}

El campo environment describe en prosa tu infraestructura de confianza. Esto le dice al clasificador qué repos, dominios y recursos son seguros en tu contexto.

También puedes definir excepciones con allow y soft_deny:

  • allow — Acciones que siempre se permiten (excepciones a bloqueos).
  • soft_deny — Acciones que siempre se bloquean.

Advertencia crítica sobre allow y soft_deny

Cuidado

Si defines allow o soft_deny en tu configuración, reemplazan completamente la lista default. No se combinan. Esto puede desactivar reglas de seguridad importantes que vienen por defecto.

Para ver las reglas default antes de modificarlas:

# Ver reglas integradas por defecto
claude auto-mode defaults

# Ver configuración efectiva (default + tus cambios)
claude auto-mode config

# Pedir feedback del clasificador AI sobre tu config
claude auto-mode critique

Nota de seguridad

autoMode NO se lee desde .claude/settings.json compartido del proyecto. Solo se lee desde user settings, local settings y managed settings. Esto previene que un repositorio malicioso inyecte reglas de auto-aprobación.

Niveles de Esfuerzo: Cuánto Piensa Claude

Los niveles de esfuerzo controlan cuántos recursos de razonamiento dedica Claude a cada respuesta. Es como elegir entre una respuesta rápida en el pasillo y una reunión formal de análisis.

Hay cuatro niveles:

  1. low — Respuestas rápidas y directas. Ideal para preguntas simples o tareas rutinarias.
  2. medium — El balance. Es el nivel por defecto para Sonnet 4.6.
  3. high — Razonamiento profundo. Para problemas complejos que necesitan análisis detallado. Es el nivel por defecto del modelo global actual, Opus 4.8.
  4. xhigh — El máximo poder de razonamiento. Solo disponible en Opus 4.8. No persiste entre sesiones (excepto vía variable de entorno).

Como referencia: a junio de 2026 el modelo por defecto de Claude Code es Opus 4.8 con esfuerzo high.

Nota importante

El nivel máximo se llama xhigh, no max. Si pones max en tu configuración, no se aplicará y caerás en el nivel por defecto. Es el error más común al copiar configuraciones viejas.

Cómo configurar el nivel de esfuerzo

Tienes varias formas de cambiar el esfuerzo:

  • /effort low|medium|high|xhigh — Slash command durante la sesión.
  • Flechas izquierda/derecha en /model — Ajusta el esfuerzo visualmente.
  • claude --effort high — Flag al iniciar Claude Code.
  • export CLAUDE_CODE_EFFORT_LEVEL=xhigh — Variable de entorno (tiene la mayor precedencia). Valores válidos: low, medium, high, xhigh.
  • "effortLevel": "xhigh" — En settings.json para que persista entre sesiones.
  • Frontmatter en skills/subagentes — Para controlar el esfuerzo de agentes específicos.

Un truco útil: escribe ultrathink en tu prompt y Claude activará el nivel high para ese turno específico.

Para desactivar completamente el razonamiento adaptativo:

export CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1

Contexto Extendido (1M Tokens)

Opus 4.8, Opus 4.7 y Sonnet 4.6 soportan una ventana de contexto de 1 millón de tokens. Eso es como poder leer un libro entero de una sola vez, en vez de leerlo por capítulos. A diferencia de antes, esta ventana de 1M está disponible a tarifa plana, sin recargo por superar los 200K tokens.

Cómo activar el contexto de 1M

Usa el sufijo [1m] al seleccionar el modelo:

/model opus[1m]
/model sonnet[1m]
claude --model opus[1m]

Disponibilidad por plan

La ventana de 1M en Opus 4.8, Opus 4.7 y Sonnet 4.6 se factura a tarifa plana: ya no hay un recargo (premium) por los tokens que superan los 200K. Esto aplica tanto en los planes de suscripción como en la API pay-as-you-go.

Para desactivar el contexto de 1M (útil si quieres controlar costos):

export CLAUDE_CODE_DISABLE_1M_CONTEXT=1

Variables de Entorno: Los Interruptores Secretos

Las variables de entorno son como interruptores escondidos detrás del panel de tu coche. No los ves, pero cambian cómo funciona todo por dentro.

Se configuran en tu terminal con export. También puedes ponerlas en tu .bashrc o .zshrc para que se apliquen siempre.

Autenticación y API

Estas son las variables más básicas para conectarte:

  • ANTHROPIC_API_KEY — Tu clave API. La más importante de todas.
  • ANTHROPIC_AUTH_TOKEN — Token Bearer personalizado (uso avanzado).
  • ANTHROPIC_CUSTOM_HEADERS — Headers extra para las peticiones HTTP.
export ANTHROPIC_API_KEY=sk-ant-tu-clave-aqui

Selección de modelo

Puedes cambiar qué modelo de Claude se usa:

  • ANTHROPIC_MODEL — El modelo principal. Ejemplo: claude-sonnet-4-6.
  • ANTHROPIC_DEFAULT_HAIKU_MODEL — Override para el modelo Haiku (rápido y barato).
  • ANTHROPIC_DEFAULT_SONNET_MODEL — Override para Sonnet.
  • ANTHROPIC_DEFAULT_OPUS_MODEL — Override para Opus (el más potente).
  • ANTHROPIC_SMALL_FAST_MODEL — Modelo para operaciones pequeñas y rápidas (resúmenes, títulos, etc.).
  • CLAUDE_CODE_SUBAGENT_MODEL — Modelo que usan los subagentes.

También puedes configurar el modelo en el settings.json con la propiedad model.

URLs base de la API: útil si necesitas apuntar a un endpoint distinto (gateway interno, región específica, etc.):

  • ANTHROPIC_BASE_URL — URL base para la API de Anthropic. Default: https://api.anthropic.com.
  • ANTHROPIC_BEDROCK_BASE_URL — URL base para AWS Bedrock.
  • ANTHROPIC_VERTEX_BASE_URL — URL base para Google Vertex AI.

Autenticación específica por proveedor:

  • AWS_BEARER_TOKEN_BEDROCK — Bearer token para autenticar contra Bedrock (alternativa a las credenciales AWS estándar).
  • CLAUDE_CODE_SKIP_BEDROCK_AUTH — Salta el flujo de auth de Bedrock cuando ya tienes credenciales externas listas.
  • CLAUDE_CODE_SKIP_VERTEX_AUTH — Salta el flujo de auth de Vertex.
  • VERTEX_REGION_<MODEL> — Región específica de Vertex por modelo. Ejemplo: VERTEX_REGION_CLAUDE_SONNET=us-east5.

Setting modelOverrides: mapea aliases de Anthropic a IDs específicos del proveedor (típicamente ARNs de Bedrock o paths de Vertex):

{
    "modelOverrides": {
        "claude-opus-4-6": "arn:aws:bedrock:us-east-1::inference-profile/anthropic.claude-opus-4-6"
    },
    "env": {
        "CLAUDE_CODE_USE_BEDROCK": "1"
    }
}

Esto deja que sigas usando el alias humano (claude-opus-4-6) en código y comandos, pero por debajo se resuelva al ARN específico de tu cuenta.

Proveedores cloud alternativos

Si tu empresa usa AWS Bedrock, Google Vertex AI o Microsoft Foundry en vez de la API directa de Anthropic:

Amazon Bedrock:

export CLAUDE_CODE_USE_BEDROCK=1
export ANTHROPIC_MODEL=us.anthropic.claude-sonnet-4-6-20250514-v1:0
export AWS_REGION=us-east-1

Google Vertex AI:

export CLAUDE_CODE_USE_VERTEX=1
export ANTHROPIC_MODEL=claude-sonnet-4-6@20250514
export CLOUD_ML_REGION=us-east5

Microsoft Foundry:

export CLAUDE_CODE_USE_FOUNDRY=1
export ANTHROPIC_FOUNDRY_BASE_URL=https://mi-recurso.services.ai.azure.com/anthropic

Variables de comportamiento

Estas variables cambian cómo se comporta Claude Code:

  • BASH_DEFAULT_TIMEOUT_MS — Tiempo máximo para un comando bash (default: 120 segundos). Súbelo si tus builds son lentos.
  • BASH_MAX_TIMEOUT_MS — Tope absoluto que Claude no puede superar, ni siquiera con un timeout custom en la llamada.
  • BASH_MAX_OUTPUT_LENGTH — Cuántos caracteres de output muestra antes de truncar.
  • CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR — Si vale 1, mantiene el cwd del proyecto al ejecutar Bash (no se queda donde te lleve un cd previo).
  • CLAUDE_CODE_MAX_OUTPUT_TOKENS — Máximo de tokens en la respuesta (default: 32000, máximo: 64000).
  • MAX_THINKING_TOKENS — Tope de tokens para extended thinking. Útil para limitar coste.
  • MAX_MCP_OUTPUT_TOKENS — Tope de tokens en la salida de tools MCP.
  • MCP_TIMEOUT — Timeout general de operaciones MCP (milisegundos).
  • MCP_TOOL_TIMEOUT — Timeout para la ejecución individual de una tool MCP.
  • CLAUDE_CODE_API_KEY_HELPER_TTL_MS — Intervalo de refresco del apiKeyHelper (ver scripts de auth más abajo).
  • CLAUDE_CODE_EFFORT_LEVEL — Nivel de razonamiento: low, medium, high o xhigh.
  • CLAUDE_AUTOCOMPACT_PCT_OVERRIDE — Porcentaje de contexto que dispara la compactación automática (1-100).
  • CLAUDE_CODE_SHELL — Fuerza un shell específico en vez del detectado automáticamente.
  • CLAUDE_CODE_USE_POWERSHELL_TOOL — Si vale 1, habilita el tool de PowerShell para skills y shell inline (Windows).
  • CLAUDE_CODE_NO_FLICKER — Si vale 1, usa el renderer alt-screen para evitar parpadeo en terminales lentas.
  • USE_BUILTIN_RIPGREP — Si vale 1, usa el ripgrep empaquetado en lugar del del sistema.
  • API_TIMEOUT_MS — Tiempo máximo de espera para respuestas de la API (default: 600000ms = 10 minutos).
  • CLAUDE_CODE_MAX_RETRIES — Número máximo de reintentos en errores de API (default: 10).
  • CLAUDE_CODE_SIMPLE — Activa modo minimalista. Reduce la interfaz al mínimo para scripts y automatización.
  • CLAUDE_CODE_ACCESSIBILITY — Activa mejoras de accesibilidad para lectores de pantalla.
  • CLAUDE_CODE_ENABLE_AWAY_SUMMARY — Muestra un resumen al volver tras unos minutos away.
  • SLASH_COMMAND_TOOL_CHAR_BUDGET — Override del presupuesto de caracteres para el listing de skills (sobrescribe skillListingBudgetFraction).
  • CLAUDE_CODE_SAFE_MODE — Si vale 1 (v2.1.169), arranca Claude Code con todas las personalizaciones desactivadas: sin hooks, skills, plugins ni settings locales. Es la mejor herramienta para troubleshooting: si el problema desaparece en safe mode, sabes que lo causa una de tus personalizaciones.
  • CLAUDE_CLIENT_PRESENCE_FILE — Ruta a un archivo marcador (v2.1.181). Mientras ese archivo indica que estás presente en la máquina, Claude Code suprime las push notifications al móvil. Así no recibes alertas en el teléfono cuando ya estás frente al ordenador.

Variables para deshabilitar funciones

A veces necesitas apagar algo. Estas variables ponen el valor en 1 para desactivar:

  • DISABLE_AUTOUPDATER — Sin actualizaciones automáticas.
  • DISABLE_TELEMETRY — Sin telemetría.
  • DISABLE_ERROR_REPORTING — Sin reportes de errores.
  • DISABLE_BUG_COMMAND — Desactiva el comando /bug.
  • DISABLE_COST_WARNINGS — Oculta los warnings de coste de la sesión.
  • DISABLE_PROMPT_CACHING — Desactiva el prompt caching (sube el coste, no recomendado salvo debug).
  • DISABLE_NON_ESSENTIAL_MODEL_CALLS — Salta llamadas no esenciales al modelo (títulos de chat, resúmenes accesorios, etc.).
  • CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC — Desactiva todo el tráfico no esencial de un golpe.
  • CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY — Suprime la encuesta de calidad al final de sesión.
  • CLAUDE_CODE_DISABLE_THINKING — Fuerza extended thinking apagado (todas las sesiones, todos los modelos).
  • CLAUDE_CODE_DISABLE_AGENT_VIEW — Desactiva background agents y la vista de agentes en segundo plano.
  • CLAUDE_CODE_DISABLE_AUTO_MEMORY — Sin auto-memoria.
  • CLAUDE_CODE_DISABLE_BACKGROUND_TASKS — Sin tareas en segundo plano.
  • CLAUDE_CODE_DISABLE_FAST_MODE — Sin modo rápido.
  • CLAUDE_CODE_DISABLE_TERMINAL_TITLE — No cambia el título del terminal.
  • CLAUDE_CODE_DISABLE_CRON — Desactiva tareas programadas (cron jobs) dentro de Claude Code.
  • CLAUDE_CODE_DISABLE_FILE_CHECKPOINTING — Sin checkpoints automáticos de archivos.
  • CLAUDE_CODE_DISABLE_MOUSE — Desactiva soporte de mouse en la interfaz.
  • CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING — Desactiva el razonamiento adaptativo por niveles de esfuerzo.
  • CLAUDE_CODE_DISABLE_1M_CONTEXT — Desactiva el contexto extendido de 1M tokens.

Un atajo útil: si necesitas un entorno minimalista, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 apaga actualizaciones, reportes de errores y telemetría, todo junto.

Para una limpieza total de telemetría y datos no esenciales, combina las tres: DISABLE_TELEMETRY=1, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 y CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1.

TLS, certificados y almacén de CAs

Las redes corporativas suelen interceptar tráfico HTTPS con un proxy de inspección TLS. Eso significa que necesitas decirle a Claude Code en qué CAs confiar y, a veces, presentar un certificado de cliente. Estas variables cubren los casos típicos.

  • NODE_EXTRA_CA_CERTS — Ruta a un archivo PEM con CAs adicionales que Claude Code debe confiar. Es la forma estándar de Node.js.
  • CLAUDE_CODE_CERT_STORE — Qué almacén de CAs usar. Valores: bundled (solo el bundle interno de Claude Code), system (solo el almacén del sistema operativo), o ambos separados por coma. Default: bundled,system.
  • CLAUDE_CODE_CLIENT_CERT — Ruta al certificado de cliente para mTLS (PEM).
  • CLAUDE_CODE_CLIENT_KEY — Ruta a la clave privada del certificado de cliente.
  • CLAUDE_CODE_CLIENT_KEY_PASSPHRASE — Passphrase si la clave está cifrada.

Diagnóstico rápido de errores SSL: si ves UNABLE_TO_VERIFY_LEAF_SIGNATURE, SELF_SIGNED_CERT_IN_CHAIN o similares, casi siempre es porque tu CA corporativa está solo en el almacén del sistema (no en el bundle). Prueba export CLAUDE_CODE_CERT_STORE=bundled,system y, si hace falta, añade el CA explícitamente con NODE_EXTRA_CA_CERTS.

Telemetría y OpenTelemetry

Claude Code puede emitir telemetría con OpenTelemetry (OTEL). Esto es muy útil para empresas que quieren observabilidad centralizada.

  • CLAUDE_CODE_ENABLE_TELEMETRY=1 — Activa OTEL.
  • OTEL_METRICS_EXPORTER — Backend para las métricas: otlp, console, prometheus, etc.
  • CLAUDE_CODE_OTEL_HEADERS_HELPER_DEBOUNCE_MS — Cada cuánto se permite refrescar los headers OTEL via otelHeadersHelper.

Para headers dinámicos (tokens que rotan, firmas por máquina, etc.) usa el setting otelHeadersHelper:

{
    "otelHeadersHelper": "/bin/generate_otel_headers.sh"
}

El script se ejecuta al inicio y periódicamente; devuelve un JSON con los headers que se enviarán al collector OTEL.

Configuración de Red y Proxy (Empresas)

Si trabajas en una oficina con red corporativa, probablemente tienes un proxy. Un proxy es como un guardia de seguridad entre tu computadora e internet. Todo el tráfico pasa por él.

Claude Code necesita conectarse a internet para funcionar. Si hay un proxy de por medio, tienes que decirle dónde está.

Configuración básica de proxy

Configura estas variables de entorno:

export HTTPS_PROXY=http://proxy.empresa.com:8080
export HTTP_PROXY=http://proxy.empresa.com:8080
export NO_PROXY="localhost,192.168.1.0/24,.empresa.com"

NO_PROXY lista los hosts que no deben pasar por el proxy. Puedes separar con comas o espacios. Usa * para bypasear todo.

Si tu proxy necesita usuario y contraseña:

export HTTPS_PROXY=http://usuario:password@proxy.empresa.com:8080

Nota

Claude Code no soporta proxies SOCKS. Solo HTTP y HTTPS.

Certificados personalizados y mTLS

Muchas empresas tienen sus propios certificados de seguridad. Es como una credencial que tu empresa le da a tu computadora para que los servidores confíen en ella.

Si ves errores de SSL al conectar, necesitas esto:

export NODE_EXTRA_CA_CERTS=/ruta/al/certificado-ca.pem

Si tu CA corporativa solo está en el almacén del sistema, también puede ayudar:

export CLAUDE_CODE_CERT_STORE=bundled,system

El default es bundled,system (ambos). Puedes restringir a uno solo si lo necesitas, pero la mayoría de errores SSL se resuelven al combinar ambos almacenes.

Para autenticación mutua (mTLS), donde tanto el cliente como el servidor se identifican:

export CLAUDE_CODE_CLIENT_CERT=/ruta/al/certificado-cliente.pem
export CLAUDE_CODE_CLIENT_KEY=/ruta/a/la-clave-privada.pem
export CLAUDE_CODE_CLIENT_KEY_PASSPHRASE=tu-passphrase

Claude Code necesita conectarse a estos dominios. Asegúrate de que tu firewall los permita:

  • api.anthropic.com — La API de Claude.
  • claude.ai — Autenticación con cuentas Claude.
  • platform.claude.com — Autenticación con Anthropic Console.
  • storage.googleapis.com — Instalador y actualizador (versiones anteriores a 2.1.116).
  • downloads.claude.ai — Descargas del instalador, auto-updater y plugins.
  • bridge.claudeusercontent.com — WebSocket bridge usado por Claude in Chrome.
  • raw.githubusercontent.com — Feed de release notes y contadores de instalación del plugin marketplace.

El Sandbox: Una Jaula de Seguridad

El sandbox es como una jaula transparente. Claude puede trabajar dentro, pero no puede tocar nada fuera de ella. Restringe el acceso al sistema de archivos y a la red a nivel del sistema operativo.

Para activarlo:

{
    "sandbox": {
        "enabled": true,
        "failIfUnavailable": true
    }
}

Cuando el sandbox está activo, los comandos Bash se aprueban automáticamente. Tiene sentido: si Claude está encerrado en una jaula, no puede hacer daño.

El setting failIfUnavailable hace que Claude Code se niegue a arrancar si pides sandbox pero el sistema no puede ofrecerlo. Es la forma segura de evitar caer en un entorno sin protección por accidente.

Por sistema operativo:

  • macOS: usa sandbox-exec nativo.
  • Linux y WSL2: usa bwrap + socat. Si tu IT empaqueta estos binarios en una ruta no estándar, indícalo con sandbox.bwrapPath y sandbox.socatPath (ambos solo managed).
  • Windows: no hay sandbox para Bash. Si tu política requiere sandbox, no uses Bash en Windows nativo; trabaja desde WSL2.

Restricciones de archivos

Controla dónde puede escribir y leer Claude:

{
    "sandbox": {
        "enabled": true,
        "filesystem": {
            "allowWrite": ["//tmp/build", "~/.kube"],
            "denyWrite": ["//etc", "//usr/local/bin"],
            "denyRead": ["~/.aws/credentials"],
            "allowRead": ["."]
        }
    }
}

Los prefijos de ruta son importantes:

  • // — Ruta absoluta desde la raíz del sistema. Ejemplo: //tmp es /tmp.
  • ~/ — Relativo a tu carpeta home.
  • / — Relativo al directorio del archivo de settings.
  • ./ o sin prefijo — Relativo al directorio actual.

El campo allowRead sirve para re-permitir lectura dentro de regiones bloqueadas por denyRead. Es útil cuando quieres bloquear un directorio amplio pero permitir acceso al workspace actual.

Para administradores, sandbox.filesystem.allowManagedReadPathsOnly en managed settings restringe a que solo se respeten las rutas de allowRead definidas por IT.

Restricciones de red

Controla a qué sitios web puede acceder Claude desde dentro del sandbox:

{
    "sandbox": {
        "enabled": true,
        "network": {
            "allowedDomains": ["github.com", "*.npmjs.org"],
            "deniedDomains": ["sensitive.cloud.example.com"],
            "allowLocalBinding": true,
            "allowUnixSockets": ["/var/run/docker.sock"],
            "allowAllUnixSockets": false,
            "allowMachLookup": ["com.apple.coresimulator.*"]
        }
    }
}

allowedDomains acepta wildcards con *. deniedDomains tiene precedencia: aunque un dominio esté en la lista permitida, si también aparece en denegados se bloquea.

Si necesitas que Claude inicie un servidor local de desarrollo, activa allowLocalBinding (solo macOS).

allowUnixSockets permite acceso a sockets Unix específicos (útil para Docker). allowAllUnixSockets permite todos los sockets Unix sin restricción.

allowMachLookup (solo macOS) lista los nombres de servicio XPC/Mach que el sandbox puede consultar. Útil para herramientas Apple como Core Simulator.

Apple Events (solo macOS, v2.1.181): por defecto los comandos dentro del sandbox no pueden enviar Apple Events (la forma en que las apps de macOS se comunican entre sí, como pedirle a Finder o a una app que haga algo). Si lo necesitas, actívalo de forma explícita con sandbox.allowAppleEvents:

{
    "sandbox": {
        "enabled": true,
        "allowAppleEvents": true
    }
}

Es opt-in: solo se abre esta vía si tú lo pides.

Proxy propio dentro del sandbox: si traes tu propio proxy para inspección o monitorización:

  • sandbox.network.httpProxyPort — Puerto HTTP del proxy.
  • sandbox.network.socksProxyPort — Puerto SOCKS5 del proxy.

Sandbox debilitado (avanzado, reduce seguridad):

  • sandbox.enableWeakerNestedSandbox (Linux/WSL2) — Habilita un sandbox más débil para escenarios como Docker no privilegiado. REDUCE LA SEGURIDAD. Úsalo solo si no tienes alternativa.
  • sandbox.enableWeakerNetworkIsolation (macOS) — Permite acceso al TLS trust service. Abre una vía de exfiltración potencial. REDUCE LA SEGURIDAD.

Para administradores, sandbox.network.allowManagedDomainsOnly en managed settings restringe a que solo se respeten los dominios definidos por IT. Dominios no permitidos se bloquean automáticamente.

Excepciones al sandbox

Algunos comandos necesitan ejecutarse fuera del sandbox. Por ejemplo, docker o git a veces necesitan acceso completo:

{
    "sandbox": {
        "enabled": true,
        "excludedCommands": ["docker", "git"],
        "allowUnsandboxedCommands": true
    }
}

Los comandos excluidos se ejecutan fuera de la jaula. Claude seguirá pidiendo permiso para ellos según tus reglas de permisos normales.

Settings Comunes que Vas a Usar

Hay muchos settings disponibles. Aquí van los más útiles para el día a día.

Modelo y preferencias de respuesta

Elige qué modelo de Claude usar y cómo responde:

{
    "model": "claude-sonnet-4-6",
    "alwaysThinkingEnabled": true,
    "outputStyle": "Explanatory",
    "language": "spanish",
    "respectGitignore": true
}
  • model — El modelo por defecto. Sonnet es el balance entre velocidad y calidad.
  • alwaysThinkingEnabled — Claude siempre muestra su razonamiento paso a paso.
  • outputStyle — Cambia lo detalladas que son las respuestas.
  • language — Idioma de la interfaz. También define el idioma del dictado por voz y, desde v2.1.176, el idioma de los títulos de sesión que se generan automáticamente.
  • respectGitignore — Controla si el file picker con @ respeta patrones de .gitignore. Default true.

Aliases de modelo disponibles:

Alias Qué hace
default Limpia override, usa el modelo recomendado del plan.
best El más capaz disponible (actualmente Opus 4.8).
sonnet Último Sonnet (Sonnet 4.6). Balance velocidad/calidad.
opus Último Opus (Opus 4.8). El más potente.
haiku Último Haiku (Haiku 4.5). Rápido y eficiente. Ideal para tareas simples.
fable Claude Fable 5, un modelo mythos-class de uso general (v2.1.170).
sonnet[1m] Sonnet con contexto de 1 millón de tokens.
opus[1m] Opus con contexto de 1 millón de tokens.
opusplan Opus para planificar, Sonnet para ejecutar.

A junio de 2026 el modelo por defecto global de Claude Code es Opus 4.8 (lanzado el 28 de mayo de 2026, v2.1.154). También existe un Opus 4.7 intermedio, además de Sonnet 4.6, Haiku 4.5 y el nuevo Claude Fable 5.

Prioridad de configuración del modelo (de mayor a menor):

  1. /model durante la sesión.
  2. --model al iniciar Claude Code.
  3. Variable ANTHROPIC_MODEL.
  4. model en settings.json.

Si quieres restringir qué modelos puede elegir el usuario:

{
    "availableModels": ["sonnet", "haiku"]
}

La opción Default siempre está disponible, independientemente de availableModels. Si eres administrador y quieres que la restricción cubra también al modelo Default, usa enforceAvailableModels (v2.1.175+, solo managed):

{
    "availableModels": ["sonnet", "haiku"],
    "enforceAvailableModels": true
}

Cadena de fallback de modelos: con fallbackModel (v2.1.166) defines hasta tres modelos de respaldo, en orden, que Claude usa si el modelo primario no está disponible (por carga, región o cuota):

{
    "fallbackModel": ["claude-sonnet-4-6", "claude-haiku-4-5"]
}

También puedes pasarlo al iniciar con el flag --fallback-model.

advisorModel: define el modelo que usa la herramienta advisor del lado del servidor. Acepta los aliases opus, sonnet y fable:

{
    "advisorModel": "opus"
}

modelOverrides (mapear alias a ID del proveedor): útil para Bedrock y Vertex, donde el alias humano claude-opus-4-6 debe resolverse a un ARN o path concreto:

{
    "modelOverrides": {
        "claude-opus-4-6": "arn:aws:bedrock:us-east-1::inference-profile/anthropic.claude-opus-4-6"
    }
}

Autocompletado con @ personalizado: por defecto Claude Code escanea el repo. Si necesitas un picker propio (ej. integrar con un sistema de búsqueda interna):

{
    "fileSuggestion": {
        "type": "command",
        "command": "~/.claude/file-suggestion.sh"
    }
}

Plantilla de URL de PR: si tu organización tiene un proxy de revisión de código (ej. internalreviews), puedes redirigir los links de PR:

{
    "prUrlTemplate": "https://reviews.example.com/{owner}/{repo}/pull/{number}"
}

Sustituye {host}, {owner}, {repo}, {number} y {url}.

Status line personalizada: el comando que define la línea de estado en la parte inferior de la sesión.

{
    "statusLine": {
        "type": "command",
        "command": "~/.claude/statusline.sh"
    }
}

Atribución en commits y PRs

Cuando Claude hace commits o pull requests, agrega un texto de atribución. Puedes personalizarlo:

{
    "attribution": {
     "commit": "🤖 Generated with Claude Code\n\nCo-Authored-By: Claude ",
     "pr": "🤖 Generated with Claude Code"
    },
    "includeGitInstructions": true
}
  • attribution.commit — Texto que se añade al final del mensaje de commit como git trailer. Si pones cadena vacía ("") se oculta toda la atribución.
  • attribution.pr — Texto que se añade a las descripciones de PR. También acepta cadena vacía para ocultarla.
  • attribution.sessionUrl (v2.1.183) — Si lo pones en false, omite el enlace a la sesión de claude.ai que normalmente se añade en commits y PRs. Útil si no quieres exponer URLs internas de sesión en el historial de git.
  • includeGitInstructions — Si vale false, no se incluyen las instrucciones built-in de commit/PR en el system prompt.

Deprecated

includeCoAuthoredBy y el flag CLI --no-co-authored-by están deprecados. La forma actual es attribution.commit / attribution.pr con cadena vacía si quieres ocultar la atribución. Las versiones nuevas seguirán respetando includeCoAuthoredBy por compatibilidad hacia atrás, pero todas las nuevas configuraciones deben usar attribution.

Personalización de la interfaz

Estos settings cambian cómo se ve y se siente Claude Code en tu terminal:

  • tui — Renderer del TUI: "default" (clásico) o "fullscreen" (alt-screen, sin parpadeo). Default: "default".
  • viewMode — Modo de visualización del transcript: "default", "verbose" o "focus".
  • showTurnDuration — Muestra cuánto tardó cada respuesta (default: true).
  • showThinkingSummaries — Muestra resúmenes de extended thinking en sesiones interactivas (default: false).
  • spinnerTipsEnabled — Muestra tips educativos mientras esperas (default: true).
  • terminalProgressBarEnabled — Barra de progreso visual (default: true).
  • syntaxHighlightingDisabled — Si vale true, desactiva el resaltado de sintaxis en diffs, bloques de código y previews.
  • prefersReducedMotion — Reduce animaciones. Útil si tu terminal es lento o por accesibilidad.
  • autoScrollEnabled — Sigue automáticamente la salida nueva al fondo en renderizado fullscreen (default: true).
  • awaySummaryEnabled — Muestra un resumen de una línea al regresar tras unos minutos away.
  • preferredNotifChannel — Canal de notificaciones: "auto", "terminal_bell", "iterm2", "iterm2_with_bell", "kitty", "ghostty" o "notifications_disabled".
  • defaultShell — Shell por defecto para comandos con !: "bash" o "powershell".
  • axScreenReader (v2.1.181) — Si vale true, renderiza la salida como texto plano apto para lectores de pantalla. Es el equivalente en settings de la variable de entorno CLAUDE_AX_SCREEN_READER=1, y complementa al ya existente CLAUDE_CODE_ACCESSIBILITY.
  • wheelScrollAccelerationEnabled (v2.1.174) — Controla la aceleración del scroll con la rueda del ratón en renderizado fullscreen. Default true; ponlo en false si el scroll te resulta demasiado brusco.

Badges de enlace por regex (footerLinksRegexes, v2.1.176): renderiza enlaces clicables en el footer cuando la salida del turno coincide con un patrón. Perfecto para convertir IDs de tickets en links directos:

{
    "footerLinksRegexes": [
        {
            "type": "regex",
            "pattern": "PROJ-\\d+",
            "url": "https://issues.example.com/browse/{key}",
            "label": "{key}"
        }
    ]
}

Solo se lee de user settings, del flag --settings y de managed settings.

Puedes personalizar hasta los verbos del spinner de carga:

{
    "spinnerVerbs": {
        "mode": "append",
        "verbs": ["Meditando", "Filosofando"]
    }
}

Y también los tips que se muestran junto al spinner:

{
    "spinnerTipsOverride": {
        "excludeDefault": true,
        "tips": [
            "Recuerda usar nuestra herramienta interna de revisión antes de hacer push.",
            "Los secretos van en Vault, no en .env."
        ]
    }
}

Esto sustituye o complementa los tips por defecto. Es perfecto para que IT mande mensajes contextuales sin interrumpir el flujo.

Limpieza y retención de datos

Claude Code guarda datos temporales como logs y cache. Por defecto, se limpian cada 30 días.

{
    "cleanupPeriodDays": 20
}

Baja el número si quieres que se limpie más seguido. Súbelo si quieres conservar el historial más tiempo.

Configuración de Skills

Los skills son extensiones de Claude Code (ver capítulo 16). Hay cuatro settings para afinar cómo se descubren y se ejecutan:

  • maxSkillDescriptionChars (v2.1.105+) — Tope de caracteres combinados de description + when_to_use por skill. Default: 1536. Subirlo si tus skills tienen descripciones largas y se truncan.
  • skillListingBudgetFraction (v2.1.105+) — Fracción del contexto reservada para el listado de skills. Default: 0.01 (1%). Subirlo si tienes muchos skills y los menos prioritarios no aparecen.
  • skillOverrides (v2.1.129+) — Visibilidad por skill. Valores: "on" (visible y ejecutable), "name-only" (solo el nombre, sin description), "user-invocable-only" (solo cuando el usuario lo invoca explícitamente), "off" (desactivado).
  • disableSkillShellExecution — Si vale true, los skills no pueden ejecutar shell inline; se sustituye por el mensaje [shell command execution disabled by policy].

Ejemplo combinando los cuatro:

{
    "maxSkillDescriptionChars": 2048,
    "skillListingBudgetFraction": 0.02,
    "skillOverrides": {
      "legacy-context": "name-only",
      "deploy": "off",
      "sensitive-action": "user-invocable-only"
    },
    "disableSkillShellExecution": false
}

Permisos para skills: Skill es una tool más en permissions.allow / deny / ask:

  • Skill(commit) — Invocación exacta.
  • Skill(review-pr *) — Con cualquier argumento.

Variable de entorno relacionada: SLASH_COMMAND_TOOL_CHAR_BUDGET override directo del presupuesto de caracteres del listing (sobrescribe skillListingBudgetFraction).

Voz y dictado

Claude Code soporta dictado por voz. Requiere cuenta Claude.ai: no funciona con API key sola.

{
    "voice": {
        "enabled": true,
        "mode": "hold",
        "autoSubmit": false
    }
}
  • voice.enabled — Habilita el dictado.
  • voice.mode — "hold" mantienes la tecla pulsada para grabar, "tap" es toggle.
  • voice.autoSubmit — En modo hold, envía automáticamente el prompt al soltar.

El idioma de dictado es el del setting language.

Deprecated

El setting voiceEnabled (sin namespace) está deprecado. Usa voice.enabled.

Worktrees (para subagentes y background agents)

Cuando un subagente o un background agent necesita un worktree git, puedes controlar cómo se crea:

{
    "worktree": {
        "baseRef": "head",
        "symlinkDirectories": ["node_modules", ".cache"],
        "sparsePaths": ["packages/my-app", "shared/utils"]
    }
}
  • worktree.baseRef — Desde dónde se ramifica. "fresh" (default) parte del remoto limpio. "head" parte de tu estado local actual.
  • worktree.symlinkDirectories — Directorios a symlinkear del repo principal en lugar de duplicarlos. Ahorra mucho disco con node_modules.
  • worktree.sparsePaths — Paths a aplicar como sparse-checkout en cada worktree nuevo.

Útil para monorepos grandes donde un checkout completo sería demasiado lento.

Settings de hooks

Los hooks se documentan a fondo en el capítulo 17. Aquí van los settings que controlan su comportamiento global:

  • disableAllHooks — Si vale true, desactiva todos los hooks y la status line personalizada. Útil cuando debuggeas un hook problemático.
  • allowedHttpHookUrls — Lista blanca de URLs (con wildcard *) que pueden recibir HTTP hooks. Si está definida, solo esas URLs reciben hooks; el resto se bloquea.
  • httpHookAllowedEnvVars — Lista blanca de variables de entorno que los HTTP hooks pueden interpolar en headers. Evita que cualquier variable del shell se filtre por accidente.
  • allowManagedHooksOnly — (Solo managed) Solo cargan hooks managed/SDK y hooks de plugin force-enabled. Ignora hooks de usuario y proyecto.

Ejemplo de configuración segura de hooks HTTP:

{
    "allowedHttpHookUrls": [
      "https://hooks.example.com/*",
      "https://internal.acme.corp/audit/*"
    ],
    "httpHookAllowedEnvVars": ["HOOK_SECRET", "AUDIT_TOKEN"]
}

Settings de MCP servers

La configuración profunda de MCP vive en el capítulo 18. Estos settings controlan qué servidores MCP se aceptan:

  • allowedMcpServers — (Solo managed) Lista blanca de servidores MCP que los usuarios pueden configurar.
  • deniedMcpServers — (Solo managed) Lista negra; tiene precedencia sobre allowedMcpServers.
  • allowManagedMcpServersOnly — (Solo managed) Solo se aplica la lista blanca de admin; bloquea cualquier adición de usuario.
  • enableAllProjectMcpServers — Auto-aprueba todos los servidores MCP de .mcp.json del proyecto.
  • enabledMcpjsonServers — Lista de servidores específicos del .mcp.json a aprobar.
  • disabledMcpjsonServers — Lista de servidores específicos del .mcp.json a rechazar.

Ejemplo selectivo:

{
    "enableAllProjectMcpServers": false,
    "enabledMcpjsonServers": ["github", "memory"],
    "disabledMcpjsonServers": ["filesystem"]
}

Scripts auxiliares de autenticación

Claude Code puede ejecutar scripts cortos para generar o refrescar credenciales en tiempo de ejecución. Útil para entornos enterprise con tokens de corta duración.

  • apiKeyHelper — Script (ejecutado con /bin/sh) que devuelve el valor de autenticación. Se envía como X-Api-Key y Authorization: Bearer. Útil para integraciones con vaults internos.
{
    "apiKeyHelper": "/bin/generate_temp_api_key.sh"
}

Variable relacionada: CLAUDE_CODE_API_KEY_HELPER_TTL_MS controla cada cuánto se refresca.

  • awsAuthRefresh — Script que modifica el directorio .aws para refrescar credenciales AWS (ej: aws sso login). Útil cuando trabajas contra Bedrock.
  • awsCredentialExport — Alternativa: script que devuelve JSON con credenciales AWS, sin tocar el directorio .aws.
  • gcpAuthRefresh — Script que refresca las Application Default Credentials de GCP. Ejemplo típico: gcloud auth application-default login.
  • otelHeadersHelper — Script para generar headers OTEL dinámicos (ver subsección de telemetría OTEL).

Todos estos scripts se ejecutan al inicio y, en el caso de los de auth, periódicamente. Ten cuidado con scripts lentos: bloquean la sesión hasta terminar.

Settings para Administradores (Empresas)

Si eres administrador de IT, estos settings te dan control sobre lo que hacen todos los usuarios de tu organización.

Server-managed settings (beta)

Disponible para Claude for Teams (v2.1.38+) y Enterprise (v2.1.30+). Se configuran desde la web en Claude.ai.

El proceso es así:

  1. Ve a Claude.ai > Admin Settings > Claude Code > Managed settings.
  2. Configura las reglas que necesites.
  3. Claude Code las descarga al iniciar y hace un chequeo cada hora.

Solo los roles Primary Owner y Owner pueden gestionarlos.

Para garantizar que las políticas siempre estén actualizadas, puedes usar forceRemoteSettingsRefresh en managed settings. Con este flag, Claude Code bloquea su inicio hasta obtener los settings frescos del servidor. Si falla la conexión, la CLI no arranca.

Limitaciones actuales (beta):

  • Se aplican a todos los usuarios por igual. No hay grupos.
  • No puedes distribuir configuraciones de MCP servers.
  • No funcionan con proveedores de terceros (Bedrock, Vertex, Foundry).

Controles de seguridad para admins

Estos settings solo funcionan en managed settings:

  • disableBypassPermissionsMode: "disable" — Bloquea el modo que salta todos los permisos.
  • disableAutoMode: "disable" — Bloquea el modo auto con clasificador de seguridad.
  • allowManagedPermissionRulesOnly: true — Solo aplican las reglas de permisos definidas por IT.
  • allowManagedHooksOnly: true — Solo hooks definidos por IT.
  • allowManagedMcpServersOnly: true — Solo MCP servers aprobados por IT.
  • allow_remote_sessions: false — Bloquea sesiones remotas.
  • forceLoginOrgUUID — Requiere login a una organización específica.
  • forceLoginMethod — Restringe método de login ("claudeai" o "console").

También puedes enviar anuncios a todos los usuarios:

{
    "companyAnnouncements": [
        "Usa solo los MCP servers aprobados por IT.",
        "Reporta cualquier problema al canal #claude-soporte."
    ]
}

Plugins y Marketplaces

Claude Code soporta plugins: extensiones que agregan funcionalidad. Los plugins vienen de marketplaces, que son como tiendas de aplicaciones.

Habilitar y deshabilitar plugins

{
    "enabledPlugins": {
        "formatter@acme-tools": true,
        "analyzer@security-plugins": false
    }
}

El formato es nombre@marketplace. Pon true para activar, false para desactivar.

Agregar marketplaces

Puedes agregar fuentes de plugins adicionales. Los marketplaces soportan siete tipos de fuentes:

  1. github — Un repositorio de GitHub.
  2. git — Cualquier repositorio Git (GitLab, Bitbucket, etc.).
  3. url — Un JSON remoto con headers opcionales.
  4. npm — Un paquete de NPM.
  5. file — Un archivo local.
  6. directory — Un directorio local.
  7. hostPattern — Un patrón regex para matching de hosts.

Los administradores pueden restringir qué marketplaces se usan con strictKnownMarketplaces y bloquear fuentes con blockedMarketplaces.

Ejemplos Prácticos

Configuración básica para un desarrollador individual

{
    "$schema": "https://json.schemastore.org/claude-code-settings.json",
    "permissions": {
         "allow": [
             "Bash(npm run *)",
             "Bash(git commit *)",
             "Bash(* --version)",
             "Bash(* --help *)"
         ],
         "deny": [
             "Bash(curl *)",
             "Read(./.env)",
             "Read(./.env.*)"
         ]
    },
    "model": "claude-sonnet-4-6",
    "spinnerTipsEnabled": true
}

Guarda esto en ~/.claude/settings.json. Permite ejecutar npm y git commit sin preguntar. Bloquea curl y la lectura de archivos .env por seguridad. Usa Sonnet como modelo base.

Configuración de proyecto para un equipo

{
    "permissions": {
        "allow": [
            "Bash(npm run lint)",
            "Bash(npm run test *)",
            "Bash(npm run build)"
        ],
        "deny": [
            "Read(./.env)",
            "Read(./.env.*)",
            "Read(./secrets/**)",
            "Bash(rm -rf *)"
        ],
        "ask": [
            "Bash(git push *)"
        ]
    },
    "env": {
        "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
    }
}

Guarda esto en .claude/settings.json y súbelo a git. Todos los del equipo tendrán las mismas reglas. Claude puede correr lint, tests y build. No puede leer secretos ni borrar archivos. Para push, pregunta cada vez.

Variables de entorno para empresa con proxy

# En tu .bashrc o .zshrc
export HTTPS_PROXY=http://proxy.empresa.com:8080
export NO_PROXY="localhost,.empresa.com"
export NODE_EXTRA_CA_CERTS=/etc/ssl/empresa-ca.pem

Configura el proxy corporativo, los hosts que no pasan por el proxy, y el certificado de seguridad de tu empresa. Agrega estas líneas a tu archivo de perfil de shell.

Sandbox completo para entornos seguros

{
    "sandbox": {
        "enabled": true,
        "autoAllowBashIfSandboxed": true,
        "excludedCommands": ["docker", "git"],
        "filesystem": {
            "allowWrite": ["//tmp/build", "~/.cache"],
            "denyWrite": ["//etc", "//usr"],
            "denyRead": ["~/.aws/credentials", "~/.ssh"]
        },
        "network": {
            "allowedDomains": ["github.com", "*.npmjs.org", "registry.yarnpkg.com"],
            "allowLocalBinding": true
        }
    }
}

Activa el sandbox con restricciones de archivos y red. Claude solo puede escribir en /tmp/build y en cache. No puede leer credenciales de AWS ni claves SSH. Solo puede acceder a GitHub y NPM por red. Docker y git se ejecutan fuera del sandbox.

Ver settings activos y permisos

/status
/permissions

Escribe /status para ver todas las fuentes de configuración activas. Escribe /permissions para ver todas las reglas de permisos y desde qué archivo vienen. Estos son los primeros comandos que debes probar si algo no funciona como esperas.

Auto mode con infraestructura confiable

{
    "autoMode": {
        "environment": [
            "Organization: Acme Corp. Primary use: software development",
            "Source control: github.example.com/acme-corp",
            "Trusted cloud buckets: s3://acme-build-artifacts",
            "Trusted internal domains: *.corp.example.com"
        ]

}

Configura el clasificador de auto mode con la infraestructura confiable de tu organización. Solo se lee de user settings, local settings, o managed settings. NO de project settings compartidos.

Configurar esfuerzo y contexto extendido

/effort high
/model opus[1m]
claude --effort xhigh --model opus[1m]

Ejemplos de cómo configurar nivel de esfuerzo y contexto extendido de 1M tokens. El nivel xhigh solo funciona con Opus 4.8 (anteriormente se llamaba 'max'). Los aliases [1m] activan la ventana de 1 millón de tokens, ahora a tarifa plana sin recargo.

Receta enterprise lockdown (managed settings)

{
    "permissions": {
         "disableBypassPermissionsMode": "disable"
    },
    "allowManagedPermissionRulesOnly": true,
    "allowManagedHooksOnly": true,
    "allowManagedMcpServersOnly": true,
    "disableAutoMode": "disable",
    "autoUpdatesChannel": "stable",
    "minimumVersion": "2.1.100",
    "sandbox": {
         "enabled": true,
         "failIfUnavailable": true,
         "filesystem": {
             "allowRead": ["."],
             "denyRead": ["~/.aws", "~/.ssh", "~/.gnupg"],
             "allowManagedReadPathsOnly": true
         },
         "network": {
             "allowedDomains": ["github.com", "api.anthropic.com", "registry.npmjs.org"],
             "allowManagedDomainsOnly": true
         }
    }
}

Combinación recomendada para entornos enterprise con políticas estrictas. Guárdalo en el archivo de managed settings de tu sistema. Bloquea bypass de permisos, fuerza que solo cuenten las reglas de IT (permisos, hooks, MCP), exige sandbox y restringe el acceso a archivos y red a lo que IT aprueba explícitamente. Combinado con autoUpdatesChannel='stable' y minimumVersion, garantiza un entorno consistente y predecible para toda la organización.

modelOverrides para Amazon Bedrock con ARN

{
    "modelOverrides": {
        "claude-opus-4-6": "arn:aws:bedrock:us-east-1::inference-profile/anthropic.claude-opus-4-6",
        "claude-sonnet-4-6": "arn:aws:bedrock:us-east-1::inference-profile/anthropic.claude-sonnet-4-6"
    },
    "env": {
        "CLAUDE_CODE_USE_BEDROCK": "1",
        "AWS_REGION": "us-east-1"
    }
}

Mapea los aliases humanos de Anthropic a los ARNs específicos del inference profile de tu cuenta Bedrock. Así puedes seguir usando 'opus' o 'sonnet' en /model y en código, pero internamente Claude Code resuelve al ARN correcto. Imprescindible cuando trabajas con perfiles de inferencia personalizados o cross-region.

Conexiones SSH para Claude Code Desktop

{
    "sshConfigs": [
        {
            "id": "dev-vm",
            "name": "Dev VM",
            "sshHost": "enrique@dev.example.com",
            "sshPort": 22,
            "sshIdentityFile": "~/.ssh/dev-key",
            "startDirectory": "~/projects/api"
        },
        {
            "id": "staging",
            "name": "Staging Box",
            "sshHost": "deploy@staging.example.com"
        }
    ]
}

Define conexiones SSH que aparecen en el dropdown del entorno de Claude Code Desktop. Cada entrada necesita id, name y sshHost; sshPort, sshIdentityFile y startDirectory son opcionales. Es la forma limpia de mover sesiones de Claude Code a máquinas remotas sin reconfigurar nada cada vez.

Consejo

Siempre agrega el campo $schema en tus settings.json. Tu editor te ayudará con autocompletado y detectará errores antes de que Claude Code los lea.

Consejo

Usa /status para diagnosticar problemas. Te muestra exactamente qué configuración está activa y de dónde viene cada setting.

Advertencia

Los deny SIEMPRE ganan. Si algo está denegado en cualquier nivel de la jerarquía, ningún otro nivel puede permitirlo. Si un permiso no funciona, revisa si hay un deny en algún nivel superior.

Advertencia

Los patrones de permisos para Bash son útiles pero no infalibles. Un usuario creativo podría encontrar variaciones del comando que eviten la restricción. Para seguridad crítica, usa el sandbox.

Nota

Las listas de permisos (allow, deny, ask) se combinan entre niveles, no se reemplazan. Si tu settings de usuario permite 'npm run test' y el de proyecto permite 'npm run lint', ambos quedan permitidos.

Consejo

Presiona Shift+Tab durante una sesión para cambiar rápidamente entre modos de permisos. No necesitas reiniciar Claude Code.

Advertencia

Nunca uses bypassPermissions en tu máquina personal. Ese modo es exclusivamente para containers y máquinas virtuales donde no hay riesgo.

Nota

WebFetch(domain:...) no bloquea el acceso a la red vía Bash. Si Claude tiene permiso para ejecutar Bash, podría usar curl o wget. Para restricciones de red robustas, usa el sandbox.

Consejo

Claude Code crea backups automáticos de tus archivos de configuración con timestamps. Se retienen los 5 más recientes. Si algo sale mal, puedes recuperar una versión anterior.

Advertencia

En Auto Mode, si defines allow o soft_deny, REEMPLAZAN toda la lista default. No se combinan. Antes de modificarlas, revisa las reglas por defecto con claude auto-mode defaults.

Advertencia

El nivel máximo de esfuerzo se llama xhigh, NO max. Si tu config usa max en effortLevel, CLAUDE_CODE_EFFORT_LEVEL o /effort, el valor se ignora y caes al nivel por defecto. Es la regresión silenciosa más común al actualizar configuraciones viejas.

Advertencia

Windows: la ruta legacy C:\ProgramData\ClaudeCode\managed-settings.json NO se soporta desde v2.1.75. Si tu MDM aún despliega ahí, las políticas dejan de aplicar sin error visible. Migra a C:\Program Files\ClaudeCode\managed-settings.json (o usa las claves de registro HKLM\SOFTWARE\Policies\ClaudeCode).

Nota

Migración v2.1.119: si actualizas desde una versión antigua, los settings autoScrollEnabled, editorMode, showTurnDuration, teammateMode y terminalProgressBarEnabled solían vivir en ~/.claude.json. Desde v2.1.119 ya pertenecen a settings.json. Si los movieras manualmente, asegúrate de que tu archivo esté actualizado.

Consejo

includeCoAuthoredBy y --no-co-authored-by están deprecados. Usa attribution.commit y attribution.pr con cadena vacía ("") si quieres ocultar la atribución en commits y PRs.

Consejo

Para errores de SSL corporativos, prueba primero CLAUDE_CODE_CERT_STORE=bundled,system. Resuelve la mayoría de casos donde el CA de la empresa solo está instalado en el almacén del sistema operativo.

Resumen del Capítulo

Claude Code se configura con archivos JSON en tres ubicaciones principales: usuario (~/.claude/settings.json), proyecto (.claude/settings.json) y local (.claude/settings.local.json), más managed settings para empresas. Los permisos controlan qué puede hacer Claude usando reglas allow, ask y deny (incluyendo Skill() y Agent()), donde deny siempre gana. Hay seis modos de permisos, incluyendo el modo auto que usa un clasificador de seguridad. Los niveles de esfuerzo (low/medium/high/xhigh — xhigh, NO 'max') controlan cuánto razona Claude, y los aliases de modelo con sufijo [1m] activan el contexto extendido de 1 millón de tokens. Las variables de entorno cubren autenticación, modelo, proxy, TLS/certificados (CLAUDE_CODE_CERT_STORE), telemetría OTEL y comportamiento avanzado. El sandbox aísla a nivel de SO (sandbox-exec en macOS, bwrap+socat en Linux/WSL2; sin sandbox en Windows). Para entornos empresariales hay una receta de lockdown que combina allowManaged*Only + sandbox.*.allowManaged*Only + disableBypassPermissionsMode. Los managed settings avanzados incluyen policyHelper, parentSettingsBehavior y disableRemoteControl. Settings nuevos cubren skills, voice, worktree, hooks, MCP, scripts de auth y control de actualizaciones (autoUpdatesChannel, minimumVersion). includeCoAuthoredBy está deprecated en favor de attribution.commit / attribution.pr.
