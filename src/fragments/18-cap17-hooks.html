Hooks

Automatiza tareas con acciones que se disparan solas en el momento justo

Intermedio

Los hooks son acciones automáticas que se ejecutan solas cuando algo pasa en Claude Code. Piensa en ellos como trampas inteligentes: tú las preparas, y cuando Claude hace algo específico, la trampa se activa. En este capítulo vas a aprender a crear tus propios hooks para formatear código, proteger archivos, recibir notificaciones y mucho más.

Qué son los hooks y para qué sirven

Imagina que tienes un asistente en tu cocina. Cada vez que termina de cocinar, tú quieres que lave los platos automáticamente. No quieres pedirlo cada vez. Quieres que lo haga solo.

Eso es exactamente un hook. Es una instrucción que le dices a Claude Code: "Cuando pase ESTO, haz AQUELLO".

Sin hooks, dependes de que Claude "recuerde" hacer ciertas cosas. A veces lo hace, a veces no. Con hooks, la acción ocurre siempre. Es automática y garantizada.

Por qué usar hooks en lugar de instrucciones

Puedes escribir en tu CLAUDE.md: "Siempre formatea el código con Prettier después de editar". Pero Claude es un modelo de lenguaje. A veces se le olvida.

Un hook no se olvida nunca. Es como una alarma programada. No importa lo que pase, se ejecuta.

Usa hooks cuando necesites que algo pase el 100% de las veces. Usa instrucciones en CLAUDE.md cuando sea una preferencia, no una obligación.

Los cinco tipos de hooks

Hay cinco formas de crear un hook. Cada una tiene su propia personalidad:

  • Command — Ejecuta un comando de terminal. Es el más común. Ejemplo: correr prettier para formatear código.
  • HTTP — Envía datos a una URL. Útil para conectar con servicios externos. Ejemplo: notificar a un servidor cuando Claude termina una tarea.
  • MCP tool — Invoca una tool de un servidor MCP que ya está conectado. Útil cuando el chequeo que quieres hacer ya existe como tool MCP. Ejemplo: lanzar un escáner de seguridad expuesto por tu servidor MCP interno.
  • Prompt — Le pregunta a un modelo de IA si la acción está bien. Es como tener un segundo par de ojos. Ejemplo: verificar si Claude debería dejar de trabajar.
  • Agent — Lanza un mini-agente que puede leer archivos y verificar cosas antes de decidir. Ejemplo: revisar que los tests pasen antes de dar luz verde.

Los tres primeros (command, HTTP y MCP tool) son determinísticos: siempre hacen lo mismo. Los dos últimos (prompt y agent) usan juicio de IA: evalúan la situación y deciden.

El ciclo de vida: cuándo se disparan los hooks

Claude Code sigue un ciclo durante cada sesión. Es como una rutina. Los hooks se conectan a momentos específicos de esa rutina.

Piensa en tu día: te levantas, desayunas, trabajas, almuerzas, trabajas más, cenas, duermes. Podrías poner una "alarma" en cualquiera de esos momentos.

Así funciona con Claude Code. Estos son los momentos clave:

  1. SessionStart — Claude arranca o se reanuda.
  2. UserPromptSubmit — Tú envías un mensaje.
  3. PreToolUse — Claude está a punto de usar una herramienta.
  4. PermissionRequest — Claude pide permiso para algo.
  5. PostToolUse — La herramienta terminó con éxito.
  6. PostToolUseFailure — La herramienta falló.
  7. PostToolBatch — Un grupo de herramientas paralelas terminó.
  8. CwdChanged — Claude cambió de directorio (hizo cd).
  9. PostCompact — Claude acaba de compactar el contexto.
  10. Stop — Claude termina de responder.
  11. SessionEnd — La sesión se cierra.

Hay más eventos (los veremos todos), pero estos son los que vas a usar el 90% del tiempo.

El flujo paso a paso

Cuando inicias Claude Code, el flujo es así:

SessionStart
   └─ Tú escribes algo → UserPromptSubmit
        └─ Claude quiere usar Bash → PreToolUse
                └─ Si necesita permiso → PermissionRequest
                └─ Bash se ejecuta bien → PostToolUse
                └─ Bash falla → PostToolUseFailure
        └─ Si lanza varias tools en paralelo → PostToolBatch
        └─ Si hizo cd → CwdChanged
        └─ Si el contexto crece y compacta → PostCompact
        └─ Claude termina → Stop
   └─ Cierras sesión → SessionEnd

Los pasos del medio se repiten muchas veces. Claude usa herramientas constantemente. Cada uso dispara los hooks correspondientes.

Algunos eventos no aparecen en el flujo típico pero son igual de importantes: PostToolBatch dispara una vez por cada grupo de herramientas paralelas (no por cada herramienta), justo antes de que Claude vuelva a pensar. CwdChanged dispara cada vez que cambia el directorio actual y es perfecto para recargar entornos como direnv. PostCompact dispara después de cada compactación y sirve para volver a inyectar lo que importa. MessageDisplay dispara mientras la respuesta de Claude se escribe en pantalla y permite transformar u ocultar ese texto en la salida visible (por ejemplo, para tapar secretos).

Cómo configurar tu primer hook

Hay dos formas de crear hooks: el menú interactivo o editando JSON directamente.

Forma fácil: el menú /hooks

Dentro de Claude Code, escribe /hooks y presiona Enter. Se abre un menú donde puedes:

  • Ver todos los hooks configurados
  • Agregar nuevos hooks de tipo command
  • Eliminar hooks existentes
  • Deshabilitar todos los hooks con un toggle

El menú muestra etiquetas: [User] para hooks globales, [Project] para hooks del proyecto, y [Local] para hooks locales.

Esta es la forma más fácil de empezar. Pero solo funciona para hooks de tipo command. Para HTTP, prompt o agent, necesitas editar el JSON a mano.

Forma completa: editar el JSON

Los hooks viven dentro de los archivos de settings. La estructura tiene tres niveles. Piensa en cajas dentro de cajas:

  1. Caja grande: El evento (cuándo se dispara)
  2. Caja mediana: El matcher (qué filtra)
  3. Caja pequeña: El handler (qué hace)

Así se ve en JSON:

{
    "hooks": {
        "PostToolUse": [
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": "echo 'Se editó un archivo!'"
                    }
                ]
            }
        ]
    }
}

Traducido al español: "Después de que Claude use Edit o Write, ejecuta este comando".

Dónde guardar tus hooks

Puedes guardar hooks en distintos lugares. Cada uno tiene un alcance diferente:

  • ~/.claude/settings.json — Usuario. Aplica a todos tus proyectos. No se comparte con el equipo.
  • .claude/settings.json — Proyecto. Aplica solo a este proyecto. Se puede commitear al repo.
  • .claude/settings.local.json — Local. Aplica solo a este proyecto, pero no se comparte (está en gitignore).
  • Managed policy — Organización. Lo configura el admin. No se puede deshabilitar.
  • Plugin hooks/hooks.json — Hooks empaquetados con un plugin. Aplican mientras el plugin está activo. Útil para distribuir suites de hooks como una unidad.
  • Frontmatter de skill o subagente — Hooks que viven mientras el componente está activo. Cuando termina, se limpian solos.

Si un hook es personal (como notificaciones), ponlo en User. Si es del equipo (como formateo de código), ponlo en Project.

El menú /hooks ahora muestra de qué fuente viene cada hook: [User], [Project], [Local], [Plugin], [Session] (los inyectados por skills o subagentes activos) y [Built-in] (los que vienen con Claude Code).

Matchers: filtrar cuándo se dispara un hook

Un matcher es un filtro. Le dice al hook: "Solo dispárate cuando coincida con esto".

Es como un portero de discoteca. No deja pasar a todos. Solo a los que están en la lista.

El matcher usa expresiones regulares (regex). No te asustes. Los patrones más comunes son simples:

  • "Bash" — Solo cuando la herramienta es Bash.
  • "Edit|Write" — Cuando es Edit O Write (la barra | significa "o").
  • "mcp__github__.*" — Cualquier herramienta del servidor MCP de GitHub (el .* significa "cualquier cosa después").
  • "" o sin matcher — Se dispara SIEMPRE, sin filtro.

Qué filtra cada evento

Cada evento filtra por un campo diferente. Aquí está la guía rápida:

  • PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied — Filtran por tool_name. Ejemplo: "Bash", "Edit", "mcp__memory__create_entities".
  • SessionStart — Filtra por source. Valores posibles: startup, resume, clear, compact.
  • Setup — Filtra por trigger. Valores: init, maintenance.
  • SessionEnd — Filtra por reason. Valores: clear, resume, logout, prompt_input_exit, bypass_permissions_disabled, other.
  • Notification — Filtra por notification_type. Valores: permission_prompt, idle_prompt, auth_success, elicitation_dialog, elicitation_complete, elicitation_response.
  • SubagentStart, SubagentStop — Filtran por agent_type. Ejemplo: "Explore", "Plan".
  • ConfigChange — Filtra por source. Valores: user_settings, project_settings, local_settings, policy_settings, skills.
  • PreCompact, PostCompact — Filtran por trigger. Valores: manual, auto.
  • InstructionsLoaded — Filtra por load_reason. Valores: session_start, nested_traversal, path_glob_match, include, compact.
  • StopFailure — Filtra por tipo de error API. Valores: rate_limit, authentication_failed, oauth_org_not_allowed, billing_error, invalid_request, server_error, max_output_tokens, unknown.
  • UserPromptExpansion — Filtra por command_name o por el nombre del skill/comando que se expandió.
  • FileChanged — ¡Ojo! Su matcher no es regex: se splittea por | como lista literal de nombres de archivo. ".envrc|.env" matchea esos dos archivos exactos.
  • Elicitation, ElicitationResult — Filtran por nombre del servidor MCP.

Algunos eventos no soportan matchers y siempre se disparan: UserPromptSubmit, PostToolBatch, Stop, TeammateIdle, TaskCreated, TaskCompleted, WorktreeCreate, WorktreeRemove y CwdChanged.

Corrección importante

Al contrario de lo que decía la documentación antigua, InstructionsLoaded sí soporta matchers. Puedes filtrar por load_reason para distinguir entre la carga inicial, la carga lazy por traversal, los includes y la recarga tras compactar.

Cómo se comunican los hooks con Claude Code

Los hooks hablan con Claude Code de dos formas: exit codes y JSON output.

Piensa en los exit codes como semáforos:

  • Exit 0 (verde) — Todo bien. La acción puede continuar.
  • Exit 2 (rojo) — Alto. Bloquea la acción.
  • Cualquier otro (amarillo) — Hubo un problema, pero no es grave. La acción continúa.

Exit codes en detalle

Con exit 0, Claude Code busca JSON en stdout. Si encuentra JSON válido, lo procesa. Si encuentra texto plano, lo agrega como contexto para Claude.

Con exit 2, Claude Code ignora stdout. Lee stderr y se lo muestra a Claude como error. El efecto depende del evento:

  • En PreToolUse — bloquea la herramienta.
  • En UserPromptSubmit — borra el prompt completo.
  • En Stop — obliga a Claude a seguir trabajando.
  • En TaskCompleted — impide marcar la tarea como completada.

Con cualquier otro código (1, 3, 127, etc.): stderr se muestra en modo verbose (Ctrl+O) y la vida sigue.

JSON output para control fino

Los exit codes son simples: sí o no. Pero a veces necesitas más control. Ahí entra el JSON output.

Tu hook puede imprimir JSON en stdout. Estos son los campos más útiles:

{
    "decision": "block",
    "reason": "No puedes hacer eso porque..."
}

O para PreToolUse, que usa un formato especial:

{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "Archivo protegido"
    }
}

Campos universales que funcionan en todos los eventos:

  • continue — Si lo pones en false, Claude deja de procesar por completo.
  • stopReason — Mensaje para el usuario cuando continue es false.
  • suppressOutput — Si es true, oculta el output en modo verbose.
  • systemMessage — Muestra un mensaje de advertencia al usuario.
  • terminalSequence — Escribe secuencias de escape de terminal (window title, notificaciones del SO, progreso en la barra de tareas).

terminalSequence: los hooks no pueden escribir a /dev/tty. Si querías parpadear el icono del Dock o cambiar el título de la ventana, este es el camino. Las secuencias permitidas son OSC 0 (icono + título), OSC 1 (icono), OSC 2 (título), OSC 9 (notificaciones de iTerm2, ConEmu, Windows Terminal y WezTerm, más progreso en la barra), OSC 99 (Kitty), OSC 777 (urxvt, Ghostty, Warp) y el BEL pelado. Sintaxis: \033]NUM;contenido\007 (con BEL) o \033]NUM;contenido\033\\ (con ST).

Límite de 10.000 caracteres: el output total de un hook (stdout, additionalContext y systemMessage) está capado a 10.000 caracteres. Si te pasas, Claude Code escribe el exceso a un archivo y le pasa al modelo un preview con la ruta. Tu hook sigue funcionando, pero el modelo solo verá el preview a menos que abra el archivo. Si vas a inyectar mucho contexto, escríbelo tú mismo a un archivo y referencia la ruta.

Qué datos recibe tu hook

Cuando un hook se dispara, recibe información sobre lo que está pasando. Para hooks de tipo command, estos datos llegan por stdin en formato JSON.

Todos los hooks reciben estos campos básicos:

  • session_id — ID único de la sesión.
  • transcript_path — Ruta al archivo de la conversación.
  • cwd — Directorio de trabajo actual.
  • permission_mode — Modo de permisos (default, plan, dontAsk, etc.).
  • hook_event_name — Nombre del evento que disparó el hook.

Además de estos, cada evento agrega sus propios campos. Por ejemplo, PreToolUse incluye tool_name y tool_input con los parámetros de la herramienta.

Referencia completa de eventos

Aquí tienes todos los eventos disponibles. Para cada uno, te explico cuándo se dispara, qué datos recibe y qué puedes hacer con él.

SessionStart

Cuándo: La sesión arranca o se reanuda.

Matcher: Filtra por source — startup, resume, clear, compact.

Qué puedes hacer: El stdout se agrega como contexto para Claude. No puede bloquear.

Tipos soportados: Solo command.

Dato especial: Tiene acceso a $CLAUDE_ENV_FILE para persistir variables de entorno para toda la sesión.

Campos de output nuevos (v2.1.152): además del additionalContext de siempre, SessionStart ahora acepta varios campos en su JSON de salida:

  • reloadSkills: true — Vuelve a escanear los skills disponibles. Útil si tu hook acaba de instalar o generar skills nuevos.
  • sessionTitle — Pone un título a la sesión.
  • watchPaths — Lista de rutas a vigilar (alimenta eventos como FileChanged).
  • initialUserMessage — Inyecta un primer mensaje del usuario. Solo funciona en modo no interactivo (por ejemplo, con -p).

Ejemplo típico: Re-inyectar recordatorios después de compactar:

{
    "hooks": {
        "SessionStart": [{
          "matcher": "compact",
          "hooks": [{
               "type": "command",
               "command": "echo 'Recordatorio: usa Bun en lugar de npm.'"
          }]
        }]
    }
}

UserPromptSubmit

Cuándo: Tú envías un mensaje, antes de que Claude lo procese.

Matcher: No soporta matchers. Siempre se dispara.

Qué puedes hacer: Bloquear el prompt (exit 2 lo borra completamente) o agregar contexto.

Tipos soportados: command, http, prompt, agent.

Campos especiales: prompt contiene el texto que enviaste.

PreToolUse

Cuándo: Claude está a punto de usar una herramienta. Es tu última oportunidad para detenerlo.

Matcher: Filtra por tool_name — Bash, Edit, Write, Read, Glob, Grep, Agent, WebFetch, WebSearch, AskUserQuestion, ExitPlanMode, mcp__servidor__herramienta.

Qué puedes hacer:

  • permissionDecision: "allow" — Dar permiso automático (salta el diálogo de permisos). Ojo: esto NO sobrescribe reglas deny ni ask definidas en managed settings. Las reglas deny siempre ganan.
  • permissionDecision: "deny" — Bloquear la herramienta.
  • permissionDecision: "ask" — Mostrar el diálogo de permisos al usuario.
  • permissionDecision: "defer" — Solo en modo headless (-p). Preserva el tool call sin ejecutarlo para que un wrapper del SDK lo procese fuera.
  • updatedInput — Modificar los parámetros antes de ejecutar.
  • additionalContext — Agregar contexto para Claude.

Tipos soportados: command, http, mcp_tool, prompt, agent.

Soporta el campo if para filtrado granular tipo permission rule (ej: "if": "Bash(git *)").

Este es probablemente el evento más poderoso. Te permite proteger archivos, bloquear comandos peligrosos, o auto-aprobar acciones seguras.

PostToolUse y PostToolUseFailure

PostToolUse se dispara cuando una herramienta termina con éxito. PostToolUseFailure se dispara cuando falla.

Matcher: Filtra por tool_name.

Importante: La herramienta ya se ejecutó. No puedes deshacerla. Pero puedes:

  • Formatear código después de una edición.
  • Logear lo que pasó.
  • Agregar contexto sobre el resultado.

Campo nuevo continueOnBlock: true (v2.1.139): normalmente, cuando un PostToolUse devuelve decision: "block", Claude se frena con ese feedback. Con continueOnBlock: true, la razón del rechazo se le pasa a Claude pero el turno continúa en lugar de cortarse. Sirve para dejar una nota ("este patrón está deprecado, úsalo así") sin interrumpir el flujo de trabajo.

Tipos soportados: command, http, prompt, agent.

Campos especiales: tool_name, tool_input, tool_response (solo en PostToolUse), error (solo en PostToolUseFailure).

Stop y SubagentStop

Stop se dispara cuando el agente principal termina de responder. SubagentStop se dispara cuando un subagente termina.

Matcher: No soporta matchers.

Qué puedes hacer: Bloquear con decision: "block" para obligar a Claude a seguir trabajando.

Feedback sin marcar error (v2.1.152): Stop y SubagentStop ahora soportan hookSpecificOutput.additionalContext. Así puedes inyectarle un comentario a Claude y dejar que el turno siga su curso sin tratarlo como un bloqueo ni un error. Es más suave que decision: "block": no fuerza a Claude a seguir, solo le añade contexto.

Tope de bloqueos consecutivos (v2.1.143): si tu Stop hook bloquea una y otra vez, Claude Code corta por lo sano. Tras 8 bloqueos seguidos, el turno termina con un warning para evitar que te quedes atrapado. Puedes ajustar ese tope con la variable de entorno CLAUDE_CODE_STOP_HOOK_BLOCK_CAP (por defecto 8). Por ejemplo, CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=3 baja el límite a tres.

Muy importante

Siempre verifica stop_hook_active en el JSON input. Si es true, significa que Claude ya intentó parar una vez y el hook lo obligó a continuar. Haz exit 0 para dejarlo parar. Si no verificas esto, creas un loop infinito.

#!/bin/bash
INPUT=$(cat)
if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0   # Dejarlo parar
fi
# ... tu lógica aquí

Notification

Cuándo: Claude Code envía una notificación (pidiendo permisos, esperando tu atención, etc.).

Matcher: Filtra por notification_type — permission_prompt, idle_prompt, auth_success.

Qué puedes hacer: No puede bloquear. Solo para side effects como enviar una notificación al escritorio.

Tipos soportados: Solo command.

Setup

Cuándo: Claude Code se lanza con --init-only, o con --init / --maintenance en modo -p. Está pensado para preparación one-shot en CI o scripts.

Matcher: Filtra por trigger — init, maintenance.

Qué puedes hacer: Preparar el entorno antes de que la sesión arranque de verdad. No es bloqueable.

Tipos soportados: command (también acepta otros, pero con limitaciones: los servidores MCP pueden no estar conectados todavía).

UserPromptExpansion

Cuándo: Tú escribes un comando (slash command o un prompt MCP) y Claude Code lo expande a un prompt real, antes de que llegue al modelo.

Matcher: Filtra por command_name o por nombre de skill/comando.

Qué puedes hacer: Inyectar contexto al prompt expandido, o bloquear la expansión con exit 2.

Input especial: expansion_type (slash_command o mcp_prompt), command_name, command_args, command_source (builtin, user o plugin) y prompt (el texto resultante).

PostToolBatch

Cuándo: Claude lanzó varias tools en paralelo y todas terminaron. Dispara una sola vez por batch, antes de la siguiente llamada al modelo.

Matcher: No soporta matchers.

Input especial: batch_size y tool_calls (la lista completa con sus inputs y resultados).

Qué puedes hacer: Validar el conjunto de resultados como un todo. Soporta decision: "block" que se reporta a Claude antes de continuar. Ideal para verificaciones que solo tienen sentido después de varias tools (ej: "si editaste estos 3 archivos juntos, corre el linter una vez").

PermissionDenied

Cuándo: Una tool call es denegada por el clasificador de modo auto.

Matcher: Igual que PreToolUse: filtra por tool_name.

Qué puedes hacer: Decirle al modelo que puede reintentar:

{
    "hookSpecificOutput": {
        "hookEventName": "PermissionDenied",
        "retry": true
    }
}

Útil cuando tu lógica determina que la denegación fue un falso positivo y vale la pena reintentar con un ajuste.

StopFailure

Cuándo: El turno termina por un error de API (no porque Claude terminó bien).

Matcher: Filtra por tipo de error — rate_limit, overloaded, authentication_failed, oauth_org_not_allowed, billing_error, invalid_request, model_not_found, server_error, max_output_tokens, unknown.

Qué puedes hacer: Loggear errores, alertar a un canal de Slack, o cambiar a un modelo más barato la próxima vez. No es bloqueable (output y exit code se ignoran).

TaskCreated

Cuándo: Se crea una task (via TaskCreate).

Matcher: No soporta matchers.

Input especial: task_id, task_name, task_description.

Qué puedes hacer: Loggear, sincronizar con un tracker externo, o bloquear la creación con decision: "block".

CwdChanged

Cuándo: Cambia el working directory de Claude (por ejemplo cuando Claude hace cd en Bash).

Matcher: No soporta matchers.

Input especial: new_cwd, old_cwd. También recibe CLAUDE_ENV_FILE, así que puedes persistir variables nuevas en el entorno.

Caso de uso típico — direnv: el comando Bash de Claude no recoge cambios de direnv automáticamente. Con un hook CwdChanged que escriba direnv export bash >> "$CLAUDE_ENV_FILE", cada cambio de directorio recarga el entorno y los siguientes Bash heredan las variables correctas.

FileChanged

Cuándo: Un archivo vigilado cambia en disco (lo modificó Claude, el usuario o cualquier otro proceso).

Matcher: ¡Ojo! No es regex. El matcher se splittea por | como una lista literal de nombres. ".envrc|.env|config.toml" matchea esos tres archivos exactos, nada más.

Input especial: file_path. También recibe CLAUDE_ENV_FILE.

Qué puedes hacer: Recargar entorno cuando cambia un .envrc, invalidar caches, o avisar al equipo.

PostCompact

Cuándo: Justo después de que la compactación de contexto termina.

Matcher: Igual que PreCompact — manual o auto.

Qué puedes hacer: Loggear, o re-inyectar contexto que el resumen perdió. Por ejemplo, recordatorios de stack, convenciones del proyecto, o el sprint actual.

Elicitation y ElicitationResult

Cuando un servidor MCP necesita pedirle algo al usuario durante una tool call (por ejemplo "confirma este pago"), dispara una elicitation.

Elicitation dispara antes de mostrarle el diálogo al usuario. Puedes auto-responder con:

{
    "hookSpecificOutput": {
        "hookEventName": "Elicitation",
        "action": "accept",
        "content": { ... }
    }
}

Los valores válidos para action son accept, decline o cancel.

ElicitationResult dispara después de que el usuario responde, antes de enviar la respuesta al servidor. Útil para auditar o modificar respuestas.

Matcher: En ambos, el nombre del servidor MCP.

MessageDisplay

Cuándo: Mientras el texto de la respuesta de Claude se muestra y se va escribiendo en pantalla (streaming). Es un evento nuevo (v2.1.152, mayo 2026).

Matcher: No soporta matchers.

Qué puedes hacer: Transformar u ocultar el texto que ve el usuario. Lo logras con hookSpecificOutput.displayContent, que reemplaza el texto solo en pantalla. Ojo con esto: no toca el contexto real de la conversación. Claude sigue "viendo" el texto original; solo cambia lo que aparece en tu terminal.

{
    "hookSpecificOutput": {
        "hookEventName": "MessageDisplay",
        "displayContent": "[texto censurado]"
    }
}

Caso de uso típico: redactar u ocultar secretos en la salida visible. Si Claude imprime sin querer un token o una contraseña, un hook MessageDisplay puede taparlo en pantalla mientras el contexto interno queda intacto.

Otros eventos

Estos eventos son menos comunes pero igualmente útiles:

  • PermissionRequest — Se dispara cuando aparece el diálogo de permisos. Puedes auto-aprobar o denegar. El output usa el formato hookSpecificOutput.decision.{behavior: "allow"|"deny"} (más explícito que permissionDecision directo). Soporta updatedInput, permissionRule y updatedPermissions (array con entradas tipo setMode para cambiar el modo de permisos en caliente). No funciona en modo -p (no interactivo). Usa PreToolUse en su lugar.
  • SubagentStart — Un subagente se crea. Puedes inyectar instrucciones extra. Solo command.
  • TeammateIdle — Un teammate va a dejar de trabajar. Exit 2 lo obliga a seguir. Solo command.
  • TaskCompleted — Una tarea va a marcarse como completada. Exit 2 lo impide. Todos los tipos.
  • ConfigChange — Un archivo de configuración cambió. Puedes bloquear el cambio (excepto policy settings). Solo command.
  • InstructionsLoaded — Un archivo CLAUDE.md se cargó. Para audit y logging. Sí soporta matchers (session_start, nested_traversal, path_glob_match, include, compact). Solo command.
  • SessionEnd — La sesión termina. Timeout de solo 1.5 segundos. Solo command.
  • WorktreeCreate / WorktreeRemove — Crear o eliminar un worktree. Permite usar SVN u otros VCS en vez de git. Solo command.

Los cinco tipos de hooks en detalle

Ya vimos que hay cinco tipos. Ahora vamos a profundizar en cómo funciona cada uno.

Command hooks

El tipo más común. Ejecuta un comando de terminal.

{
    "type": "command",
    "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write",
    "timeout": 600,
    "async": false
}

Campos disponibles:

  • command (obligatorio) — El comando shell a ejecutar.
  • args (opcional) — Si la pones, cambia a exec form.
  • shell (opcional) — Shell a usar en shell form. En Unix por defecto bash. En Windows por defecto Git Bash, pero puedes elegir powershell.
  • timeout (opcional) — Segundos antes de cancelar. Por defecto: 600 (10 minutos). En UserPromptSubmit baja a 30 segundos.
  • async (opcional) — Si es true, se ejecuta en background sin bloquear a Claude.
  • asyncRewake (opcional) — Como async, pero exit 2 "despierta" a Claude con stderr como system reminder.
  • statusMessage (opcional) — Texto que aparece en el spinner mientras el hook corre.

El hook recibe datos JSON por stdin. Para leerlos, usa jq o lee stdin en tu script.

Exec form vs shell form:

  • Shell form (solo command, sin args) — el comando se interpreta por el shell. Pipes (|), &&, globs y expansión de variables funcionan. Es la forma cómoda para comandos cortos.
  • Exec form (command + args) — se llama al binario directamente, sin shell de por medio. No hay pipes, no hay &&, no hay globs. Más seguro y rápido. Requerido para archivos .cmd o .bat en Windows.
{
    "type": "command",
    "command": "node",
    "args": ["${CLAUDE_PLUGIN_ROOT}/check.js", "--fix"]
}

HTTP hooks

Envían un POST a una URL con los datos del evento como body.

{
    "type": "http",
    "url": "http://localhost:8080/hooks/tool-use",
    "headers": {
      "Authorization": "Bearer $MY_TOKEN"
    },
    "allowedEnvVars": ["MY_TOKEN"]
}

Campos disponibles:

  • url (obligatorio) — URL del endpoint.
  • headers (opcional) — Headers HTTP. Soportan variables de entorno con $VAR o ${VAR}.
  • allowedEnvVars (opcional) — Lista de variables permitidas. Las no listadas se reemplazan con strings vacíos.

Nota

HTTP hooks solo se pueden configurar editando el JSON. El menú /hooks no los soporta.

La respuesta del servidor usa el mismo formato que command hooks. Respuesta 2xx con JSON se procesa igual. Errores de conexión o non-2xx son errores no bloqueantes.

MCP tool hooks

Invocan una tool de un servidor MCP que ya está conectado. Útiles cuando lo que quieres chequear ya existe como tool MCP (por ejemplo un escáner de seguridad expuesto por un servidor interno).

{
    "type": "mcp_tool",
    "server": "security_scanner",
    "tool": "scan_file",
    "input": {
        "file_path": "${tool_input.file_path}"
    }
}

Campos disponibles:

  • server (obligatorio) — Nombre del servidor MCP conectado.
  • tool (obligatorio) — Nombre de la tool a invocar.
  • input (opcional) — Inputs para la tool. Soporta interpolación con ${tool_input.campo} para pasar datos del evento original.
  • timeout (opcional) — 600 segundos por defecto.

Ojo con el orden: el servidor MCP tiene que estar conectado cuando dispara el hook. Si lo usas en SessionStart o Setup, puede dispararse antes de la conexión y fallar. Para eventos seguros: PreToolUse, PostToolUse, UserPromptSubmit y los que disparan en medio de la sesión.

Prompt hooks

Le preguntan a un modelo de IA si algo está bien. Es como tener un revisor automático.

{
    "type": "prompt",
    "prompt": "Analiza si Claude debería parar. Contexto: $ARGUMENTS. Responde {\"ok\": true} o {\"ok\": false, \"reason\": \"...\"}",
    "model": "haiku",
    "timeout": 30
}

El modelo (Haiku por defecto) lee el prompt y responde con JSON:

  • {"ok": true} — Permite la acción.
  • {"ok": false, "reason": "..."} — Bloquea la acción.

Usa $ARGUMENTS en el prompt para inyectar los datos del evento. Si no lo incluyes, se agregan al final automáticamente.

Campo model: por defecto el hook usa Haiku (rápido y barato). Si tu chequeo necesita más cabeza, puedes pedir Opus u otro modelo concreto: "model": "claude-opus-4-1-20250805". Solo aplica a hooks de tipo prompt.

Agent hooks

El tipo más poderoso. Lanza un mini-agente que puede leer archivos, buscar código y verificar cosas.

{
    "type": "agent",
    "prompt": "Verifica que todos los tests unitarios pasen. $ARGUMENTS",
    "timeout": 120
}

El agente tiene acceso a herramientas: Read, Grep, Glob. Puede hacer hasta 50 turnos de herramientas. Responde con el mismo formato que prompt hooks: {"ok": true/false}.

Timeout por defecto: 60 segundos. Usa agent hooks cuando la verificación requiere inspeccionar archivos reales.

El campo if: filtros condicionales finos

El matcher filtra por nombre de herramienta. Pero a veces necesitas filtrar más fino: "solo cuando el Bash es un git push", o "solo cuando el Edit toca un .ts".

Para eso existe el campo if. Usa la misma sintaxis que las reglas de permisos del capítulo de permisos: Tool(patrón).

{
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "if": "Bash(git *)",
                        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-git-policy.sh"
                    }
                ]
            }
        ]
    }
}

El proceso del hook solo se lanza cuando el tool call matchea la condición. Es más eficiente que filtrar dentro del script, porque te ahorras el spawn cuando no aplica.

Ejemplos típicos:

  • "if": "Bash(git *)" — solo cuando Claude corre algo que empiece por git.
  • "if": "Edit(*.ts)" — solo cuando edita un archivo TypeScript.
  • "if": "Write(src/**)" — solo cuando escribe dentro de src/.

Para comandos Bash compuestos (npm test && git push), evalúa cada subcomando.

Requisitos y limitaciones:

  • Necesitas Claude Code v2.1.85 o superior. Versiones anteriores lo ignoran y el hook corre siempre.
  • Solo funciona en eventos de tool: PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest y PermissionDenied. Ponerlo en otros eventos hace que el hook nunca corra.
  • Correcciones de versión: los patrones de ruta como Edit(src/**), Read(~/.ssh/**) y Read(.env) se corrigieron en v2.1.176; antes podían no coincidir bien. Los wildcards de PowerShell como PowerShell(git push*) se arreglaron en v2.1.147 (antes solo coincidía PowerShell(*)). Si usas estos patrones, asegúrate de estar en una versión reciente.

Hooks asíncronos: no bloquear a Claude

Por defecto, los hooks bloquean a Claude. Él espera a que terminen antes de continuar. Si tu hook tarda 30 segundos, Claude espera 30 segundos.

Con async: true, el hook se ejecuta en el fondo. Claude sigue trabajando sin esperar.

{
    "type": "command",
    "command": "npm test",
    "async": true,
    "timeout": 300
}

Limitaciones de hooks async:

  • Solo funciona con type: "command". Prompt y agent no pueden ser async.
  • No pueden bloquear herramientas ni retornar decisiones. La acción ya procedió.
  • Los resultados llegan en el siguiente turno de conversación.
  • Cada ejecución crea un proceso separado. No hay deduplicación.

Usa hooks async para tareas largas como correr tests o hacer builds.

asyncRewake: lo mejor de los dos mundos. Si pones "asyncRewake": true, el hook corre en background como un async normal. Pero si eventualmente sale con exit 2, "despierta" a Claude: el stderr aparece como un system reminder en el siguiente turno. Es la forma de reaccionar a fallos en background (un CI que se cayó, un test que falló) sin bloquear el flujo actual.

{
    "type": "command",
    "command": "./background-ci-check.sh",
    "asyncRewake": true
}

Variables de entorno especiales

Claude Code define variables útiles que puedes usar en tus hooks:

  • $CLAUDE_PROJECT_DIR — La raíz de tu proyecto. Siempre úsala entre comillas: "$CLAUDE_PROJECT_DIR".
  • $CLAUDE_ENV_FILE — Disponible en SessionStart, Setup, CwdChanged y FileChanged. Escribe aquí variables que quieres persistir para toda la sesión (formato export VAR=value).
  • ${CLAUDE_PLUGIN_ROOT} — Directorio raíz del plugin actual. Para scripts empaquetados con un plugin.
  • ${CLAUDE_PLUGIN_DATA} — Directorio persistente donde tu plugin puede guardar datos entre sesiones (logs, caches, estado). Disponible en hooks declarados por un plugin.
  • $CLAUDE_EFFORT — Nivel de esfuerzo del turno actual. Disponible solo en eventos de tool-use. Sus valores posibles son low, medium, high, xhigh y max. Útil para ajustar el comportamiento del hook según si Claude está en "modo rápido" o "modo a fondo".
  • $CLAUDE_CODE_SESSION_ID — ID de la sesión actual. Desde v2.1.163, cuando reanudas con --resume, los servidores MCP de tipo stdio reciben este mismo ID que tus hooks y comandos Bash. Así puedes correlacionar lo que hace el hook con lo que hace el servidor MCP en la misma sesión.
  • $CLAUDE_CODE_REMOTE — Vale true en entornos web remotos.

Para el timeout de SessionEnd (que por defecto es muy corto, 1.5 segundos), puedes usar:

CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS=5000 claude

Persistir variables con CLAUDE_ENV_FILE

Este es un truco muy útil. En un hook de SessionStart, puedes escribir variables de entorno que estarán disponibles para todos los comandos Bash de la sesión:

#!/bin/bash
if [ -n "$CLAUDE_ENV_FILE" ]; then
   echo 'export NODE_ENV=production' >> "$CLAUDE_ENV_FILE"
   echo 'export DEBUG_LOG=true' >> "$CLAUDE_ENV_FILE"
fi
exit 0

Es como preparar el terreno al inicio del día. Todas las herramientas que Claude use después tendrán esas variables disponibles.

Seguridad: lo que debes saber

Los command hooks se ejecutan con todos tus permisos de usuario. Pueden leer, modificar o borrar cualquier archivo que tú puedas acceder. Esto es poderoso pero peligroso.

Buenas prácticas de seguridad

  • Siempre pon las variables entre comillas — Escribe "$VAR", no $VAR. Sin comillas, un path con espacios puede romper tu script.
  • Valida los inputs — No confíes ciegamente en el JSON que recibes. Verifica paths y valores.
  • Bloquea path traversal — Si un path contiene .., podría salirse de tu proyecto. Verifícalo.
  • Usa paths absolutos — Con $CLAUDE_PROJECT_DIR en lugar de paths relativos.
  • Evita archivos sensibles — No dejes que hooks lean .env, .git/ o archivos de claves.

El sistema de snapshot

Claude Code toma una foto de tus hooks al inicio de la sesión. Usa esa foto durante toda la sesión.

Si alguien (o algo) modifica los hooks mientras trabajas, Claude Code te avisa. Los cambios no aplican hasta que los revises en el menú /hooks.

Esto previene que código malicioso modifique tus hooks y tome control mid-sesión.

Los hooks que agregas directamente desde /hooks sí toman efecto inmediatamente.

Deshabilitar todos los hooks

Para deshabilitar todos los hooks sin borrarlos:

  • Abre /hooks y usa el toggle al final del menú.
  • O agrega "disableAllHooks": true en tu settings.

Ojo: Si un admin configuró hooks vía managed policy, tu disableAllHooks no los afecta. Solo disableAllHooks a nivel managed puede deshabilitar managed hooks.

Para entornos enterprise estrictos, managed policy tiene dos settings adicionales:

  • "allowManagedHooksOnly": true — Bloquea todos los hooks de usuario, proyecto y plugin. Solo corren los hooks definidos en managed policy. Útil cuando seguridad necesita garantizar que solo los hooks auditados de la organización están activos.
  • "enabledPlugins": { "mi-plugin": true } — Lista blanca de plugins exentos del bloqueo. Aunque allowManagedHooksOnly esté activo, los plugins listados aquí sí pueden registrar sus hooks. Sirve para vetar plugins uno por uno tras una auditoría.

Hooks en Skills y Agents

Puedes definir hooks directamente en skills y subagentes usando frontmatter YAML al inicio del archivo:

---
name: secure-operations
description: Operaciones con verificación de seguridad
hooks:
   PreToolUse:
      - matcher: "Bash"
        hooks:
           - type: command
             command: "./scripts/security-check.sh"
---

Estos hooks tienen vida limitada. Solo funcionan mientras el skill o agente está activo. Cuando termina, se limpian solos.

Para subagentes, los hooks Stop se convierten automáticamente a SubagentStop.

El campo once: true hace que el hook se ejecute una sola vez y se remueva. Solo funciona en skills.

Deduplicación y combinación de varios hooks

Como hay seis lugares donde puedes guardar hooks (user, project, local, managed, plugin, frontmatter de skill/agent), es muy fácil terminar con el mismo hook registrado dos veces. Claude Code maneja esto solo.

Deduplicación automática

Los handlers idénticos se deduplican automáticamente:

  • Command hooks — se deduplican por command + args. Si el mismo comando exacto está en tus settings de usuario y en los del proyecto, solo corre una vez.
  • HTTP hooks — se deduplican por url. Si dos archivos definen el mismo endpoint, se llama una sola vez.

Esto evita que prettier corra cuatro veces sobre el mismo archivo porque tres compañeros y tú lo configuraron por separado.

Cuando varios hooks distintos matchean el mismo evento

Si tienes varios hooks distintos conectados al mismo evento, todos se ejecutan en paralelo y todos llegan a completar antes de mezclar resultados. Un hook que dice "deny" no detiene los side effects de sus hermanos (los logs ya se escribieron, las notificaciones ya se enviaron).

Cuando hay que combinar decisiones:

  • PreToolUse — gana la decisión más restrictiva. deny > ask > allow. Si un hook dice allow y otro deny, la herramienta se bloquea.
  • additionalContext — todos los fragmentos se concatenan y se pasan juntos a Claude. No tienes que preocuparte por elegir uno.
  • decision: "block" en eventos como Stop, PostToolUse o ConfigChange — basta con que un hook diga block para que tenga efecto.

Esto es muy útil para componer: un hook escribe un log, otro hace un chequeo de seguridad, otro envía a Slack. Cada uno hace su parte sin coordinarse con los demás.

Debugging: cuando tu hook no funciona

Los hooks pueden fallar silenciosamente. Aquí tienes las herramientas para encontrar el problema.

Herramientas de debugging

  • Modo verbose (Ctrl+O) — Muestra el output de hooks en el transcript. Es lo primero que debes activar.
  • Flag --debug — Ejecuta claude --debug para ver detalles completos: qué hooks coincidieron, exit codes, output.
  • Prueba manual — Simula el hook desde la terminal:
echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./mi-hook.sh
echo $?

Si el exit code no es 0 y no es 2, tienes un error no bloqueante.

Errores comunes y soluciones

"Mi hook no se dispara"

  • El matcher es case-sensitive. "bash" no es lo mismo que "Bash".
  • Estás usando PermissionRequest en modo -p. Ese evento no se dispara en modo no interactivo. Usa PreToolUse.
  • Verifica con /hooks que el hook aparece bajo el evento correcto.

"Error en el transcript"

  • El script no es ejecutable. Corre chmod +x ./mi-hook.sh.
  • jq no está instalado. Instala jq en tu sistema.
  • El comando no se encuentra. Usa paths absolutos.

"/hooks muestra 'no hooks configured'"

  • Tu JSON tiene errores (trailing commas, comentarios). JSON puro no acepta eso, y un JSON inválido sí rompe todo el archivo.
  • El archivo está en la ubicación incorrecta.
  • Reinicia la sesión o abre /hooks para recargar.

Nota (mediados de 2026)

Antes, escribir mal el nombre de un evento (un typo como PreToolUze) hacía que se ignorara todo el archivo de settings. Eso ya no pasa: un nombre de evento no reconocido se descarta solo, sin tumbar el resto de tu configuración. Pero ojo, esto es solo para nombres de evento desconocidos; un JSON inválido (con comas finales o sintaxis rota) sí sigue rompiendo el archivo entero.

"Loop infinito con Stop hook"

  • Tu Stop hook no verifica stop_hook_active. Si no lo verificas, Claude nunca puede parar.

"JSON validation failed"

  • Tu shell profile (~/.zshrc o ~/.bashrc) tiene echo statements que se mezclan con el JSON del hook. Envuélvelos así:
if [[ $- == *i* ]]; then
   echo 'Shell ready'
fi

"Mi FileChanged con regex no matchea nada"

  • FileChanged no usa regex. Splittea el matcher por | como una lista literal de nombres. "^\.env.*" nunca matchea. Usa ".envrc|.env|.env.local" con nombres exactos. Para patrones más complejos, filtra dentro del script con un matcher vacío.

"Mi MCP tool hook dice que no encuentra el servidor"

  • El hook disparó antes de que el servidor MCP conectara. Pasa típicamente cuando lo pones en SessionStart o Setup. Mueve la lógica a un evento que dispare después de la conexión (UserPromptSubmit, PreToolUse) o usa type: command y verifica la conexión manualmente.

"PermissionRequest aprueba TODO"

  • Tu matcher está vacío o es .*. Con eso, el hook auto-aprueba cada permiso. Restringe el matcher a tools específicas (ExitPlanMode, un Bash concreto, etc.). Es la regla de oro: PermissionRequest nunca debe ir sin matcher.

"Mi hook escribe a /dev/tty pero no sale nada"

  • /dev/tty no está disponible para hooks. Si necesitas tocar el terminal (cambiar título, lanzar una notificación nativa), usa el campo terminalSequence en el JSON output con secuencias OSC permitidas.

"Mi additionalContext se ve truncado"

  • El output total (stdout + additionalContext + systemMessage) está capado a 10.000 caracteres. El exceso se escribe a un archivo y el modelo solo ve un preview con la ruta. Reduce el output o escribe tú mismo a un archivo y referencia la ruta.

"Mi if no filtra como espero"

  • Tu versión de Claude Code es anterior a 2.1.85 (lo ignora y el hook corre siempre), o pusiste if en un evento que no es de tool (PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest o PermissionDenied) — fuera de esos eventos el hook nunca corre.

Ejemplos Prácticos

Notificación en macOS cuando Claude necesita atención

{
    "hooks": {
        "Notification": [
            {
                "matcher": "",
                "hooks": [
                    {
                        "type": "command",
                        "command": "osascript -e 'display notification \"Claude Code necesita tu atención\" with title \"Claude Code\"'"
                    }
                ]
            }
        ]
    }
}

Agrega esto a ~/.claude/settings.json. Cada vez que Claude necesite tu atención, verás una notificación nativa de macOS. El matcher vacío significa que se dispara para todas las notificaciones.

Auto-formatear con Prettier después de cada edición

{
    "hooks": {
        "PostToolUse": [
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
                    }
                ]
            }
        ]
    }
}

Agrega esto a .claude/settings.json del proyecto. Después de cada Edit o Write, extrae el path del archivo con jq y lo pasa a Prettier para formatearlo. Así el código siempre queda limpio.

Proteger archivos sensibles con un script

#!/bin/bash
# .claude/hooks/protect-files.sh
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/")
for pattern in "${PROTECTED_PATTERNS[@]}"; do
 if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Bloqueado: $FILE_PATH coincide con patrón protegido '$pattern'" >&2
    exit 2
 fi
done
exit 0

Este script se guarda como .claude/hooks/protect-files.sh (no olvides chmod +x). Lee el JSON de stdin, extrae el file_path, y verifica si coincide con patrones protegidos. Si coincide, sale con exit 2 para bloquear la edición. Regístralo como hook PreToolUse con matcher Edit|Write.

Bloquear comandos destructivos (rm -rf)

#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q 'rm -rf'; then
   jq -n '{
        hookSpecificOutput: {
            hookEventName: "PreToolUse",
            permissionDecision: "deny",
            permissionDecisionReason: "Comando destructivo bloqueado"
        }
   }'
else
   exit 0
fi

PreToolUse hook para Bash que detecta comandos rm -rf y los bloquea usando JSON output con permissionDecision deny. Más elegante que exit 2 porque da una razón clara a Claude.

Correr tests en background después de ediciones

{
    "hooks": {
        "PostToolUse": [
            {
                "matcher": "Write|Edit",
                "hooks": [
                    {
                        "type": "command",
                        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/run-tests-async.sh",
                        "async": true,
                        "timeout": 300
                    }
                ]
            }
        ]
    }
}

Hook asíncrono que ejecuta tests en background mientras Claude sigue trabajando. Los resultados se entregan en el siguiente turno de conversación. El timeout de 300 segundos da suficiente tiempo para tests largos.

Prompt hook para verificar si Claude debe parar

{
    "hooks": {
        "Stop": [
            {
                "hooks": [
                    {
                        "type": "prompt",
                        "prompt": "Analiza si Claude debería parar. Contexto: $ARGUMENTS. Verifica si: 1) Todas las tareas están completas, 2) No hay errores pendientes. Responde con JSON: {\"ok\": true} para permitir parar, o {\"ok\": false, \"reason\": \"explicación\"} para continuar.",
                        "timeout": 30
                    }
                ]
            }
        ]
    }
}

Un modelo de IA (Haiku) evalúa si Claude debería dejar de trabajar. Si hay tareas pendientes, responde ok: false con una razón, y Claude continúa. Si todo está listo, responde ok: true y Claude para.

Filtrar con if: solo correr el hook para comandos git

{
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "if": "Bash(git *)",
                        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-git-policy.sh"
                    }
                ]
            }
        ]
    }
}

Con el campo if, el proceso del hook solo se lanza cuando el comando Bash empieza por git. Más eficiente que tener un script que se lanza para cada Bash y filtra adentro. Requiere Claude Code v2.1.85+.

Recargar direnv al cambiar de directorio (CwdChanged)

{
    "hooks": {
        "SessionStart": [
            {
                "hooks": [
                    {
                        "type": "command",
                        "command": "direnv export bash >> \"$CLAUDE_ENV_FILE\""
                    }
                ]
            }
        ],
        "CwdChanged": [
            {
                "hooks": [
                    {
                        "type": "command",
                        "command": "direnv export bash >> \"$CLAUDE_ENV_FILE\""
                    }
                ]
            }
        ]
    }
}

El comando Bash de Claude no recoge cambios de direnv automáticamente. Este combo arregla eso: SessionStart carga el entorno inicial y CwdChanged lo recarga cada vez que Claude hace cd. CLAUDE_ENV_FILE se ejecuta como preamble en cada Bash siguiente, así que las variables nuevas están disponibles.

Auto-aprobar ExitPlanMode sin diálogo

{
    "hooks": {
        "PermissionRequest": [
            {
                "matcher": "ExitPlanMode",
                "hooks": [
                    {
                        "type": "command",
                        "command": "echo '{\"hookSpecificOutput\": {\"hookEventName\": \"PermissionRequest\", \"decision\": {\"behavior\": \"allow\"}}}'"
                    }
                ]
            }
        ]
    }
}

Cuando Claude termina un plan, pide salir de plan mode. Este hook auto-aprueba SOLO para ExitPlanMode usando el nuevo formato hookSpecificOutput.decision.behavior. Mantén el matcher estrecho: con vacío o .* se auto-aprobaría TODO.

Logging a servicio externo con HTTP hook

{
    "hooks": {
        "PostToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "http",
                        "url": "https://audit.miempresa.com/claude-events",
                        "headers": {
                          "Authorization": "Bearer $AUDIT_TOKEN"
                        },
                        "allowedEnvVars": ["AUDIT_TOKEN"],
                        "timeout": 30,
                        "async": true
                    }
                ]
            }
        ]
    }
}

Envía cada Bash ejecutado a un servicio de auditoría externo. async: true hace que el POST no bloquee a Claude. allowedEnvVars permite interpolar el token sin filtrarlo al resto del entorno del hook. Errores de red son no bloqueantes.

Consejo

Empieza simple. Tu primer hook debería ser una notificación de escritorio (Notification). Es fácil de configurar y ves resultados inmediatos.

Consejo

Usa el menú /hooks para crear y probar hooks rápidamente. Cuando te sientas cómodo, edita el JSON directamente para hooks más avanzados.

Advertencia

Siempre verifica stop_hook_active en hooks de tipo Stop. Si no lo haces, creas un loop infinito donde Claude nunca puede dejar de trabajar.

Advertencia

Los command hooks tienen tus permisos completos. Un error en un hook puede borrar archivos. Prueba tus scripts manualmente antes de registrarlos.

Advertencia

PermissionRequest NO se dispara en modo no interactivo (-p). Si automatizas con --print, usa PreToolUse para controlar permisos.

Nota

Los hooks HTTP solo se configuran editando JSON directamente. El menú /hooks no los soporta.

Nota

El timeout de SessionEnd es de solo 1.5 segundos por defecto. Si tu hook de limpieza necesita más tiempo, ajústalo con CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS.

Consejo

Para debugging, usa Ctrl+O (modo verbose) para ver el output de hooks. Si necesitas más detalle, ejecuta claude --debug.

Resumen del Capítulo

Los hooks son acciones automáticas que se disparan en momentos específicos del ciclo de vida de Claude Code. Los configuras en archivos settings JSON con tres niveles: evento, matcher y handler. Hay cinco tipos de handlers (command, http, mcp_tool, prompt, agent), una familia amplia de eventos (SessionStart, Setup, UserPromptSubmit, PreToolUse, PostToolUse, PostToolBatch, PermissionRequest, PermissionDenied, Stop, StopFailure, TaskCreated, CwdChanged, FileChanged, PreCompact, PostCompact, Elicitation, MessageDisplay, y más), el campo if para filtrado granular por contenido del tool call, y tres exit codes clave (0 para éxito, 2 para bloquear, otros para errores no bloqueantes). Usa Ctrl+O y --debug para depurar problemas.
