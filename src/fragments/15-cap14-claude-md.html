CLAUDE.md y Memoria del Proyecto

Cómo darle instrucciones permanentes a Claude Code y cómo él aprende de ti

INTERMEDIO

Cada vez que abres Claude Code, él empieza desde cero. No recuerda nada de la sesión anterior. Eso suena terrible, pero tiene solución. Existen dos sistemas de memoria que le permiten recordar tus instrucciones y aprender de ti. En este capítulo vas a aprender a usar ambos para que Claude Code trabaje exactamente como tú quieres.

Los dos sistemas de memoria

Claude Code tiene dos formas de recordar cosas entre sesiones. Piensa en ellas como dos cuadernos diferentes:

  • CLAUDE.md — Un cuaderno que tú escribes. Ahí pones instrucciones, reglas y contexto del proyecto. Es como dejarle una nota al empleado nuevo con las reglas de la oficina.
  • Auto memory (MEMORY.md) — Un cuaderno que Claude escribe solo. Cuando descubre algo importante mientras trabaja, lo anota ahí. Es como el cuaderno personal donde el empleado nuevo apunta trucos que va descubriendo.

Ambos se cargan al inicio de cada sesión. Claude los lee antes de hacer cualquier otra cosa.

La diferencia clave

CLAUDE.md contiene instrucciones y reglas. Tú decides qué va ahí. Auto memory contiene aprendizajes y patrones. Claude decide qué va ahí.

Dato importante

Estos archivos son contexto, no configuración forzada. Claude los lee e intenta seguirlos. Pero si escribes instrucciones vagas o contradictorias, puede que no las cumpla al 100%.

La buena noticia: instrucciones claras y específicas se cumplen en un ~92% de los casos. Las vagas bajan a ~73%. Así que la clave es ser directo y preciso.

Importante

Como CLAUDE.md es solo contexto que guía a Claude, no sirve para bloquear una acción de verdad. Si necesitas que algo nunca ocurra pase lo que pase (por ejemplo, impedir un git push a main), usa un hook PreToolUse o managed settings (permissions.deny), no una regla en CLAUDE.md.

Nota técnica

El contenido de CLAUDE.md se inyecta como un mensaje de usuario después del system prompt, no como parte del system prompt mismo. Esto significa que Claude lo trata como instrucciones importantes, pero no tienen el mismo peso que el system prompt. Si necesitas instrucciones a nivel de system prompt (por ejemplo, en scripts de automatización), usa el flag --append-system-prompt. Este flag agrega texto directamente al system prompt, lo que le da más peso. Debe pasarse en cada invocación, así que es más práctico para scripts que para uso interactivo.

CLAUDE.md: tus instrucciones permanentes

Un archivo CLAUDE.md es un documento de texto plano en formato Markdown. Ahí escribes las reglas que Claude debe seguir en tu proyecto.

Imagina que contratas a un asistente temporal cada día. Cada mañana le dejas una hoja con las reglas del proyecto. Eso es exactamente lo que hace CLAUDE.md.

Qué poner en un CLAUDE.md

Un buen CLAUDE.md incluye:

  • Comandos de build y test — cómo compilar, ejecutar tests y hacer linting.
  • Estándares de código — indentación, convenciones de nombres, lenguajes preferidos.
  • Arquitectura — dónde viven las cosas en el proyecto.
  • Decisiones importantes — por qué usamos X en vez de Y.

Aquí tienes un ejemplo real:

# Mi Proyecto

## Comandos de Build
- `npm run build` para compilar
- `npm test` para ejecutar tests
- `npm run lint` para linting

## Estandares de Codigo
- Usar 2 espacios de indentacion
- Componentes React con TypeScript
- Tests unitarios para toda logica de negocio

## Arquitectura
- API handlers en src/api/handlers/
- Componentes React en src/components/
- Utilidades compartidas en src/utils/

Cómo escribir instrucciones efectivas

No todas las instrucciones funcionan igual de bien. Hay trucos para que Claude las siga con más precisión:

  • Usa bullets — las listas con viñetas tienen un 35% más de cumplimiento que párrafos largos.
  • Sé imperativo — escribe "Usa 2 espacios de indentación" en vez de "El proyecto usa 2 espacios". Los imperativos tienen un 25% más de precisión.
  • Sé específico — "Usa Node 20" es mejor que "usa una versión reciente de Node".
  • Incluye ejemplos de código — un snippet vale más que mil palabras.
  • Mantén el archivo corto — menos de 200 líneas. Los archivos más largos pierden efectividad drásticamente (~71% de cumplimiento vs ~92% para archivos cortos).

Evita estos errores comunes:

  • No dupliques reglas entre diferentes archivos CLAUDE.md.
  • No pongas detalles de implementación (eso pertenece al código).
  • No escribas solo prohibiciones ("no hagas X") sin dar alternativas.

Generar un CLAUDE.md automáticamente con /init

No tienes que empezar desde cero. El comando /init analiza tu proyecto y genera un CLAUDE.md inicial.

Simplemente abre Claude Code en tu proyecto y escribe /init. Claude mirará tu código, descubrirá los comandos de build, las convenciones y la estructura. Luego creará un archivo CLAUDE.md con todo eso.

Si ya tienes un CLAUDE.md, /init sugiere mejoras en vez de sobreescribirlo. Es un buen punto de partida. Después puedes refinarlo con instrucciones que Claude no descubriría por su cuenta.

Además del código, /init también lee archivos de configuración de otros agentes si existen en tu repositorio:

  • AGENTS.md — el formato común para agentes de código.
  • .cursorrules — reglas de Cursor.
  • .windsurfrules — reglas de Windsurf.
  • .devin/rules/ — reglas de Devin.

Si encuentra alguno, incorpora las partes relevantes al CLAUDE.md generado. Esto es útil cuando migras desde otro agente y no quieres reescribir todas tus convenciones a mano.

Existe una variante interactiva más completa. Si estableces la variable de entorno CLAUDE_CODE_NEW_INIT=1 antes de ejecutar /init, se habilita un flujo de múltiples fases:

  1. Claude te pregunta qué artefactos quieres configurar: archivos CLAUDE.md, skills, hooks.
  2. Explora el codebase con un subagente para entender la estructura.
  3. Te hace preguntas de seguimiento para llenar vacíos.
  4. Te presenta una propuesta revisable antes de escribir nada.

Este flujo es ideal para proyectos grandes donde quieres un CLAUDE.md más completo desde el inicio.

Dónde poner los archivos CLAUDE.md

CLAUDE.md puede vivir en varios lugares. Cada ubicación tiene un alcance diferente. Piensa en esto como las reglas de una empresa:

  • La empresa tiene reglas generales (nivel organización).
  • Cada persona tiene sus preferencias (nivel usuario).
  • Cada proyecto tiene sus convenciones (nivel proyecto).
  • Cada persona tiene sus notas personales por proyecto (nivel local).
  • Cada módulo puede tener reglas especiales (nivel subdirectorio).

Las reglas más específicas ganan sobre las más generales. Si la empresa dice "usa tabs" pero el proyecto dice "usa espacios", gana el proyecto.

Nivel 1: Managed policy (organización)

Es el nivel más amplio. Lo gestiona el equipo de IT o DevOps de tu empresa. Aplica a todos los usuarios de la organización.

Ubicaciones según sistema operativo:

  • macOS — /Library/Application Support/ClaudeCode/CLAUDE.md
  • Linux / WSL — /etc/claude-code/CLAUDE.md
  • Windows — C:\Program Files\ClaudeCode\CLAUDE.md

Dato clave

Este archivo nunca puede ser excluido. Ni siquiera con claudeMdExcludes. Es la ley de la empresa, nadie la puede saltarse.

Se despliega con herramientas de gestión como MDM, Group Policy, Ansible o similares.

Alternativa para IT/DevOps: en vez de desplegar un archivo CLAUDE.md físico, puedes incrustar su contenido directamente dentro del managed-settings.json usando el setting claudeMd:

{
    "claudeMd": "Always run `make lint` before committing.\nNever push directly to main."
}

Carga con la misma prioridad que un CLAUDE.md gestionado en disco: aplica antes que las instrucciones de usuario y proyecto.

Importante

Este setting solo se honra en managed/policy settings. Si lo pones en settings de usuario, de proyecto o local, se ignora.

Nivel 2: Usuario (personal)

Tus preferencias personales. Aplican a todos los proyectos en tu máquina.

Ubicación: ~/.claude/CLAUDE.md

Aquí pondrías cosas como tu estilo de código favorito o atajos de herramientas que usas siempre. Este archivo no se versiona en git porque es solo tuyo.

Nivel 3: Proyecto (equipo)

Instrucciones compartidas con tu equipo. Se guardan en control de versiones.

Tienes dos opciones de ubicación:

  • ./CLAUDE.md — en la raíz del proyecto.
  • ./.claude/CLAUDE.md — dentro del directorio .claude.

Ambas funcionan igual. Elige la que prefieras. Aquí van los comandos de build, estándares de código y decisiones de arquitectura del proyecto.

Nivel 3.5: Local (personal por proyecto)

A veces necesitas instrucciones que son solo tuyas pero específicas de un proyecto. Por ejemplo, tus URLs de sandbox, datos de prueba que prefieres, o configuraciones personales que no quieres imponer al equipo.

Para eso existe CLAUDE.local.md. Se crea en la raíz del proyecto, junto a CLAUDE.md.

Diferencias clave con CLAUDE.md:

  • Debe ir en .gitignore. Es personal, no se comparte con el equipo.
  • Se carga después de CLAUDE.md en cada nivel de directorio. Eso significa que cuando hay conflicto, las instrucciones de CLAUDE.local.md ganan porque son lo último que Claude lee en ese nivel.
  • Si ejecutas /init y eliges la opción personal, se agrega automáticamente a .gitignore.

Dato sobre worktrees: un CLAUDE.local.md que está en .gitignore solo existe en el worktree donde lo creaste. Si trabajas con múltiples worktrees y quieres compartir instrucciones personales entre ellos, la solución es importar un archivo desde tu home:

# En CLAUDE.local.md de cada worktree:
@~/.claude/my-project-instructions.md

Así mantienes un solo archivo de instrucciones personales y lo importas desde cualquier worktree.

Nivel 4: Subdirectorio (módulo)

Instrucciones específicas para partes del proyecto. Por ejemplo, src/api/CLAUDE.md con reglas solo para la API.

Diferencia importante: estos archivos no se cargan al inicio. Se cargan bajo demanda, solo cuando Claude lee archivos en ese subdirectorio. Es como un manual que solo se abre cuando trabajas en esa área.

Reglas modulares con .claude/rules/

Si tu CLAUDE.md se está haciendo muy largo, puedes dividir las instrucciones en archivos separados. Para eso existe el directorio .claude/rules/.

Imagina que en vez de un manual gigante, tienes carpetas separadas: una para testing, otra para seguridad, otra para estilo de código. Eso es .claude/rules/.

Una distinción importante: las rules (reglas en .claude/rules/) se cargan en el contexto automáticamente cada sesión (o cuando se abren archivos coincidentes si tienen frontmatter paths). Los skills (en .claude/skills/) son diferentes: solo se cargan cuando los invocas explícitamente o cuando Claude determina que son relevantes para tu prompt. Esto ahorra contexto porque los skills no ocupan espacio hasta que se necesitan.

Estructura básica

Crea archivos .md dentro de .claude/rules/. Cada archivo cubre un tema:

tu-proyecto/
├── .claude/
│     ├── CLAUDE.md                # Instrucciones principales
│     └── rules/
│           ├── code-style.md      # Estilo de codigo
│           ├── testing.md         # Convenciones de testing
│           └── security.md        # Requisitos de seguridad

Claude descubre estos archivos de forma recursiva. Puedes crear subdirectorios como rules/frontend/ y rules/backend/ para organizar mejor.

Los archivos sin frontmatter (texto especial al inicio) se cargan al arrancar, igual que el CLAUDE.md principal.

Reglas que solo aplican a ciertos archivos

Puedes crear reglas que solo se activan cuando Claude trabaja con archivos específicos. Para eso usas un frontmatter al inicio del archivo de regla.

El frontmatter es un bloque de texto entre tres guiones (---) que va al principio del archivo. Ahí defines patrones de archivos:

---
paths:
  - "src/api/**/*.ts"
---

# Reglas para la API

- Todos los endpoints deben validar su entrada
- Usar el formato estandar de error
- Incluir comentarios de documentacion OpenAPI

Esta regla solo se activa cuando Claude lee un archivo TypeScript dentro de src/api/. No se carga al inicio ni se activa al escribir archivos.

Patrones glob comunes:

  • **/*.ts — todos los TypeScript en cualquier carpeta.
  • src/**/* — todo bajo src/.
  • *.md — archivos Markdown solo en la raíz.
  • src/**/*.{ts,tsx} — TypeScript y TSX bajo src/.

Reglas personales

También puedes tener reglas personales en ~/.claude/rules/*.md. Aplican a todos tus proyectos.

Estas reglas se cargan antes que las del proyecto. Eso significa que si hay conflicto, las reglas del proyecto ganan. Las del proyecto tienen más prioridad.

Compartir reglas entre proyectos con symlinks

Si tienes reglas que aplican a varios proyectos, puedes usar symlinks (enlaces simbólicos). Un symlink es como un atajo que apunta a otro archivo.

# Enlazar un directorio completo de reglas
ln -s ~/shared-claude-rules .claude/rules/shared

# Enlazar un archivo individual
ln -s ~/company-standards/security.md .claude/rules/security.md

Los symlinks se resuelven normalmente. Claude los lee como si fueran archivos normales. Si hay symlinks circulares (A apunta a B que apunta a A), Claude los detecta y los ignora.

Importar archivos con @

Tu CLAUDE.md puede importar otros archivos usando la sintaxis @ruta/al/archivo. Es como poner un enlace que se expande automáticamente.

See @README for project overview and @package.json for available npm
commands.

# Instrucciones adicionales
- Flujo de git: @docs/git-instructions.md

# Preferencias personales
- @~/.claude/my-project-instructions.md

Los archivos importados se cargan junto con el CLAUDE.md que los referencia. Las rutas relativas se resuelven desde la ubicación del archivo que contiene el import, no desde tu directorio actual.

Límites de los imports

Los imports tienen algunas restricciones:

  • Profundidad máxima de 4 niveles. Es decir, A importa B, B importa C... hasta 4 saltos.
  • La primera vez que Claude encuentra imports externos en un proyecto, te pide permiso. Aparece un diálogo mostrando los archivos.
  • Si rechazas el diálogo, los imports quedan deshabilitados para ese proyecto. No hay forma fácil de reactivarlos después.

Compatibilidad con AGENTS.md

Algunos equipos usan un archivo AGENTS.md para dar instrucciones a agentes de código (como Copilot o Cursor). Claude Code no lee AGENTS.md. Solo lee CLAUDE.md.

Si tu repositorio ya tiene un AGENTS.md y quieres que Claude también siga esas instrucciones, la solución es simple: crea un CLAUDE.md que lo importe.

@AGENTS.md

## Instrucciones especificas de Claude Code

- Usar plan mode para cambios bajo src/billing/
- Ejecutar tests antes de cada commit

Claude carga el contenido de AGENTS.md al inicio de la sesión y luego agrega las instrucciones específicas que pongas debajo.

Alternativa más simple: si no necesitas ninguna instrucción específica de Claude debajo, puedes usar un symlink en vez de un import:

ln -s AGENTS.md CLAUDE.md

Funciona en Mac y Linux sin más. En Windows requiere privilegios de Administrador o tener activado Developer Mode, así que el import @AGENTS.md sigue siendo más portable entre sistemas operativos.

Cómo se cargan los CLAUDE.md

Claude Code busca archivos CLAUDE.md caminando hacia arriba desde tu directorio actual. Si ejecutas Claude en foo/bar/, carga:

  1. foo/bar/CLAUDE.md (y foo/bar/CLAUDE.local.md si existe)
  2. foo/CLAUDE.md (y foo/CLAUDE.local.md si existe)

Los CLAUDE.md en subdirectorios debajo de tu directorio actual se cargan bajo demanda (cuando Claude lee archivos en esas carpetas).

Dato útil

Los comentarios HTML de bloque (<!-- tu nota aquí -->) se eliminan automáticamente antes de inyectar el contenido en el contexto de Claude. Los que están dentro de bloques de código se preservan. Esto es práctico para dejar notas de mantenimiento en tu CLAUDE.md sin consumir tokens del contexto.

Cargar CLAUDE.md de directorios adicionales

El flag --add-dir da acceso a directorios extra. Pero por defecto, los CLAUDE.md de esos directorios no se cargan.

Para cargarlos, usa esta variable de entorno:

CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../shared-config

Esto carga CLAUDE.md, .claude/CLAUDE.md y .claude/rules/*.md del directorio adicional.

Excluir CLAUDE.md que no necesitas

En proyectos grandes (como monorepos), puede haber CLAUDE.md de otros equipos que interfieren con tu trabajo. Puedes excluirlos con el setting claudeMdExcludes.

Ponlo en .claude/settings.local.json para que sea local a tu máquina:

{
    "claudeMdExcludes": [
        "**/monorepo/CLAUDE.md",
        "/home/user/monorepo/other-team/.claude/rules/**"
    ]
}

Los patrones se comparan contra rutas absolutas de archivo. Los arrays se fusionan entre las diferentes capas de settings.

Recuerda: el CLAUDE.md de managed policy nunca puede ser excluido.

CLAUDE.md sobrevive a /compact

Si usas el comando /compact para resumir la conversación, no te preocupes. El CLAUDE.md de la raíz del proyecto sobrevive: Claude lo re-lee desde disco y lo vuelve a cargar fresco, sin importar lo que haya pasado en la conversación.

Matiz importante para proyectos con CLAUDE.md anidados en subdirectorios: esos archivos no se re-inyectan automáticamente tras un /compact. Se vuelven a cargar de forma on-demand, la siguiente vez que Claude lea un archivo dentro de ese subdirectorio. Si llevas un rato sin tocar esa parte del código, sus instrucciones específicas no van a estar activas hasta que vuelvas a entrar ahí.

Si una instrucción desapareció después de compactar, es porque la diste solo en la conversación. No estaba en CLAUDE.md. Solución: agrégala al archivo para que persista.

Auto memory: el cuaderno personal de Claude

Auto memory es el segundo sistema de memoria. Aquí Claude escribe por su cuenta. Cuando descubre algo útil mientras trabaja contigo, lo anota para recordarlo después.

Piensa en un chef que trabaja en tu cocina. Al principio no sabe dónde está nada. Pero cada día anota cosas: "el azúcar está en el cajón de arriba", "al dueño le gusta la comida sin sal". Eso es auto memory.

Qué guarda Claude en auto memory

Claude guarda cosas como:

  • Comandos de build que descubrió.
  • Trucos de debugging que funcionaron.
  • Decisiones de arquitectura que encontró.
  • Tus preferencias de estilo de código.
  • Flujos de trabajo que detecta que prefieres.

No guarda algo en cada sesión. Solo guarda cosas que serían útiles en una conversación futura. Cuando ves "Writing memory" o "Recalled memory" en la interfaz, Claude está escribiendo o leyendo de auto memory.

Los subagentes (agentes secundarios que Claude lanza para tareas paralelas) también pueden mantener su propia auto memory. Así que si un subagente descubre algo útil, también lo anota.

También puedes pedirle que recuerde algo directamente:

Prompt: "siempre usa pnpm, no npm"
Prompt: "recuerda que los tests de API requieren Redis local"

Para agregar algo a CLAUDE.md en vez de auto memory, sé específico: "add this to CLAUDE.md".

Dónde vive la auto memory

Cada proyecto tiene su carpeta de memoria en:

~/.claude/projects/<proyecto>/memory/
├── MEMORY.md                # Indice, se carga al inicio
├── debugging.md             # Notas de debugging
├── api-conventions.md       # Convenciones de API
└── ...                      # Otros archivos por tema

El nombre <proyecto> se deriva del repositorio git. Todos los worktrees y subdirectorios del mismo repo comparten la misma memoria.

Detalle importante

Solo las primeras 200 líneas o 25KB (lo que venga primero) de MEMORY.md se cargan al inicio. El contenido más allá de ese umbral no se carga automáticamente. Los archivos de temas (como debugging.md) tampoco se cargan al inicio. Claude los lee bajo demanda cuando los necesita.

Auto memory es local a tu máquina. No se comparte entre computadoras ni entornos cloud.

Configurar auto memory

Auto memory viene habilitada por defecto. Puedes controlarla de varias formas:

  • Toggle rápido — escribe /memory en una sesión para activarla o desactivarla.
  • Settings del proyecto — pon "autoMemoryEnabled": false en los settings.
  • Variable de entorno — CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude

Si quieres cambiar dónde se guardan los archivos, usa el setting autoMemoryDirectory:

{
    "autoMemoryDirectory": "~/mi-directorio-de-memoria"
}

Este setting se puede leer desde cualquier nivel de settings, pero hay un matiz de seguridad: cuando lo defines en .claude/settings.json o .claude/settings.local.json (settings del proyecto), solo se honra tras aceptar el diálogo de confianza del workspace (workspace trust). Esto evita que un proyecto compartido redirija tu memoria a un lugar no deseado sin tu aprobación explícita.

Mantener la auto memory limpia

Después de unas 10 sesiones, la auto memory puede acumular información duplicada u obsoleta. Aproximadamente un 30% de redundancia.

La solución es simple: edita los archivos a mano. Son markdown plano. Usa /memory para abrir la carpeta de memoria y revisar qué hay ahí. Borra lo que ya no aplica.

Claude también se cuida solo. Mantiene MEMORY.md conciso moviendo notas detalladas a archivos de temas separados.

El comando /memory

El comando /memory es tu herramienta para inspeccionar todo el sistema de memoria. Al ejecutarlo, te muestra:

  • Todos los archivos CLAUDE.md y CLAUDE.local.md cargados en la sesión actual.
  • Todas las reglas de .claude/rules/ activas.
  • Un toggle para activar o desactivar auto memory.
  • Un enlace para abrir la carpeta de auto memory.

Puedes seleccionar cualquier archivo de la lista para abrirlo en tu editor. Es la forma más fácil de saber qué instrucciones están activas y qué ha guardado Claude en su memoria.

Hook InstructionsLoaded (avanzado)

Si necesitas saber exactamente qué archivos de instrucciones se cargan y cuándo, existe un hook (un gancho que se dispara automáticamente) llamado InstructionsLoaded.

Este hook se dispara cada vez que un CLAUDE.md o un archivo de reglas se carga en contexto. Tanto al inicio de la sesión como cuando se cargan archivos bajo demanda.

Sirve para:

  • Auditar qué instrucciones recibe Claude.
  • Tracking de cumplimiento en entornos empresariales.
  • Observabilidad del sistema de memoria.

El hook recibe información como:

  • file_path — ruta del archivo cargado.
  • memory_type — si es User, Project, Local o Managed.
  • load_reason — por qué se cargó (inicio de sesión, navegación de subdirectorio, patrón glob, o import).

Limitaciones: este hook no puede bloquear ni modificar la carga. Solo notifica. Y solo soporta hooks de tipo command (no HTTP ni prompt).

Problemas comunes y soluciones

Aquí van los problemas más frecuentes con el sistema de memoria:

Claude no sigue las instrucciones del CLAUDE.md

Posibles causas:

  • Las instrucciones son vagas. "Formatea bien el código" no dice nada. "Usa 2 espacios de indentación" sí.
  • El archivo no se cargó. Verifica con /memory.
  • Hay instrucciones contradictorias entre varios archivos.

Solución: ejecuta /memory, verifica que los archivos se cargan, haz las instrucciones más específicas y busca contradicciones.

El CLAUDE.md es demasiado grande

Si tu CLAUDE.md tiene más de 200 líneas, pierde efectividad. La tasa de cumplimiento baja de ~92% a ~71%.

Solución: divide el contenido. Mueve instrucciones detalladas a archivos en .claude/rules/. Usa imports @path para referenciar documentos extensos. Mantén CLAUDE.md como un resumen ejecutivo.

Advertencia importante

Dividir el contenido con imports @path ayuda a organizar los archivos, pero no reduce el contexto. Los archivos importados se expanden y cargan completos al arrancar la sesión, igual que si estuvieran inline en el CLAUDE.md original. Para reducir el contexto real que ocupan las instrucciones, lo que funciona es usar path-scoped rules en .claude/rules/ con frontmatter paths: esas reglas solo se cargan cuando Claude trabaja con archivos que matchean el patrón.

CLAUDE.md de otros equipos interfiere en monorepo

Claude sube por el árbol de directorios cargando CLAUDE.md ancestrales. En un monorepo, eso puede traer reglas de otros equipos.

Solución: usa claudeMdExcludes en .claude/settings.local.json para excluir los archivos irrelevantes.

Auto memory tiene información obsoleta

Después de muchas sesiones, la auto memory acumula basura. Comandos que ya no existen, decisiones que cambiaron.

Solución: abre la carpeta con /memory, revisa los archivos y borra lo que ya no sirve. Son archivos de texto plano. Puedes editarlos con cualquier editor.

Tabla resumen de ubicaciones

Aquí tienes todas las ubicaciones de memoria en un solo lugar:

  • Managed policy — /Library/Application Support/ClaudeCode/CLAUDE.md (macOS), /etc/claude-code/CLAUDE.md (Linux). Alcance: organización. No excluible.
  • Usuario — ~/.claude/CLAUDE.md. Alcance: todos tus proyectos. Personal.
  • Proyecto — ./CLAUDE.md o ./.claude/CLAUDE.md. Alcance: el proyecto. Compartido vía git.
  • Local (personal por proyecto) — ./CLAUDE.local.md. Alcance: el proyecto, solo tú. En .gitignore. Se carga después de CLAUDE.md.
  • Subdirectorio — ./subdir/CLAUDE.md. Alcance: ese módulo. Carga bajo demanda.
  • Reglas — .claude/rules/*.md. Alcance: proyecto. Modulares por tema.
  • Reglas de usuario — ~/.claude/rules/*.md. Alcance: todos tus proyectos. Menor prioridad.
  • Auto memory — ~/.claude/projects/<proyecto>/memory/. Escrito por Claude. Local a la máquina.

Ejemplos Prácticos

Crear tu primer CLAUDE.md con /init

/init

Ejecuta /init en tu proyecto. Claude analizará el código y generará un CLAUDE.md con los comandos de build, convenciones y estructura que descubra. Después, edita el archivo para agregar lo que Claude no descubrió.

Estructura básica de CLAUDE.md para un proyecto web

# Mi App Web

## Comandos
- `pnpm dev` para desarrollo local
- `pnpm test` para tests
- `pnpm build` para producción

## Estandares
- TypeScript estricto, sin 'any'
- Componentes React funcionales
- 2 espacios de indentacion

## Arquitectura
- Pages en src/pages/
- Componentes en src/components/
- API en src/api/

Un CLAUDE.md corto y efectivo. Tiene comandos, estándares y arquitectura. Todo en menos de 20 líneas. Usa bullets e imperativos para máximo cumplimiento.

Crear una regla path-specific para la API

---
paths:
   - "src/api/**/*.ts"
---

# Reglas de API

- Valida inputs con zod schemas
- Retorna errores con formato { error: string, code: number }
- Documenta cada endpoint con JSDoc

Guarda esto en .claude/rules/api.md. Solo se activa cuando Claude lee archivos TypeScript en src/api/. Así no consume contexto innecesario cuando trabajas en otras partes.

Pedirle a Claude que recuerde algo

siempre usa pnpm en vez de npm

Escribe esto en el chat de Claude Code. Claude lo guardará en auto memory y lo recordará en sesiones futuras. No necesitas editar ningún archivo.

Inspeccionar toda la memoria activa

/memory

Muestra todos los archivos de instrucciones cargados, te permite abrir cualquiera en tu editor, y te da acceso a la carpeta de auto memory para revisar qué ha aprendido Claude.

Excluir CLAUDE.md irrelevantes en un monorepo

{
    "claudeMdExcludes": [
        "**/other-team/CLAUDE.md",
        "**/legacy-app/.claude/rules/**"
    ]
}

Pon esto en .claude/settings.local.json. Excluye los CLAUDE.md de otros equipos para que no interfieran con tu trabajo. El .local hace que sea solo para tu máquina.

Consejo

Mantén tu CLAUDE.md debajo de 200 líneas. Los archivos cortos tienen ~92% de cumplimiento. Los largos bajan a ~71%.

Consejo

Usa imperativos ('Usa X') en vez de descriptivos ('El proyecto usa X'). Los imperativos tienen un 25% más de precisión.

Consejo

Ejecuta /memory regularmente para ver qué archivos están activos y qué ha guardado Claude en auto memory.

Consejo

Usa CLAUDE.local.md para tus preferencias personales por proyecto (URLs de sandbox, datos de prueba, configuraciones propias) sin ensuciar el git del equipo. Agrégalo a .gitignore y listo.

Advertencia

Las instrucciones en CLAUDE.md son contexto, no configuración forzada. Si son vagas o contradictorias, Claude puede no seguirlas.

Advertencia

Auto memory solo carga las primeras 200 líneas o 25KB (lo que venga primero) de MEMORY.md al inicio. El contenido más allá de ese umbral no se carga automáticamente.

Advertencia

Si rechazas el diálogo de aprobación de imports (@path) la primera vez, los imports quedan deshabilitados permanentemente para ese proyecto.

Nota

Auto memory requiere Claude Code v2.1.59 o posterior.

Nota

Auto memory es local a tu máquina. No se comparte entre computadoras ni entornos cloud.

Nota

Las reglas con paths frontmatter solo se activan cuando Claude LEE archivos coincidentes, no cuando los escribe (issue conocido #23478).

Resumen del Capítulo

Claude Code tiene dos sistemas de memoria: CLAUDE.md (instrucciones que tú escribes) y auto memory (notas que Claude escribe solo). Los archivos CLAUDE.md pueden vivir en múltiples ubicaciones con diferentes alcances, desde nivel organización hasta nivel subdirectorio, incluyendo CLAUDE.local.md para preferencias personales por proyecto. La clave para que funcionen bien es mantenerlos cortos (menos de 200 líneas), usar instrucciones específicas con bullets e imperativos, y revisar periódicamente la auto memory para limpiar información obsoleta.
