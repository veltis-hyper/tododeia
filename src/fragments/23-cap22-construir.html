Construir con Claude

Patrones de desarrollo para crear aplicaciones inteligentes con la API de Claude

En este capítulo vas a aprender a construir aplicaciones reales con la API de Claude. Piensa en Claude como un cerebro poderoso. Tu trabajo es conectar ese cerebro con tus datos, tus herramientas y tus usuarios. Vamos a cubrir los patrones más importantes: desde obtener respuestas en formato JSON perfecto, hasta crear agentes autónomos que resuelven problemas solos.

El panorama general: qué puedes construir

La API de Claude no es solo un chatbot. Es una plataforma completa de desarrollo. Imagina que tienes una caja de herramientas gigante. Cada herramienta sirve para algo diferente.

Las capacidades se organizan en cinco áreas:

  • Capacidades del modelo — razonamiento, formato de respuestas, pensamiento extendido.
  • Herramientas (Tools) — acciones que Claude puede ejecutar en el mundo real. Buscar en la web, ejecutar código, editar archivos.
  • Infraestructura de herramientas — orquestación a escala. Descubrimiento automático de herramientas, MCP, streaming.
  • Gestión de contexto — cómo manejar conversaciones largas sin perder información.
  • Archivos y datos — procesamiento de documentos, PDFs, imágenes.

En este capítulo nos enfocamos en los patrones de desarrollo más usados. Son recetas probadas que puedes copiar y adaptar.

Structured Outputs: respuestas en formato perfecto

Cuando le pides algo a Claude por la API, normalmente responde con texto libre. Pero a veces necesitas datos estructurados. Por ejemplo: un JSON con campos específicos que tu programa pueda leer.

Structured Outputs (salidas estructuradas) es la solución. Le dices a Claude exactamente qué forma debe tener su respuesta. Claude la sigue al pie de la letra.

Piensa en ello como un formulario. En lugar de dejar que Claude escriba lo que quiera, le das un formulario con campos específicos. Claude los llena.

JSON Outputs: respuestas con forma definida

Usas el parámetro output_config.format para definir un JSON Schema. JSON Schema es como un plano arquitectónico. Describe qué campos debe tener la respuesta, de qué tipo son, y cuáles son obligatorios.

response = client.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    output_config={
        'format': {
            'type': 'json_schema',
            'schema': {
                'type': 'object',
                'properties': {
                    'nombre': {'type': 'string'},
                    'email': {'type': 'string'},
                    'plan': {'type': 'string'}
                },
                'required': ['nombre', 'email', 'plan'],
                'additionalProperties': False
            }
        }
    },
    messages=[{'role': 'user', 'content': 'Extrae: Juan Perez, juan@mail.com, plan Enterprise'}]
)

Claude siempre devuelve un JSON válido que cumple con tu esquema. No hay sorpresas.

Disponibilidad (GA): Structured Outputs está generalmente disponible en Fable 5, Mythos 5, Opus 4.5 a 4.8, Sonnet 4.5/4.6 y Haiku 4.5. Opus 4.8 es ahora el modelo Opus más reciente (el string de ejemplo en la documentación es claude-opus-4-8). Los ejemplos de este capítulo usan claude-opus-4-7, que sigue siendo válido; si quieres el modelo más nuevo, basta con cambiar el identificador a claude-opus-4-8.

Helpers de los SDKs: Pydantic y Zod

Escribir JSON Schemas a mano es tedioso. Los SDKs oficiales lo simplifican.

En Python, usas Pydantic. Defines una clase y el SDK la convierte en JSON Schema automáticamente:

from pydantic import BaseModel
from anthropic import Anthropic

class ContactInfo(BaseModel):
    name: str
    email: str
    plan_interest: str

client = Anthropic()
response = client.messages.parse(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{'role': 'user', 'content': 'Extrae: Juan (juan@mail.com), plan Pro'}],
    output_format=ContactInfo,
)
print(response.parsed_output.name)  # 'Juan'

En TypeScript, usas Zod con el helper zodOutputFormat:

import { z } from 'zod';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';

const ContactSchema = z.object({
    name: z.string(),
    email: z.string(),
    plan_interest: z.string()
});

const response = await client.messages.parse({
    model: 'claude-opus-4-7',
    max_tokens: 1024,
    messages: [{role: 'user', content: 'Extract...'}],
    output_config: { format: zodOutputFormat(ContactSchema) }
});

El SDK valida la respuesta contra tu esquema original. Si algo falla, te avisa.

Los SDKs de Java y Ruby también tienen helpers nativos con clases tipadas y outputConfig(Class<T>). Para C#, Go y PHP, se pasan raw JSON schemas directamente via output_config. Todos los SDKs soportan el mismo mecanismo de constrained decoding del lado del servidor.

Strict Tool Use: herramientas con esquema garantizado

Hay otra forma de obtener datos estructurados: strict tool use. Agregas strict: true a la definición de una herramienta. Claude garantiza que los parámetros siempre cumplen el esquema.

tools: [{
    name: 'registrar_contacto',
    strict: true,
    description: 'Registra un contacto nuevo en el sistema.',
    input_schema: {
        type: 'object',
        properties: {
            nombre: { type: 'string' },
            email: { type: 'string' }
        },
        required: ['nombre', 'email']
    }
}]

Esto es como ponerle candado al formulario. Claude no puede enviar datos que no cumplan las reglas.

Limitaciones del JSON Schema

No todo se soporta en los esquemas de structured outputs. Estas keywords no funcionan:

  • minimum, maximum (límites numéricos)
  • minLength, maxLength (límites de texto)
  • pattern (expresiones regulares)
  • oneOf, allOf
  • const, default
  • Recursive schemas (un schema que se referencia a sí mismo)
  • $ref externos (referencias a schemas fuera del documento actual)
  • additionalProperties distinto de false — debe estar en false siempre

Los SDKs de Python y TypeScript manejan esto automáticamente. Remueven las constraints no soportadas y las agregan como texto en las descripciones. Por ejemplo, si tu campo tiene minimum: 100, el SDK agrega a la descripción: "Must be at least 100".

Formatos de string soportados: date, time, date-time, email, uri, uuid.

Existen también límites numéricos importantes para strict tool use y JSON outputs:

  • Máximo 20 strict tools por request.
  • Máximo 24 parámetros opcionales en total entre todos los schemas de la request. Cada parámetro opcional duplica parte del state space de la gramática interna.
  • Máximo 16 parámetros con union types (anyOf) en total entre todos los schemas.

Latencia del primer request: la compilación de la gramática añade latencia inicial. El timeout de compilación es de 180 segundos. Los siguientes requests con el mismo schema usan el resultado cacheado (24 horas).

Dos incompatibilidades importantes: Structured Outputs es incompatible con Citations (recibes error 400 si intentas usar ambos en la misma request). También es incompatible con Message Prefilling. Sin embargo, funciona perfectamente con batch processing y streaming.

RAG: dale a Claude acceso a tus documentos

RAG significa Retrieval-Augmented Generation. En español: generación aumentada con recuperación. Suena complicado, pero la idea es simple.

Imagina que Claude es un experto muy inteligente, pero que no ha leído tus documentos internos. RAG es como darle acceso a tu biblioteca antes de que responda. Primero busca información relevante, luego responde con esa información fresca.

Cómo funciona RAG paso a paso

RAG tiene tres pasos. Piensa en ello como buscar un dato en una enciclopedia:

  1. Partir los documentos en pedazos (chunking): Tomas tus documentos y los divides en secciones pequeñas. Cada sección se llama un chunk. Es como cortar un libro en fichas.
  2. Crear representaciones numéricas (embedding): Cada chunk se convierte en un vector numérico. Un embedding es como una coordenada GPS para el significado del texto. Textos similares quedan cerca en el "mapa".
  3. Buscar y responder: Cuando llega una pregunta, buscas los chunks más cercanos (por similitud). Luego envías esos chunks a Claude junto con la pregunta.
def answer_query(query, db):
    # Paso 1: Buscar chunks relevantes
    results = db.search(query, k=3)

    # Paso 2: Armar contexto
    context = ''
    for result in results:
        context += f'\n{result["text"]}\n'

    # Paso 3: Preguntar a Claude
    prompt = f"""
    {query}
    {context}
    Responde basandote solo en los documentos.
    """
    response = client.messages.create(
        model='claude-haiku-4-5',
        max_tokens=2500,
        messages=[{'role': 'user', 'content': prompt}],
        temperature=0,
    )
    return response.content[0].text

Embeddings: Anthropic no los ofrece. Un detalle importante que sorprende a muchos: Anthropic no tiene un modelo de embeddings propio. Para el paso 2 (convertir texto en vectores) recomienda usar un proveedor externo como Voyage AI. Hay dos parámetros prácticos que debes conocer:

  • input_type — indica si el texto es un documento o una consulta. Usa 'document' cuando indexas tus chunks y 'query' cuando embebes la pregunta del usuario. Es clave para la calidad de la recuperación: nunca lo dejes en None en tareas de retrieval, porque el modelo aplica un prompt interno distinto para cada caso.
  • output_dtype — controla la cuantización de los vectores. Por defecto es float (máxima precisión). Las opciones int8 y binary reducen almacenamiento y costo a cambio de algo de precisión.
import voyageai
vo = voyageai.Client()

# Al indexar tus chunks
doc_embds = vo.embed(textos, model='voyage-4', input_type='document').embeddings

# Al consultar
q_embd = vo.embed([pregunta], model='voyage-4', input_type='query').embeddings[0]

Cómo medir si tu RAG funciona bien

No basta con construir un RAG. Necesitas saber si funciona. Hay cuatro métricas clave:

  • Precisión — de los chunks que recuperaste, cuántos eran realmente útiles. Si recuperas 3 chunks y solo 2 son relevantes, tu precisión es 66%.
  • Recall — de todos los chunks útiles que existen, cuántos lograste recuperar. Si había 4 chunks buenos y encontraste 2, tu recall es 50%.
  • F1 Score — el promedio armónico entre precisión y recall. Es el balance entre ambos.
  • MRR (Mean Reciprocal Rank) — qué tan arriba en la lista aparece el primer resultado correcto. Si el resultado correcto es el primero, MRR = 1. Si es el tercero, MRR = 0.33.

Anthropic Research publicó la técnica Contextual Retrieval, que combinada con reranking, reduce hasta 67% los fallos de recuperación respecto a un RAG estándar. Esa es la mejora oficial reportada en 2024 que sigue vigente.

Citations API: citaciones automáticas con verificación

La API de Claude tiene una Citations API dedicada para RAG. Cuando adjuntas documentos con citaciones habilitadas, Claude automáticamente respalda cada afirmación con referencias al documento original. Es como si Claude pusiera notas al pie de página verificables.

Se habilita agregando citations: {enabled: true} a cada documento:

response = client.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{
        'role': 'user',
        'content': [
            {
                'type': 'document',
                'source': {
                    'type': 'text',
                    'media_type': 'text/plain',
                    'data': 'La empresa fue fundada en 2010. Tiene 500 empleados.'
                },
                'title': 'Ficha de empresa',
                'citations': {'enabled': True}
            },
            {'type': 'text', 'text': 'Cuando se fundo la empresa?'}
        ]
    }]
)

La API soporta tres tipos de documentos:

  • Plain text — texto simple o prosa. Claude lo divide en oraciones automáticamente (chunking por oración) y cita por índices de caracteres.
  • PDF — archivos PDF con texto. También chunking por oración, pero las citas incluyen número de página (empezando en 1).
  • Custom content — para listas, transcripciones o formatos especiales. Tú defines los bloques y Claude los usa tal cual, sin chunking adicional. Ideal para chunks de RAG que ya tienes pre-procesados.

Cada documento tiene tres campos principales:

  • source — el contenido del documento. Este es el campo citable.
  • title — título opcional. Se pasa al modelo pero no es citable.
  • context — metadata opcional (texto o JSON). Tampoco es citable.

Un dato importante sobre costos: el texto citado (cited_text) no cuenta como tokens de salida. Esto hace que las citaciones sean más económicas que pedirle a Claude que copie fragmentos del documento en su respuesta normal. Además, en turnos siguientes, cited_text tampoco cuenta como tokens de entrada.

Para usar citaciones con tus chunks de RAG, tienes dos opciones: si quieres que Claude cite oraciones específicas, pon cada chunk en un documento de texto plano. Si prefieres controlar la granularidad exacta, usa custom content documents donde cada bloque es un chunk.

Search results blocks: la alternativa moderna a Citations

En 2026 Anthropic introdujo un tipo de bloque dedicado a RAG: search_result. Es la forma recomendada hoy cuando quieres que Claude cite fuentes con la misma calidad y formato que cuando usa la herramienta nativa de búsqueda web.

La diferencia con Citations: en lugar de meter cada chunk como un document, devuelves resultados con campos source (URL u origen) y title. Claude genera citas naturales sin que tengas que activar nada extra. Es más simple y produce respuestas mejor atribuidas.

Se puede usar de dos formas:

Pre-fetched (tú ya tienes los resultados): los entregas top-level en el mensaje del usuario.

messages = [{
    'role': 'user',
    'content': [
        {
            'type': 'search_result',
            'source': 'https://docs.empresa.com/contrato',
            'title': 'Contrato de servicios v3',
            'content': [{'type': 'text', 'text': 'La empresa fue fundada en 2010...'}],
            'citations': {'enabled': True}
        },
        {'type': 'text', 'text': 'Cuando se fundo la empresa?'}
    ]
}]

Dinámico via tool: defines una herramienta de búsqueda y devuelves search_result blocks como tool_result.content. Claude los cita igual que si fueran resultados de web search.

Modelos soportados: Opus 4.7, 4.6, 4.5, 4.1, Sonnet 4.6, 4.5 y Haiku 4.5. Es ZDR-eligible. Cuando puedas usarlo, prefiérelo sobre Citations: el código es más limpio y las respuestas se sienten más naturales.

Contextual Retrieval: la receta avanzada de Anthropic

Contextual Retrieval es una técnica publicada por Anthropic Research que reduce hasta 67% los fallos de recuperación de un RAG estándar. Es la receta oficial cuando quieres calidad seria.

Combina tres ingredientes:

  1. Contextual Embeddings: antes de embeddear cada chunk, le agregas un párrafo explicativo generado por Claude. Algo como: "Este fragmento pertenece al contrato de servicios v3, sección 4, y habla de las cláusulas de rescisión". El embedding resultante captura mucho mejor el significado.
  2. Contextual BM25: índices léxicos clásicos (BM25) sobre los mismos chunks contextualizados. Capturan terminología exacta que los embeddings semánticos a veces se pierden.
  3. Reranking: después de combinar los top-N resultados de ambos, un reranker (puede ser Claude Haiku) reordena por relevancia final.

Las tres técnicas juntas reducen 67% los fallos. Las dos primeras solas reducen ~49%. El reranking solo añade el resto.

Costo a considerar: generar el contexto de cada chunk con Claude tiene un costo inicial. Pero combinado con prompt caching del documento fuente, el costo amortizado es bajo. Y solo se hace una vez por documento.

Recomendación oficial: evalúa retrieval (recall@k de los chunks correctos) y end-to-end (calidad de la respuesta final) por separado. Si tu retrieval va bien pero la respuesta no, el problema está en el prompt. Si el retrieval falla, mejora chunking/embeddings/reranking.

Files API: sube archivos una vez, úsalos muchas

La Files API resuelve un problema muy concreto: si subes el mismo PDF en cada request, pagas su procesamiento cada vez. Con Files API, lo subes una vez, recibes un file_id, y lo referencias en todas las llamadas siguientes.

Es como tener una nube compartida con Claude. Subes el archivo y le pasas el link.

Cómo usar la Files API

Activa el beta agregando el header anthropic-beta: files-api-2025-04-14. Los SDKs lo pasan via betas=['files-api-2025-04-14'].

Subir un archivo y usarlo:

uploaded = client.beta.files.upload(
    file=('contrato.pdf', open('contrato.pdf', 'rb'), 'application/pdf')
)

resp = client.beta.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{
        'role': 'user',
        'content': [
            {'type': 'document', 'source': {'type': 'file', 'file_id': uploaded.id}},
            {'type': 'text', 'text': 'Resume este contrato'}
        ]
    }],
    betas=['files-api-2025-04-14']
)

Operaciones disponibles: upload, list, retrieve (metadata), delete, download.

Tipos soportados: PDF, texto plano, imágenes (JPEG, PNG, GIF, WebP) y datasets para code execution.

Límites y restricciones de la Files API

La Files API tiene topes que debes conocer:

  • 500 MB por archivo individual.
  • 500 GB totales por organización.
  • Aproximadamente 100 requests por minuto en beta.
  • Solo puedes descargar archivos generados por skills o code execution. Los que tú subes no se pueden bajar de vuelta. Si necesitas el archivo original, guárdalo localmente antes de subirlo.

Costo: las operaciones del Files API (upload, list, delete) son gratis. Solo se cobra el contenido del archivo como input tokens cuando lo usas en una request a Messages.

Errores frecuentes: 404 si el file_id no existe, 400 si el tipo de archivo no se soporta o si excede el context window al usarse, 413 si el archivo supera 500 MB, 403 si tu organización superó 500 GB. No es ZDR-eligible.

Tool Use: conecta a Claude con el mundo real

Por defecto, Claude solo puede leer texto y generar texto. Tool Use (uso de herramientas) le da superpoderes. Le permite ejecutar funciones que tú defines.

Es como darle manos a un cerebro. Sin herramientas, Claude solo puede pensar y hablar. Con herramientas, puede consultar bases de datos, llamar APIs, enviar emails, y mucho más.

Cómo definir una herramienta

Cada herramienta necesita tres cosas:

  1. name: un nombre corto y descriptivo. Solo letras, números, guiones y guiones bajos. Máximo 64 caracteres.
  2. description: una descripción detallada de 3-4 oraciones. Qué hace, cuándo usarla, qué significa cada parámetro.
  3. input_schema: un JSON Schema con los parámetros que acepta.
tools = [{
    'name': 'obtener_clima',
    'description': 'Obtiene el clima actual de una ciudad. Usa esto cuando el usuario pregunte por el tiempo. El parametro ciudad debe incluir pais.',
    'input_schema': {
        'type': 'object',
        'properties': {
            'ciudad': {
                'type': 'string',
                'description': 'Ciudad y pais, ej: Madrid, Espana'
            }
        },
        'required': ['ciudad']
    }
}]

Las descripciones detalladas son clave. Cuanto mejor describas la herramienta, mejor la usará Claude.

Un dato útil sobre costos: cuando defines al menos una herramienta, Claude agrega automáticamente un system prompt interno para tool use. Esto consume 346 tokens extra con tool_choice en auto o none, y 313 tokens extra con any o tool (para Opus 4.6, Sonnet 4.6 y Haiku 4.5). Tenlo en cuenta al calcular costos.

El conteo varía según el modelo (rango general de 290 a 804 tokens). En Opus 4.8 los counts aproximados son ~290 tokens con tool_choice en auto o none, y ~410 tokens con any o tool.

Controlar cuándo usa herramientas

El parámetro tool_choice controla el comportamiento:

  • auto — Claude decide si usar o no una herramienta. Es el valor por defecto.
  • any — Claude debe usar alguna herramienta. No puede responder sin usarla.
  • tool — Claude debe usar una herramienta específica que tú indicas.
  • none — Claude no puede usar herramientas. Solo texto.

Por defecto, Claude puede usar varias herramientas en paralelo en una sola respuesta. Si necesitas que use solo una a la vez, agrega disable_parallel_tool_use: true.

Importante

Importante con thinking: si activas extended thinking o adaptive thinking, tool_choice solo acepta auto o none. Combinarlo con any o un tool específico devuelve error 400. La razón: Claude necesita libertad para razonar sin estar obligado a llamar una tool concreta.

Tool Runner: automatiza el bucle

Normalmente, cuando Claude quiere usar una herramienta, tu programa debe: recibir la petición, ejecutar la función, devolver el resultado, y enviar otro mensaje. Es un bucle manual.

El Tool Runner (beta) automatiza todo esto. Tú decoras tus funciones y el runner se encarga del resto:

from anthropic import beta_tool

@beta_tool
def obtener_clima(ciudad: str) -> str:
    """Obtiene el clima actual de una ciudad.
    Args:
        ciudad: Ciudad y pais
    """
    return '{"temp": "22C", "condicion": "Soleado"}'

runner = client.beta.messages.tool_runner(
    model='claude-opus-4-7',
    max_tokens=1024,
    tools=[obtener_clima],
    messages=[{'role': 'user', 'content': 'Que clima hace en Buenos Aires?'}],
)
for message in runner:
    print(message.content[0].text)

El runner ejecuta la herramienta, maneja los resultados y continúa la conversación. Tú solo defines las funciones.

Errores comunes con herramientas

Hay un error muy frecuente que causa dolor de cabeza. Cuando un mensaje del usuario contiene un tool_result y texto, el tool_result debe ir primero en el array de contenido. Si pones el texto antes, recibes un error 400.

// CORRECTO: tool_result primero
messages: [{
    role: 'user',
    content: [
        { type: 'tool_result', tool_use_id: '...', content: '...' },
        { type: 'text', text: 'Gracias, ahora...' }
    ]
}]

// INCORRECTO: texto primero -> Error 400
messages: [{
    role: 'user',
    content: [
        { type: 'text', text: 'Gracias' },
        { type: 'tool_result', tool_use_id: '...', content: '...' }
    ]
}]

Server tools: herramientas que ejecuta Anthropic

Hay dos familias de herramientas: client tools (tu app las ejecuta) y server tools (las ejecuta Anthropic en sus servidores). Las server tools son las más cómodas porque no tienes que implementarlas.

Server tools disponibles:

  • web_search — Claude busca en la web por sí solo.
  • web_fetch — Claude descarga una URL.
  • code_execution — Claude ejecuta Python en un contenedor sandboxed.
  • advisor_tool — un modelo más inteligente actúa como consultor cuando Claude (más rápido) necesita una segunda opinión. Útil para combinar latencia baja con calidad alta puntual.
  • tool_search — permite escalar a miles de tools cargándolas bajo demanda con un patrón regex. Solo se inyectan en contexto las que matchean. Resuelve el problema de tener cientos de tools y no querer pagar tokens por todas en cada request.

Otras capacidades nuevas: programmatic tool calling permite que Claude llame tus tools desde dentro de un container de code_execution. Y fine-grained tool streaming streamea los parámetros de cada tool sin esperar validación JSON, útil para mostrar feedback inmediato en la UI.

MCP connector: clientes MCP sin escribir cliente

El MCP connector te deja conectar a servidores MCP remotos directamente desde la Messages API, sin escribir un cliente MCP propio. Anthropic se encarga del transporte y la negociación.

Activa el beta con header anthropic-beta: mcp-client-2025-11-20. El header anterior mcp-client-2025-04-04 está deprecated y debes migrar.

La configuración tiene dos partes: mcp_servers (lista de servidores) y tools con bloques type: 'mcp_toolset' que referencian cada servidor por nombre.

resp = client.beta.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{'role': 'user', 'content': 'Lista mis eventos de hoy'}],
    mcp_servers=[{
        'type': 'url',
        'url': 'https://gcal-mcp.example.com/sse',
        'name': 'gcal',
        'authorization_token': token
    }],
    tools=[{
        'type': 'mcp_toolset',
        'mcp_server_name': 'gcal',
        'default_config': {'enabled': False},
        'configs': {'list_events': {'enabled': True}}
    }],
    betas=['mcp-client-2025-11-20']
)

Dos patrones típicos:

  • Allowlist — default_config: {enabled: false} + configs habilitando solo las tools permitidas. Recomendado para producción.
  • Denylist — default_config: {enabled: true} + configs deshabilitando las prohibidas. Más permisivo.

Restricciones a tener en cuenta:

  • Solo soporta tool calls del spec MCP (no prompts ni resources via API).
  • El servidor debe ser público HTTPS (Streamable HTTP o SSE).
  • No está disponible en Bedrock ni Vertex AI. Solo Claude API, Claude Platform on AWS y Microsoft Foundry.
  • No es ZDR-eligible.
  • Si mcp_server_name de un toolset no coincide con name de un server, recibes error de validación.

En la respuesta verás bloques mcp_tool_use y mcp_tool_result en lugar de los tool_use/tool_result normales.

Agentes autónomos: Claude que trabaja solo

Un agente autónomo es un programa que usa Claude para tomar decisiones y ejecutar acciones sin intervención humana. Imagina un robot que puede leer archivos, buscar información, escribir código, y corregir errores. Todo por su cuenta.

El Agent SDK de Anthropic (antes Claude Code SDK) te da las mismas herramientas que usa Claude Code internamente.

Tu primer agente con el Agent SDK

Instalar el SDK es sencillo:

# Python
pip install claude-agent-sdk

# TypeScript
npm install @anthropic-ai/claude-agent-sdk

Un agente básico se ve así:

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    async for message in query(
        prompt='Encuentra y corrige el bug en auth.py',
        options=ClaudeAgentOptions(
            allowed_tools=['Read', 'Edit', 'Bash']
        ),
    ):
        print(message)

asyncio.run(main())

Con esas tres líneas principales, creaste un agente que puede leer archivos, editarlos y ejecutar comandos. El SDK maneja todo el bucle de herramientas internamente.

Subagentes: divide y vencerás

Un agente puede delegar trabajo a subagentes especializados. Es como un jefe que asigna tareas a su equipo.

async for message in query(
    prompt='Revisa la calidad del codigo en este proyecto',
    options=ClaudeAgentOptions(
        allowed_tools=['Read', 'Glob', 'Grep', 'Agent'],
        agents={
            'code-reviewer': AgentDefinition(
                description='Revisa calidad y seguridad del codigo.',
                prompt='Analiza el codigo y sugiere mejoras.',
                tools=['Read', 'Glob', 'Grep'],
            )
        },
    ),
):
    print(message)

El agente principal decide cuándo delegar. Cada subagente tiene sus propias herramientas e instrucciones. Cuando termina, reporta resultados al agente principal.

Un aviso: Claude Opus 4.6 a veces sobreusa subagentes cuando una operación directa sería más eficiente. Vigila que la delegación tenga sentido.

Patrones para agentes de larga duración

Los agentes que trabajan por períodos largos necesitan estrategias especiales:

  • Gestión de estado — usa JSON para datos estructurados, texto libre para notas de progreso, y git para checkpoints. Es como un cuaderno de notas organizado.
  • Multi-context window — usa el primer context window para setup (tests, scripts de inicialización). Los siguientes para iterar y refinar.
  • Self-correction — el patrón más común es generar un borrador, revisarlo, y refinarlo. Tres pasadas son mejor que una.
  • Seguridad — siempre pide confirmación para acciones destructivas o irreversibles. Un agente que borra archivos sin preguntar es peligroso.

Los cinco patrones canónicos de Anthropic

Anthropic Engineering publicó el artículo Building Effective Agents con cinco patrones de referencia que cubren la mayoría de casos de uso. Aprenderlos te ahorra reinventar la rueda.

  1. Prompt chaining: encadenas llamadas en secuencia. La salida de una alimenta a la siguiente. Útil cuando el problema se descompone en pasos lineales fijos. Ejemplo: 1) extraer datos, 2) clasificarlos, 3) generar reporte.
  2. Routing: un primer LLM clasifica la petición y la enruta a un especialista. Útil cuando tienes prompts muy distintos para tareas distintas. Ejemplo: un primer modelo decide si es soporte técnico, ventas o facturación, y delega.
  3. Parallelization: divides el trabajo en sub-tareas que pueden correr en paralelo, y luego agregas los resultados. Útil para velocidad o para tener múltiples opiniones. Ejemplo: pedir tres revisiones de un texto en paralelo y combinar las mejoras.
  4. Orchestrator-workers: un lead agent decide dinámicamente qué sub-tareas crear y las delega a workers, cada uno con sus propios prompts, herramientas y modelos. A diferencia de parallelization, las sub-tareas no se conocen de antemano. Claude Code usa este patrón para resolver GitHub issues.
  5. Evaluator-optimizer: un LLM genera una respuesta y otro la evalúa/refina en bucle hasta cumplir criterios. Útil cuando el resultado tiene calidad subjetiva (escritura, código, diseño) y necesitas iterar.

El mensaje central del artículo: empieza siempre con la solución más simple. Un prompt bien escrito + evals suele ganarle a una orquesta de cuatro agentes. Solo escala a multi-agente cuando midas que lo simple no rinde.

Claude Managed Agents: agentes con memoria persistente

En 2026 Anthropic introdujo Claude Managed Agents (beta): una plataforma para desplegar agentes con características que el Agent SDK por sí solo no te da out-of-the-box.

Lo que aporta sobre el Agent SDK clásico:

  • Memoria persistente — el agente recuerda interacciones entre sesiones sin que tú manejes el storage.
  • Sub-agentes nativos — orquestador + workers manejados por la plataforma.
  • File system compartido — los sub-agentes ven los mismos archivos sin que tú sincronices nada.
  • Advisor strategy — integración nativa con la advisor_tool para combinar un modelo rápido con consultas puntuales a uno más fuerte.

Cuándo elegir uno u otro: usa el Agent SDK si quieres control total y correr local (Claude Code, scripts propios, CI). Usa Managed Agents cuando necesites desplegar un agente como producto con memoria entre sesiones y mínima infraestructura de tu lado.

Conversaciones multi-turno y gestión de contexto

Cada vez que envías un mensaje a Claude, le envías toda la conversación anterior. Es como releerle toda la historia cada vez que le hablas. Esto consume tokens (las unidades de texto que Claude procesa).

La ventana de contexto es el límite de cuánto puede recordar Claude en una conversación. Es como la memoria de trabajo de una persona. Estándar: 200,000 tokens. Beta: 1 millón de tokens.

Context awareness: Claude sabe cuánto le queda

Claude puede rastrear cuántos tokens le quedan. Es como un indicador de gasolina. Al inicio de la conversación, recibe su presupuesto total:

<budget:token_budget>200000</budget:token_budget>

Después de cada uso de herramienta, recibe una actualización:

<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>

Disponible en Claude Sonnet 4.6, Sonnet 4.5 y Haiku 4.5.

Compaction: resumir para no olvidar

Compaction (compactación) es como tomar notas resumidas de una reunión larga. Cuando la conversación se acerca al límite, Claude genera un resumen de las partes más antiguas. Luego continúa con el resumen en lugar del texto completo.

Se habilita así:

response = client.beta.messages.create(
    betas=['compact-2026-01-12'],
    model='claude-opus-4-7',
    max_tokens=4096,
    messages=messages,
    context_management={
        'edits': [{'type': 'compact_20260112'}]
    },
)

El proceso es automático. Cuando los tokens de entrada superan el 80% del contexto (configurable con trigger_tokens), Claude genera un resumen y descarta los mensajes antiguos.

Es beta. Funciona con Opus 4.7, Opus 4.6 y Sonnet 4.6.

Context rot: más no siempre es mejor

Hay una trampa con las ventanas de contexto grandes. A medida que crece el texto acumulado, la precisión y el recall se degradan. Anthropic lo llama context rot (deterioro de contexto).

Es como intentar encontrar una frase específica en un libro de 1000 páginas. Cuanto más grande el libro, más difícil encontrarla.

La lección: no llenes el contexto solo porque puedes. Curar lo que está en el contexto es tan importante como tener espacio disponible. Prefiere compaction o context editing sobre simplemente meter más texto.

System prompts avanzados

El system prompt es la primera instrucción que recibe Claude. Define su personalidad, reglas y comportamiento. Es como el manual de operaciones de un empleado.

Los modelos Claude 4.5 y posteriores son más responsivos al system prompt que versiones anteriores. Esto significa que tus instrucciones tienen más peso.

Nota

Nota sobre verbosidad en Opus 4.7: el modelo calibra cuánta explicación da según el contexto. Si quieres respuestas concisas, pídelo explícitamente. Una instrucción como "Provide concise, focused responses. Skip non-essential context" en el system prompt produce respuestas más breves y al grano. Si no lo dices, Opus 4.7 tiende a explicar más por defecto.

Usa XML tags para organizar instrucciones

Las XML tags son como carpetas para tus instrucciones. Ayudan a Claude a distinguir entre diferentes tipos de información:

system = """
<instructions>
Eres un asistente de soporte tecnico para la empresa Acme.
Respondes siempre en espanol. Eres amable pero directo.
</instructions>

<context>
Productos de Acme: Widget Pro ($99), Widget Plus ($149).
Horario de soporte: Lunes a Viernes, 9am-6pm.
</context>

<rules>
Nunca compartas precios de competidores.
Si no sabes algo, di 'Voy a consultar con el equipo'.
</rules>
"""

Coloca los documentos largos al inicio del prompt. Las instrucciones importantes van al final (Claude presta más atención al principio y al final).

Prompts especiales para agentes

Anthropic recomienda XML tags específicos para configurar agentes:

  • <default_to_action> — Claude toma acción en lugar de solo sugerir. Ideal para agentes de código.
  • <investigate_before_answering> — Claude verifica información antes de responder. Reduce alucinaciones drásticamente.
  • <use_parallel_tool_calls> — Claude lanza herramientas en paralelo cuando no hay dependencias. Mejora velocidad.
  • <avoid_excessive_markdown_and_bullet_points> — Claude escribe en prosa fluida en lugar de listas interminables.

Un tip para Claude 4.6: evita lenguaje agresivo como "CRITICAL: You MUST...". Esto causa que Claude sobreuse herramientas. Usa lenguaje normal: "Usa esta herramienta cuando...".

Multishot prompting: enseña con ejemplos

Multishot prompting es darle a Claude ejemplos de lo que quieres antes de pedirle que trabaje. Es como mostrarle una foto del plato terminado antes de que cocine.

Proporciona 3-5 ejemplos envueltos en tags <examples>:

<examples>
<example>
  Input: "Me encanto el producto, funciona perfecto"
  Output: {"sentimiento": "positivo", "confianza": 0.95}
</example>
<example>
  Input: "No sirve, lo devolvi al dia siguiente"
  Output: {"sentimiento": "negativo", "confianza": 0.90}
</example>
</examples>

Los ejemplos son la forma más efectiva de comunicar el formato y estilo exacto que esperas.

Thinking: deja que Claude piense en voz alta

Extended thinking y adaptive thinking permiten a Claude mostrar su proceso de razonamiento. Es como pedirle a un matemático que muestre sus cálculos, no solo la respuesta final.

Adaptive thinking: Claude decide cuánto pensar

Con thinking: {type: 'adaptive'}, Claude decide automáticamente si necesita pensar y cuánto. Para una pregunta simple, no piensa. Para un problema complejo, piensa profundamente.

Es el modo recomendado por defecto en 2026, y el único modo de thinking disponible en Opus 4.7. También es el default en Mythos Preview.

El parámetro effort controla la profundidad:

  • max — problemas muy complejos. Más lento, más costoso, más preciso.
  • xhigh — nuevo en Opus 4.7. Entre max y high. Útil cuando high se queda corto pero max es exagerado.
  • high — default. Buen equilibrio para la mayoría de tareas.
  • medium — recomendado para aplicaciones generales con presupuesto ajustado.
  • low — alto volumen o baja latencia. Respuestas rápidas.
response = client.messages.create(
    model='claude-opus-4-7',
    max_tokens=64000,
    thinking={'type': 'adaptive'},
    output_config={'effort': 'medium'},
    messages=[{'role': 'user', 'content': 'Explica la relatividad'}],
)

Nuevo parámetro thinking.display: controla cómo se devuelven los thinking blocks al cliente:

  • summarized — default en Claude 4. Devuelve un resumen del razonamiento.
  • omitted — default en Opus 4.7 y Mythos. Devuelve thinking vacío pero conserva el signature criptográfico (que sigue siendo necesario para multi-turn con tool use). Reduce latencia, sobre todo en streaming.
thinking={'type': 'adaptive', 'display': 'summarized'}

Importante

Importante sobre costos: el conteo de tokens facturados de thinking no coincide con lo visible. Siempre se cobra el thinking completo, aunque uses summarized u omitted. No es un truco para pagar menos: es un truco para recibir menos bytes y reducir latencia de transferencia.

Extended thinking manual: tú pones el límite (deprecated)

Si prefieres controlar exactamente cuántos tokens puede usar para pensar, históricamente existió este modo:

thinking={'type': 'enabled', 'budget_tokens': 16384}

Estado en 2026: este modo manual con budget_tokens está:

  • Deprecated en Opus 4.6 y Sonnet 4.6 (sigue funcionando pero no se recomienda).
  • No soportado en Opus 4.7. Si lo envías, recibes error 400.

La recomendación oficial es migrar a adaptive con effort. Si necesitas un cap duro de costo, combina thinking: {type: 'adaptive'} con un max_tokens conservador.

Tabla rápida de soporte por modelo:

  • Opus 4.7 — solo adaptive.
  • Opus 4.6, Sonnet 4.6 — adaptive (recomendado) o enabled (deprecated).
  • Opus 4.5, Sonnet 4.5 — enabled con budget_tokens.
  • Modelos anteriores — sin thinking.

Los tokens de pensamiento se cobran como tokens de salida.

Thinking blocks en multi-turno: la regla cambió según el modelo. En Opus 4.5+ y Sonnet 4.6+, los thinking blocks de turnos anteriores se conservan en el contexto y debes devolverlos intactos. En modelos previos se eliminan automáticamente. Si haces tool use multi-turno con Opus 4.5+, asegúrate de no perder los thinking blocks ni modificar su firma criptográfica.

Un detalle técnico clave: los thinking blocks usan firmas criptográficas. Si los modificas durante un ciclo de herramientas, la API devuelve un error. Siempre devuélvelos sin tocar. Y ojo: cambiar entre adaptive y enabled/disabled a mitad de conversación rompe el cache breakpoint de mensajes (system y tools sobreviven, los mensajes no).

Evaluaciones: mide si tu sistema funciona

Construir algo con Claude es solo la mitad del trabajo. La otra mitad es asegurarte de que funciona bien. Las evaluaciones (evals) son pruebas sistemáticas para medir rendimiento.

Es como el control de calidad en una fábrica. Antes de lanzar tu producto, lo pruebas con diferentes escenarios.

Define tus criterios de éxito primero

Antes de evaluar, define qué significa "funciona bien" para tu caso. Criterios comunes:

  • Task fidelity — ¿Claude hace lo que le pediste?
  • Consistency — ¿da respuestas similares a preguntas similares?
  • Relevance — ¿la respuesta es pertinente a la pregunta?
  • Tone/style — ¿el tono es adecuado?
  • Latency — ¿responde a tiempo?
  • Cost — ¿cuánto cuesta por petición?

Tres formas de evaluar

Hay tres métodos principales para calificar las respuestas de Claude:

  1. Evaluación por código: escribes funciones que verifican la respuesta. Es lo más rápido y confiable. Ideal para respuestas con formato predecible.
def evaluate_exact_match(output, expected):
    return output.strip().lower() == expected.lower()

accuracy = sum(
    evaluate_exact_match(output, expected)
    for output, expected in zip(outputs, answers)
) / len(answers)
print(f'Precision: {accuracy * 100}%')
  1. Evaluación humana: personas revisan las respuestas. Es lo más flexible pero lo más lento y costoso.
  2. LLM como juez: usas otro modelo de Claude para evaluar las respuestas. Rápido, flexible, y escala bien.
def grade_with_llm(answer, rubric):
    prompt = f"""Evalua esta respuesta segun la rubrica:
    <rubric>{rubric}</rubric>
    <answer>{answer}</answer>
    Razona en <thinking>, luego di 'correct' o 'incorrect' en <result>."""

    return client.messages.create(
        model='claude-opus-4-7',
        max_tokens=2048,
        messages=[{'role': 'user', 'content': prompt}],
    ).content[0].text

Buena práctica: usa un modelo diferente para evaluar que para generar. Esto evita sesgos.

Evaluación en Claude Console

La Claude Console tiene una herramienta de evaluación integrada. El workflow es:

  1. Crea tu prompt con variables dinámicas: {{PRODUCTO}}, {{PREGUNTA}}.
  2. Ve a la pestaña "Evaluate".
  3. Agrega test cases: manualmente, generados por Claude, o importados desde CSV.
  4. Ejecuta la evaluación.
  5. Compara side-by-side múltiples versiones de tu prompt.
  6. Califica cada respuesta en escala 1-5.
  7. Itera y refina.

Es la forma más visual y directa de mejorar tus prompts.

Prompt Caching y Batch Processing

Dos técnicas para ahorrar dinero y tiempo cuando usas la API a escala.

Prompt Caching: no pagues dos veces por lo mismo

Prompt caching guarda porciones del prompt que se repiten. Si tu system prompt tiene 2000 tokens y lo envías en cada petición, sin caching pagas esos 2000 tokens cada vez. Con caching, solo pagas la primera vez (a un pequeño recargo) y las siguientes pagas casi nada.

Dos duraciones disponibles:

  • 5 minutos — estándar, disponible en todas las plataformas. El TTL se refresca a costo cero cada vez que el cache se usa.
  • 1 hora — extendido, disponible en Claude API y Vertex AI. Se activa con ttl: '1h'.

Pricing relativo (sobre el precio de input):

  • Escritura 5m: 1.25× input.
  • Escritura 1h: 2× input.
  • Lectura (cache hit): 0.1× input. Es decir, 90% de descuento.

Mínimos cacheables por modelo (un prefijo más pequeño que esto no se cachea):

  • Opus 4.7, Opus 4.6, Opus 4.5, Haiku 4.5: 4096 tokens.
  • Sonnet 4.6, Sonnet 4.5, Opus 4.1: 1024 tokens.
  • Haiku 3.5: 2048 tokens.

Dos modos de uso:

  1. Automatic caching: pasas cache_control: {type: 'ephemeral'} a nivel top-level del request. El sistema cachea el último bloque cacheable y mueve el breakpoint conforme crece la conversación. Es la opción más simple.
  2. Explicit breakpoints: pones cache_control en bloques individuales (system, tools, document, message). Máximo 4 breakpoints por request. Lookback de 20 bloques hacia atrás buscando match.

Orden del prefijo cacheable: el sistema busca matches en este orden tools → system → messages. Si invalidas un bloque de tools, invalidas todo lo que viene después.

resp = client.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    cache_control={'type': 'ephemeral'},
    system='Eres un asistente legal experto...',
    messages=conversation_history,
)
print(resp.usage.cache_read_input_tokens)
print(resp.usage.cache_creation_input_tokens)

Verifica siempre cache_read_input_tokens y cache_creation_input_tokens en la respuesta para confirmar que el cache está funcionando.

Es especialmente útil para: system prompts largos, definiciones de herramientas, documentos de RAG, y cualquier prefijo que se repita entre peticiones.

Pre-warm del cache con max_tokens=0

Truco útil: si sabes que vas a usar un prompt caro repetidamente, puedes precalentar el cache sin generar respuesta. Solo pagas el costo de escritura del cache.

client.messages.create(
    model='claude-opus-4-7',
    max_tokens=0,
    system=[{
        'type': 'text',
        'text': documento_grande,
        'cache_control': {'type': 'ephemeral'}
    }],
    messages=[{'role': 'user', 'content': 'warmup'}]
)

Con max_tokens=0 el modelo no genera nada, pero el prefill (que incluye la escritura del cache) sí se ejecuta. Las llamadas reales posteriores ven cache hit.

Restricciones del pre-warm con max_tokens=0:

  • No se permite con stream=true.
  • No se permite con extended thinking activo.
  • No se permite con structured outputs.
  • No se permite con tool_choice forzado (any o tool específico).
  • No se permite dentro de batch processing.

Si caes en alguna de esas combinaciones, recibes error 400.

Batch Processing: procesa miles de peticiones con descuento

Batch Processing es procesamiento asíncrono de grandes volúmenes. Envías miles de peticiones de golpe y las recibes cuando están listas. A cambio, recibes un descuento del 50% sobre el precio estándar (tanto input como output).

Ideal para: evaluaciones masivas, procesamiento de documentos, generación de datasets, y cualquier tarea que no necesite respuesta inmediata. La mayoría de batches terminan en menos de una hora.

Disponible en Claude API, Claude Platform on AWS, Amazon Bedrock y Google Vertex AI.

Compatibilidades importantes:

  • Compatible con structured outputs, citations, prompt caching (lectura) y la mayoría de features.
  • No es ZDR-eligible. Si tu org requiere Zero Data Retention, batch no es para ti.
  • No acepta pre-warm de cache con max_tokens=0.

Errores comunes y cómo evitarlos

Construir con Claude tiene sus trampas. Aquí van los errores más frecuentes y cómo solucionarlos.

Errores técnicos

  • tool_result blocks en orden incorrecto — en mensajes user con tool_result y texto, los tool_result deben ir primero. Error 400 si no.
  • Schema con keywords no soportadas — minimum, pattern, oneOf, recursive schemas y $ref externos no funcionan en structured outputs. Usa los SDKs que los transforman automáticamente o quítalos del schema.
  • Thinking blocks modificados — si tocas un thinking block durante tool use, la firma criptográfica falla. Devuélvelos intactos siempre.
  • Exceder el context window — desde Sonnet 3.7, Claude devuelve un error de validación en lugar de truncar silenciosamente. Usa token counting o compaction.
  • tool_choice: 'any' con extended/adaptive thinking — devuelve error 400. Solo se permiten auto o none cuando thinking está activo. Cambia uno de los dos.
  • Switching adaptive ↔ enabled/disabled rompe el message cache — si cambias el tipo de thinking a mitad de conversación, pierdes el cache de mensajes (system y tools sobreviven). Decide al inicio qué modo usarás y mantenlo.
  • MCP server name mismatch — si mcp_server_name en un toolset no coincide con el name de un server en mcp_servers, error de validación. También falla si declaras un server sin toolset que lo referencie.
  • Rate limit en Files API — ~100 req/min en beta. Si los superas, recibes 429. Usa backoff exponencial o contacta sales si necesitas un límite mayor.
  • Cache miss inesperado — pusiste cache_control sobre contenido que cambia cada request (timestamps, IDs dinámicos). Mueve el breakpoint a la frontera del contenido estable y verifica cache_read_input_tokens en la respuesta.
  • Structured outputs schema compilation timeout — schema demasiado complejo o más de 20 strict tools, 24 opcionales o 16 union types. Simplifica o pártelo en varios requests.
  • Citations + structured outputs — 400 invalid_request_error. Son incompatibles. Si necesitas ambos, haz dos llamadas separadas.
  • Recuperación RAG de baja calidad — omitir input_type en los embeddings de Voyage (o usar el mismo valor para query y document) degrada la calidad de la recuperación. Solución: usa input_type='document' al indexar e input_type='query' al consultar; nunca lo dejes en None.

Errores de comportamiento

  • Claude solo sugiere en vez de actuar — tu prompt usa lenguaje ambiguo. Solución: usa lenguaje directo o agrega <default_to_action> al system prompt.
  • Sobreuso de herramientas — prompts con lenguaje agresivo ("CRITICAL: You MUST...") causan que Claude 4.6 abuse de las tools. Solución: lenguaje normal.
  • Alucinaciones sobre código — Claude habla de archivos que no ha leído. Solución: <investigate_before_answering> en el system prompt.
  • Exceso de markdown — listas interminables en vez de prosa. Solución: <avoid_excessive_markdown_and_bullet_points>.
  • Sobreingeniería — Claude crea archivos extra, abstracciones innecesarias. Solución: sé explícito en lo que quieres y lo que no.
  • Thinking tokens caros — Opus 4.6 piensa mucho en effort alto. Solución: baja el effort, agrega instrucción de limitar thinking, o usa budget_tokens.
  • Overthinking excesivo — Claude Opus 4.6 hace mucha más exploración inicial que modelos anteriores, especialmente con effort alto. Solución: agrega la instrucción "Choose an approach and commit to it. Avoid revisiting decisions unless you encounter new information that directly contradicts your reasoning." También puedes usar max_tokens como cap duro en costos de thinking con adaptive thinking, o remover over-prompting de herramientas que antes sub-activaban.

Ejemplos Prácticos

Extraer datos estructurados con Pydantic

from pydantic import BaseModel
from anthropic import Anthropic

class Producto(BaseModel):
    nombre: str
    precio: float
    disponible: bool

client = Anthropic()
response = client.messages.parse(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{'role': 'user', 'content': 'Extrae: Widget Pro, $99.99, en stock'}],
    output_format=Producto,
)
print(response.parsed_output.nombre)  # 'Widget Pro'
print(response.parsed_output.precio)  # 99.99

Define un modelo Pydantic con los campos que necesitas. El SDK de Python convierte automáticamente la clase en JSON Schema, lo envía a Claude, y te devuelve un objeto tipado. No necesitas parsear JSON manualmente.

Pipeline RAG básico con búsqueda vectorial

def responder_con_rag(pregunta, vector_db):
    # Buscar los 3 chunks más relevantes
    chunks = vector_db.search(pregunta, k=3)
    contexto = '\n'.join([c['text'] for c in chunks])

    prompt = f"""
    {pregunta}
    {contexto}
    Responde basandote SOLO en los documentos proporcionados.
    Si la información no está en los documentos, dilo.
    """
    response = client.messages.create(
        model='claude-haiku-4-5',
        max_tokens=2000,
        messages=[{'role': 'user', 'content': prompt}],
        temperature=0,
    )
    return response.content[0].text

Pipeline RAG en tres pasos: 1) busca chunks relevantes en tu base de datos vectorial, 2) arma un prompt con XML tags para separar pregunta y documentos, 3) envía a Claude con temperature=0 para respuestas consistentes. La instrucción de basarse solo en documentos reduce alucinaciones.

Agente autónomo que corrige bugs

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

async def fix_bugs():
    async for msg in query(
        prompt='Encuentra todos los bugs en el directorio src/ y corrigelos. Ejecuta los tests después.',
        options=ClaudeAgentOptions(
            allowed_tools=['Read', 'Edit', 'Bash', 'Glob', 'Grep']
        ),
    ):
        print(msg)

asyncio.run(fix_bugs())

Crea un agente que automáticamente: busca archivos con Glob/Grep, los lee con Read, identifica bugs, los corrige con Edit, y ejecuta tests con Bash. El Agent SDK maneja todo el bucle de herramientas. Tú solo describes la tarea.

Evaluación automática con LLM como juez

def evaluar_respuesta(respuesta, criterio):
    prompt = f"""Evalua está respuesta:
    {criterio}
    {respuesta}

    Razona paso a paso en .
    Luego di 'aprobado' o 'rechazado' en ."""

    resultado = client.messages.create(
        model='claude-opus-4-7',
        max_tokens=1024,
        messages=[{'role': 'user', 'content': prompt}],
    ).content[0].text

    return 'aprobado' in resultado.lower()

# Evaluar 100 respuestas
aprobados = sum(evaluar_respuesta(r, 'Debe ser conciso y correcto')
for r in respuestas)
print(f'Tasa de aprobacion: {aprobados}/{len(respuestas)}')

Usa un modelo Claude como juez para evaluar respuestas de otro modelo. El juez razona antes de decidir (chain-of-thought) para mayor precisión. Escala bien: puedes evaluar cientos de respuestas automáticamente.

Compaction para conversaciones largas

messages = []

# Conversación larga con compaction automatica
for pregunta in preguntas_del_usuario:
    messages.append({'role': 'user', 'content': pregunta})

    response = client.beta.messages.create(
        betas=['compact-2026-01-12'],

Habilita compactación automática para conversaciones que pueden crecer mucho. Cuando el contexto supera el 80% del límite, Claude genera un resumen de lo anterior y continúa. No pierdes información importante, pero ahorras tokens.

RAG con search_result blocks (pre-fetched)

# Tu motor de búsqueda devolvio estos resultados
resultados = [
    {'url': 'https://docs.acme.com/faq', 'title': 'FAQ Acme', 'text': 'El plan Pro cuesta $99/mes...'},
    {'url': 'https://docs.acme.com/limits', 'title': 'Límites', 'text': 'Pro incluye 10000 requests/dia...'}
]

resp = client.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{
        'role': 'user',
        'content': [
            *[{
                'type': 'search_result',
                'source': r['url'],
                'title': r['title'],
                'content': [{'type': 'text', 'text': r['text']}],
                'citations': {'enabled': True}
            } for r in resultados],
            {'type': 'text', 'text': 'Que incluye el plan Pro?'}
        ]
    }]
)

Los search_result blocks producen citas con la misma calidad y formato que la herramienta nativa de web search. Es la forma recomendada en 2026 para RAG con atribución natural. Cada bloque expone source y title que Claude usa al citar.

MCP connector con allowlist

resp = client.beta.messages.create(
    model='claude-opus-4-7',
    max_tokens=1024,
    messages=[{'role': 'user', 'content': 'Lista mis eventos de hoy en Google Calendar'}],
    mcp_servers=[{
        'type': 'url',
        'url': 'https://gcal-mcp.example.com/sse',
        'name': 'gcal',
        'authorization_token': oauth_token
    }],
    tools=[{
        'type': 'mcp_toolset',
        'mcp_server_name': 'gcal',
        # Allowlist: deshabilita todo por defecto y habilita explicitamente
        'default_config': {'enabled': False},
        'configs': {
            'list_events': {'enabled': True}
        }
    }],
    betas=['mcp-client-2025-11-20']
)

Patrón allowlist con MCP connector: el servidor expone muchas tools pero tú solo permites list_events. Reduce superficie de ataque y costo de tokens. El header mcp-client-2025-11-20 es el vigente; el anterior está deprecated.

Usa los SDKs de Python (Pydantic) o TypeScript (Zod) para structured outputs. Manejan automáticamente las limitaciones del JSON Schema y validan las respuestas.

Consejo

Para agentes, usa adaptive thinking con effort 'medium' como punto de partida. Ajusta según resultados.

Consejo

Las descripciones detalladas en tus herramientas (3-4 oraciones) mejoran drásticamente la precisión con que Claude las usa.

Advertencia

No uses lenguaje agresivo en prompts para Claude 4.6 ('CRITICAL: You MUST...'). Causa sobreuso de herramientas. Usa instrucciones normales.

Advertencia

Los thinking blocks tienen firmas criptográficas. Nunca los modifiques durante ciclos de tool use o recibirás un error.

Advertencia

Más contexto no es automáticamente mejor. El 'context rot' degrada precisión. Cura lo que pones en el contexto.

Nota

El Tool Runner (beta) y el Agent SDK son diferentes. El Tool Runner automatiza el bucle de herramientas para la API cliente. El Agent SDK es un framework completo para agentes autónomos.

Nota

Prompt caching puede ahorrar mucho dinero si tu system prompt es grande y lo envías en cada petición. Dos duraciones: 5 minutos y 1 hora. Lectura cuesta solo 0.1× del input (90% de descuento).

Consejo

En Opus 4.7, usa effort 'xhigh' cuando 'high' se queda corto pero 'max' es exagerado. Es el nuevo punto intermedio para razonamiento profundo sin pagar el costo de 'max'.

Advertencia

Extended thinking manual (thinking.type: 'enabled' con budget_tokens) está deprecated en Opus 4.6 y Sonnet 4.6, y NO se soporta en Opus 4.7. Migra a adaptive thinking con effort + max_tokens como cap duro.

Nota

La Files API te deja subir un archivo una vez y referenciarlo por file_id en múltiples requests. Solo se cobra el contenido como input tokens al usarlo; upload/list/delete son gratis. Límite: 500 MB por archivo, ~100 req/min.

Consejo

Precalienta el cache con max_tokens=0 antes de una sesión intensiva. Pagas solo la escritura del cache una vez y las siguientes llamadas ven cache hit. No funciona con stream, thinking, structured outputs, tool_choice forzado ni batches.

Nota

Prefilled responses (pre-llenar la respuesta del asistente) ya no se soporta en Claude 4.6+. Usa structured outputs o instrucciones directas en su lugar.

Resumen del Capítulo

Construir con Claude va mucho más allá de enviar mensajes de texto. Structured outputs garantizan respuestas en formato JSON perfecto. RAG le da acceso a tus documentos. Tool use le da manos para actuar. El Agent SDK crea agentes autónomos completos. Y las evaluaciones te aseguran que todo funciona bien. La clave está en combinar estos patrones según tu caso de uso.
