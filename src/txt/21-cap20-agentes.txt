Qué son los subagentes

Un subagente es un asistente de IA especializado que maneja un tipo específico de tarea. Piensa en
una empresa. El jefe (Claude, el agente principal) no hace todo solo. Delega tareas a empleados
especializados (los subagentes).

Cada subagente tiene tres cosas propias:

   • Su propio prompt: instrucciones específicas de cómo comportarse.
   • Sus propias herramientas: puede tener acceso solo a leer archivos, o también a editarlos.
   • Su propia ventana de contexto: su memoria es independiente del agente principal.

Cuando Claude encuentra una tarea que coincide con la descripción de un subagente, le pasa el
trabajo. El subagente trabaja de forma independiente y devuelve solo el resultado final. Todo el
trabajo intermedio se queda dentro del subagente.

Esto tiene dos ventajas enormes. Primero, el contexto principal no se llena con detalles que no
necesitas ver. Segundo, puedes restringir lo que cada subagente puede hacer, como darle a un
empleado acceso solo a ciertos archivos.

Agente principal vs subagentes
El agente principal es Claude en tu conversación. Es el jefe. Mantiene el hilo de la conversación contigo
y decide cuándo delegar.

Los subagentes son los empleados. Reciben una tarea, la ejecutan y devuelven un resumen. No hablan
contigo directamente. Solo le reportan al jefe.

Subagentes anidados (desde v2.1.172, junio 2026). Antes, un subagente no podía crear otros
subagentes. Eso cambió: hoy un subagente sí puede lanzar sus propios subagentes. Es útil cuando una
tarea delegada se divide a su vez en subtareas paralelas (por ejemplo, un investigador que reparte la
búsqueda entre varios ayudantes).

Pero no hay cadenas infinitas. El anidamiento tiene un límite fijo de 5 niveles de profundidad (no es
configurable). La profundidad cuenta cuántos niveles de subagente hay por debajo de tu conversación
principal. Un subagente que está en la profundidad 5 ya no recibe la herramienta Agent, así que no
puede anidar más. El mismo límite aplica tanto a subagentes en foreground como en background.

El panel de subagentes muestra el árbol completo, con un contador (+N) en cada fila que indica
cuántos descendientes tiene ese subagente. Solo el resumen del subagente de nivel superior vuelve a
ti; todo el trabajo intermedio de los anidados se queda dentro de su rama.


Cuándo usar subagentes vs conversación principal
No todo necesita un subagente. Aquí tienes una guía rápida:

Usa la conversación principal cuando:

   • Necesitas ida y vuelta frecuente con Claude.
   • El cambio es rápido y simple.
   • La latencia importa (los subagentes agregan un poco de tiempo extra).

Usa subagentes cuando:

   • La tarea genera mucho output (logs, resultados de tests).
   • Necesitas restringir herramientas (solo lectura, por ejemplo).
   • El trabajo es autocontenido y solo importa el resultado final.
   • Quieres ejecutar varias tareas en paralelo.

También existe /btw para preguntas rápidas. Es como tocarle el hombro a Claude sin interrumpir el
flujo. Ve todo el contexto pero no tiene herramientas y la respuesta se descarta.



Subagentes integrados (built-in)

Claude Code viene con varios subagentes listos para usar. No necesitas configurar nada. Claude los
usa automáticamente cuando la situación lo requiere.

Explore
Es el explorador del equipo. Su trabajo es buscar y analizar código sin modificar nada. Usa el modelo
Haiku, que es rápido y barato.

Qué hace: busca archivos, encuentra definiciones, analiza la estructura del codebase.

Qué NO hace: no puede escribir ni editar archivos. Es de solo lectura.

Puedes pedirle tres niveles de profundidad:

   • quick : búsquedas rápidas y dirigidas.
   • medium : exploración balanceada.
   • very thorough : análisis exhaustivo en múltiples ubicaciones.

Claude lo usa automáticamente cuando necesita entender tu codebase antes de hacer cambios.

Para ir rápido y barato, Explore omite los archivos CLAUDE.md y el git status . Además es one-
shot: hace su tarea y devuelve el resultado, pero no expone un agent ID, así que no se puede
reanudar. Si necesitas continuar un trabajo de exploración, usa general-purpose o un subagente
personalizado.


Plan
Es el arquitecto. Investiga el codebase para recopilar contexto antes de presentarte un plan de acción.
También es de solo lectura.

Se activa cuando estás en plan mode (modo planificación). Claude le delega la investigación para que
el contexto de búsqueda no llene tu conversación.

Igual que Explore, Plan omite los archivos CLAUDE.md y el git status para ir más rápido, y es
one-shot: no devuelve agent ID, así que no se puede reanudar. Si quieres retomar el trabajo, usa
general-purpose o un subagente personalizado.



General-purpose
Es el todoterreno. Tiene acceso a todas las herramientas. Puede leer, escribir, ejecutar comandos y
más.

Claude lo usa cuando la tarea requiere tanto explorar como modificar código. Es el más versátil de los
subagentes integrados.


Otros subagentes integrados
Hay algunos más especializados:

   • Bash: ejecuta comandos de terminal en un contexto separado.
   • statusline-setup: configura la línea de estado. Se activa con /statusline . Usa Sonnet porque
    la configuración suele requerir entender preferencias y editar archivos con precisión.
   • Claude Code Guide: responde preguntas sobre las funciones de Claude Code. Usa Haiku para
    respuestas rápidas.

Cómo crear subagentes personalizados

Los subagentes integrados son útiles, pero la magia está en crear los tuyos. Es como contratar
empleados especializados para tu proyecto.

Hay tres formas de crear subagentes:

  1. Con el comando /agents (la más fácil).
  2. Creando un archivo Markdown manualmente.
  3. Pasando un JSON al lanzar Claude Code con --agents .

Crear con /agents (recomendado)
Escribe /agents en la conversación. Aparece un menú interactivo donde puedes:

   • Ver todos los subagentes disponibles.
   • Crear uno nuevo paso a paso.
   • Elegir si es para este proyecto o para todos tus proyectos.
   • Seleccionar herramientas, modelo y color.
   • Dejar que Claude te ayude a generar la configuración.

El subagente queda disponible inmediatamente. No necesitas reiniciar.


Crear con archivo Markdown
Un subagente es un archivo .md con dos partes: la configuración (llamada frontmatter) y las
instrucciones.

El frontmatter es un bloque de YAML entre tres guiones ( --- ). Ahí defines el nombre, la descripción,
las herramientas y el modelo. Debajo va el prompt: las instrucciones que recibe el subagente.



   ---
   name: code-reviewer
   description: Reviews code for quality and best practices
   tools: Read, Glob, Grep
   model: sonnet
   ---


   You are a code reviewer. When invoked, analyze the code
   and provide specific, actionable feedback on quality,
   security, and best practices.

Este subagente solo puede leer archivos (Read, Glob, Grep). No puede editar nada. Perfecto para
revisiones seguras.


Dónde guardar los archivos de subagentes
La ubicación del archivo determina quién puede usarlo. Hay cinco niveles, ordenados de mayor a
menor prioridad:

  1. Managed settings (prioridad 1): subagentes organizacionales, desplegados por administradores
    de tu empresa. Tienen la prioridad máxima.
  2. Flag --agents (prioridad 2): solo existe durante esa sesión. Se pasa como JSON al lanzar
    Claude.
  3. .claude/agents/ (prioridad 3): subagentes del proyecto. Se pueden commitear al control de
    versiones para compartir con el equipo.
  4. ~/.claude/agents/ (prioridad 4): subagentes personales. Disponibles en todos tus proyectos.
  5. Plugins (prioridad 5): vienen con plugins instalados.

Si dos subagentes tienen el mismo nombre, gana el de mayor prioridad. Puedes verificar con
/agents o claude agents desde la terminal.

Los subagentes de proyecto se descubren caminando hacia arriba desde el directorio actual.
Importante: los directorios agregados con --add-dir NO se escanean para buscar subagentes.


Crear con --agents (para sesiones temporales)
Puedes definir subagentes como JSON al lanzar Claude. Útil para pruebas rápidas o scripts de
automatización:



   claude --agents '{
      "code-reviewer": {
          "description": "Expert code reviewer",
          "prompt": "You are a senior code reviewer.",
          "tools": ["Read", "Grep", "Glob"],
          "model": "sonnet"
      }
   }'



Este subagente solo vive durante esa sesión. Al cerrar Claude, desaparece.

Referencia completa del frontmatter

El frontmatter es la configuración de tu subagente. Aquí tienes todos los campos disponibles:

Campos obligatorios
   • name : identificador único. Solo letras minúsculas y guiones. Ejemplo: code-reviewer .
   • description : cuándo Claude debe usar este subagente. Claude lee esta descripción para
    decidir si delegar. Escribe algo claro. Truco: agrega "use proactively" si quieres que Claude lo use
    sin que se lo pidas.


Herramientas y permisos
   • tools : lista de herramientas permitidas. Si lo omites, hereda todas. Ejemplos: Read , Glob ,
     Grep , Bash , Write , Edit , Agent . Para restringir qué subagentes puede crear, usa
     Agent(worker, researcher) .

   • disallowedTools : lo opuesto. Herramientas que quieres prohibir. Útil cuando quieres heredar
    casi todo pero excluir unas pocas.
   • permissionMode : controla los permisos. Opciones: default (verificación normal),
     acceptEdits (auto-acepta ediciones), auto (modo automático), dontAsk (auto-deniega),
     bypassPermissions (salta todo), plan (solo lectura).

Cuidado con bypassPermissions . Si el agente padre lo usa, los subagentes lo heredan y no puedes
cambiarlo. Lo mismo aplica para auto : si el padre usa auto mode, el subagente hereda auto mode y
su permissionMode en el frontmatter se ignora.


Modelo y límites
   • model : qué modelo usar. Acepta alias ( sonnet , opus , haiku , fable ) o IDs completos (a
    junio de 2026, por ejemplo claude-opus-4-8 o claude-sonnet-4-6 ). Si lo omites, hereda el
    modelo del padre.
   • maxTurns : límite de turnos antes de detenerse. Útil para evitar que un subagente trabaje de más.
    Ejemplo: maxTurns: 10 .
   • background : ponlo en true para que siempre corra en segundo plano.

El modelo que realmente usa un subagente se resuelve con esta prioridad (de mayor a menor):

  1. Variable de entorno CLAUDE_CODE_SUBAGENT_MODEL : sobreescribe el modelo de todos los
    subagentes. Útil para controlar costos globalmente. Ejemplo: export
    CLAUDE_CODE_SUBAGENT_MODEL=haiku .

  2. Parámetro per-invocation: el modelo que el agente principal pasa al invocar el subagente en esa
    llamada específica.

                                                                                 AGENTES Y SUBAGENTES




  3. Frontmatter model : el modelo definido en el archivo del subagente.
  4. Modelo del padre: si nada de lo anterior se define, hereda el modelo de la conversación principal.


Campos avanzados
   • isolation : ponlo en worktree para darle una copia aislada del repositorio (más detalles
    adelante).
   • memory : memoria persistente entre conversaciones. Opciones: user , project , local (más
    detalles adelante).
   • skills : skills que se cargan en el contexto del subagente. Los subagentes NO heredan skills del
    padre; hay que listarlos explícitamente.
   • mcpServers : servidores MCP disponibles. Puede ser un nombre (comparte conexión del padre) o
    una definición inline (se conecta al iniciar y se desconecta al terminar).
   • hooks : hooks del ciclo de vida. Soporta PreToolUse , PostToolUse y Stop .
   • effort : nivel de esfuerzo del subagente. Opciones: low , medium , high , xhigh , max .
    Sobreescribe el nivel de esfuerzo de la sesión. Los niveles disponibles dependen del modelo: max
    solo está disponible para Opus (en la doc de junio de 2026, Opus 4.8) y xhigh es el nivel
    intermedio entre high y max .
   • color : color de visualización en la lista de tareas y transcripts. Opciones: red , blue , green ,
    yellow , purple , orange , pink , cyan .

   • initialPrompt : prompt que se envía automáticamente como primer turno de usuario cuando
    el agente corre como agente principal de sesión (vía --agent o el setting agent ). Los
    comandos y skills dentro del prompt se procesan normalmente. Ejemplo: initialPrompt: /
    review-all .




Cómo invocar subagentes

Hay varias formas de activar un subagente: automática, por nombre, con @-mention o con el flag --
agent .

Invocación automática
Claude lee la description de cada subagente y decide cuándo usarlo. Si le pides "revisa este
código", y tienes un subagente cuya descripción dice "Reviews code for quality", Claude lo invocará
automáticamente.

Por eso la descripción es tan importante. Una descripción vaga = Claude no sabrá cuándo usarlo.

Invocación explícita
Puedes pedir un subagente por nombre:



   Use the code-reviewer subagent to check the auth module



También puedes encadenar subagentes en secuencia:



   Use the code-reviewer to find problems,
   then use the optimizer to fix them



Y ejecutar varios en paralelo:



   Research the authentication, database, and API
   modules in parallel using separate subagents




Invocación con @-mention
Escribe @ en tu mensaje y aparece un menú typeahead con todos los subagentes disponibles.
Selecciona uno y Claude garantiza que ese subagente se ejecute. No es una sugerencia; es una
instrucción directa.

Esto es más confiable que mencionarlo por nombre, porque elimina la ambigüedad. Claude no tiene
que adivinar si quieres delegarle a ese subagente o no.


Sesión completa como subagente (--agent)
Con el flag --agent , toda la sesión adopta el system prompt, las herramientas y el modelo del
subagente:



   claude --agent code-reviewer



Es como si Claude fuera ese subagente durante toda la sesión. El system prompt del subagente
reemplaza el de Claude Code. Los archivos CLAUDE.md y la memoria del proyecto se siguen cargando
normalmente.

Para subagentes de plugins, usa la sintaxis <plugin>:<agente> :

   claude --agent my-plugin:code-reviewer



También puedes hacer que un proyecto siempre arranque con un subagente específico. Agrega esto a
.claude/settings.json :



   {
       "agent": "code-reviewer"
   }



El flag --agent en la línea de comandos siempre tiene prioridad sobre este setting.


Reanudar un subagente
Cada vez que se invoca un subagente, empieza desde cero. Pero puedes pedirle a Claude que reanude
uno anterior:



   Continue that code review and now
   analyze the authorization logic



Para reanudar, Claude usa la herramienta SendMessage apuntando al ID del agente anterior. El
subagente reanudado conserva todo: tool calls, resultados, razonamiento. Es como retomar una
conversación pausada.

Importante:      esta     capacidad     requiere      que     tengas     activada     la     variable
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 . Esa misma variable que habilita agent teams (más
adelante en este capítulo) es la que expone la herramienta SendMessage . Sin ella, cada invocación
de subagente arranca desde cero.



   export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
   claude



Los transcripts de subagentes que se pueden reanudar viven en ~/.claude/projects/{proyecto}/
{sesión}/subagents/agent-{id}.jsonl .

Worktrees: aislamiento de repositorio

Imagina que tienes un documento de Word. No puedes tener dos personas editándolo al mismo
tiempo sin que se pisen. Los worktrees de Git resuelven esto creando copias del repositorio donde
cada persona trabaja por separado.

Un worktree es un directorio separado con sus propios archivos y su propia rama. Pero comparte el
mismo historial de Git. Es como tener dos escritorios con copias del mismo proyecto.

Worktrees en subagentes
Pon isolation: worktree en el frontmatter y el subagente recibe su propia copia del repositorio:



   ---
   name: feature-builder
   description: Build features in isolation
   isolation: worktree
   tools: Read, Write, Edit, Bash
   ---


   Build the requested feature in your
   isolated worktree.



Si el subagente no hace cambios, el worktree se limpia automáticamente. Si hace cambios, Claude te
pregunta si quieres mantenerlos o borrarlos.


Worktrees desde la línea de comandos
Puedes lanzar Claude directamente en un worktree con el flag --worktree (o -w ):



   claude --worktree feature-auth
   claude -w bugfix-123
   claude --worktree       # nombre auto-generado



Los worktrees se crean en .claude/worktrees/<nombre>/ . La rama se llama worktree-
<nombre> . Se recomienda agregar .claude/worktrees/ a tu .gitignore .

Worktree desde un PR. Si pones # seguido del número del PR, Claude fetcha esa pull request y crea
el worktree con su rama:

                                                                           AGENTES Y SUBAGENTES




    claude --worktree '#1234'



Eso ejecuta git fetch origin pull/1234/head y crea .claude/worktrees/pr-1234/ con la
rama del PR. Perfecto para revisar pull requests sin tocar tu checkout principal. Recuerda poner el
#1234 entre comillas para que la shell no lo interprete como comentario.

Desde qué rama parte el worktree. Por defecto, los worktrees branchean desde origin/HEAD (la
rama por defecto del remoto, normalmente          main ). Puedes cambiar esto con el setting
worktree.baseRef en tu settings.json :



    {
        "worktree": {
            "baseRef": "head"
        }
    }



Acepta dos valores: fresh (default, branch desde origin/HEAD , ideal para empezar limpio) o head
(branch desde tu HEAD actual, útil cuando quieres heredar trabajo en progreso). No acepta refs
arbitrarios.

Limitación en modo headless. Cuando combinas --worktree con -p (modo no-interactivo), los
worktrees NO se limpian automáticamente. No hay prompt de salida que pregunte qué hacer. Tienes
que removerlos a mano con git worktree remove <path> . Si automatizas mucho con -p ,
planifica una limpieza periódica o vigila .claude/worktrees/ .


Copiar archivos gitignored a worktrees (.worktreeinclude)
Cuando se crea un worktree, los archivos que están en .gitignore no se copian (por ejemplo,
.env ). Pero muchas veces necesitas esos archivos para que tu proyecto funcione.

Crea un archivo llamado .worktreeinclude en la raíz de tu proyecto. Usa la misma sintaxis que
.gitignore para listar los archivos gitignored que quieres copiar a cada worktree nuevo:



    .env
    .env.local
    config/secrets.json

Solo se copian archivos que coincidan con un patrón Y que estén gitignored. Archivos que no están

También puedes usar el hook WorktreeCreate en settings.json para tener control total sobre la

Memoria persistente

Normalmente, un subagente empieza sin recuerdos. Cada vez es una hoja en blanco. La memoria
persistente cambia eso. Es como darle un cuaderno de notas que conserva entre conversaciones.

Actívalo con el campo memory en el frontmatter. Hay tres alcances:

   • user : se guarda en ~/.claude/agent-memory/<nombre>/ . Disponible en todos tus proyectos.
   • project : se guarda en .claude/agent-memory/<nombre>/ . Específico de este proyecto. Se
    puede commitear.
   • local : se guarda en .claude/agent-memory-local/<nombre>/ . Local, no se commitea.

Cuando la memoria está habilitada, el subagente recibe instrucciones automáticas para leer y escribir
en su directorio de memoria. También se inyectan automáticamente las primeras 200 líneas o 25 KB
de MEMORY.md , lo que ocurra primero. Si tu archivo de memoria es largo o tiene líneas muy extensas
(por ejemplo, snippets de código grandes), te puedes quedar corto antes de las 200 líneas. La regla
práctica: pon lo más importante arriba y mantén las entradas concisas.



   ---
   name: code-reviewer
   description: Reviews code for quality
   memory: user
   ---


   As you review code, update your memory with
   patterns, conventions, and recurring issues.



Con el tiempo, el subagente aprende patrones de tu codebase. Cada revisión es mejor que la anterior.



Hooks en subagentes

Los hooks son acciones automáticas que se ejecutan en momentos específicos. Como una alarma que
suena cuando algo pasa. Los subagentes soportan hooks en dos lugares.



                                                534                                    @soyenriquerocha

Hooks en el frontmatter
Dentro del archivo del subagente, puedes definir hooks para tres eventos:

   • PreToolUse : antes de usar una herramienta.
   • PostToolUse : después de usar una herramienta.
   • Stop : cuando el subagente termina (se convierte automáticamente en SubagentStop ).



   ---
   name: db-reader
   description: Execute read-only database queries
   tools: Bash
   hooks:
      PreToolUse:
         - matcher: "Bash"
           hooks:
              - type: command
                command: "./scripts/validate-readonly-query.sh"
   ---


   You are a database analyst with
   read-only access.



En este ejemplo, cada vez que el subagente intenta ejecutar un comando Bash, un script valida que
sea una operación de solo lectura. Si no lo es, el script bloquea la ejecución.


Hooks en settings.json
Desde el archivo settings.json del proyecto, puedes definir hooks globales para eventos de
subagentes:

   • SubagentStart : cuando un subagente inicia.
   • SubagentStop : cuando un subagente termina.

   {
       "hooks": {
           "SubagentStart": [
               {
                   "matcher": "db-agent",
                   "hooks": [
                       {
                           "type": "command",
                           "command": "./scripts/setup-db.sh"
                       }
                   ]
               }
           ]
       }
   }



Esto permite preparar el entorno antes de que un subagente empiece o limpiar después de que
termine.



Subagentes con servidores MCP

Los subagentes pueden tener sus propios servidores MCP. Esto es poderoso. Puedes darle a un
subagente acceso a un navegador sin que el agente principal lo tenga.

Hay dos formas de asignar un servidor MCP:

   • Por nombre: comparte la conexión del padre. Solo pon el nombre del servidor.
   • Inline: define la conexión completa. Se conecta al iniciar el subagente y se desconecta al terminar.



   ---
   name: browser-tester
   description: Tests features in a real browser
   mcpServers:
       - playwright:
               type: stdio
               command: npx
               args: ["-y", "@playwright/mcp@latest"]
       - github
   ---


   Use Playwright to navigate and test web pages.

En este ejemplo, playwright es una definición inline (se crea para el subagente) y github es una
referencia por nombre (usa la conexión existente del padre).



Forks: subagentes que heredan tu conversación

Hasta aquí, todos los subagentes que vimos arrancan con un contexto fresco: el system prompt del
frontmatter más la tarea que les pasas. No ven nada de tu conversación.

Un fork es lo opuesto. Es un subagente que hereda toda tu conversación actual. Mismo system
prompt, mismas herramientas, mismo modelo, mismos mensajes intercambiados hasta ese
momento. Como si te clonaras a ti mismo en otra terminal para que siga trabajando mientras tú haces
otra cosa.

Es una función experimental, requiere Claude Code v2.1.117 o superior.

Fork vs subagente nombrado
Las dos formas de delegar trabajan distinto. Esta comparación te ayuda a elegir:

   • Subagente nombrado (lo de las secciones anteriores): contexto fresco. Recibe solo el prompt
    que le pasas. Tiene el system prompt, herramientas y modelo de su definición. Su cache de
    prompt es independiente del padre. En background, los prompts de permisos se auto-deniegan.
   • Fork: contexto heredado. Recibe toda la conversación actual. Tiene el mismo system prompt,
    herramientas y modelo que tú en ese momento. Comparte el prompt cache con el padre (más
    barato y rápido). Sus prompts de ejecución se ven en tu terminal mientras corre.

Regla simple: usa subagente nombrado cuando quieres encapsular una tarea con su propia
experticia y restricciones. Usa fork cuando quieres seguir el mismo hilo de trabajo pero en paralelo,
sin tener que re-explicar el contexto.


Cómo activar fork mode
Buenas noticias: desde Claude Code v2.1.161 el comando /fork está habilitado por defecto. Ya no
necesitas exportar ninguna variable de entorno para usarlo. (Los forks en general requieren v2.1.117 o
superior.)

La variable CLAUDE_CODE_FORK_SUBAGENT sigue existiendo, pero ahora vale 1 por defecto y sirve
para lo contrario: si quieres deshabilitar fork mode explícitamente, ponla en 0 :

AGENTES Y SUBAGENTES




   # Desactivar fork mode explícitamente:
   export CLAUDE_CODE_FORK_SUBAGENT=0
   claude



La variable se honra en las tres formas de usar Claude Code: interactivo, headless ( -p ) y el SDK.

Cuando fork mode está activo pasan tres cosas:

  1. Los spawns de general-purpose se vuelven forks. El subagente integrado
     general-purpose deja de comportarse como un subagente fresco y se convierte en un fork de
    tu conversación.
  2. Todos los spawns van a background. Los forks corren en segundo plano por defecto para que
    puedas seguir trabajando.
  3. El comando /fork queda disponible. Es la forma directa de crear un fork con una instrucción
    específica.


El comando /fork
Con fork mode activo, escribe /fork seguido de una directiva:



   /fork draft unit tests for the parser changes



Claude crea un fork con toda tu conversación actual y la directiva como instrucción inicial. El fork
aparece en el panel inferior y corre en background. Cuando termina, te devuelve el resultado final sin
saturar el contexto con sus tool calls intermedios.

Otros ejemplos útiles:



   /fork explore alternative implementations of
   the rate limiter


   /fork investigate why the integration tests
   are flaky on Windows



Cada fork puede ir por un camino distinto. Tú sigues con la línea principal mientras ellos exploran.

Limitaciones de los forks
Los forks tienen dos limitaciones importantes:

   • Un fork no puede spawnear más forks. No hay forks de forks. Si necesitas más paralelismo,
    lánzalos desde el agente principal.
   • En background, los prompts interactivos fallan. Si un fork necesita preguntarte algo (por
    ejemplo, confirmación de un permiso que no está pre-aprobado), ese tool call falla y el fork
    continúa sin esa herramienta. Pre-aprueba lo que vaya a necesitar antes de lanzar.



Agent Teams (experimental)

Los subagentes trabajan dentro de una sesión. Los agent teams son algo diferente: coordinan
múltiples sesiones de Claude Code como un equipo real.

Piensa en la diferencia así:

   • Subagentes: el jefe le da tareas a empleados y recibe reportes. Comunicación de ida y vuelta con
    el jefe solamente.
   • Agent teams: un equipo donde todos se comunican entre sí. Tienen una lista de tareas
    compartida.

Cómo activar agent teams
Los agent teams son experimentales. Para habilitarlos:



   export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1



Necesitas Claude Code v2.1.32 o superior.

Hay dos modos de visualización:

   • in-process: todos corren en el mismo terminal. Usa Shift+Down para ciclar entre teammates.
   • split panes (tmux): cada teammate tiene su propio panel. Necesitas tener tmux instalado.

Configura el modo en settings.json con teammateMode ( in-process , auto , tmux ) o con el
flag --teammate-mode . Ojo con el default: desde v2.1.179 el valor por defecto cambió de auto a
in-process . Si actualizaste y tus sesiones ya no abren split panes solos, es por esto: ahora hay que
pedir tmux (o auto ) explícitamente.

Creación automática (desde v2.1.178). Ya no tienes que crear el equipo a mano. Los tools
TeamCreate y TeamDelete fueron eliminados: cuando le pides a Claude que lance teammates, el
equipo se arma solo, y la limpieza es automática al salir de la sesión. También cambió el nombre del
equipo en los hooks: el campo team_name quedó deprecado y ahora se deriva de la sesión como
session- seguido de los primeros 8 caracteres del session ID.

Al spawnear teammates, puedes referenciar definiciones de subagentes de cualquier scope. El
teammate respeta el allowlist de herramientas y modelo de la definición. El body se agrega como
instrucciones adicionales (no reemplaza) al system prompt del teammate. Las herramientas de
coordinación ( SendMessage , task tools) siempre están disponibles. Importante: los campos
skills y mcpServers del frontmatter NO se aplican cuando la definición corre como teammate.

Tamaño recomendado: empieza con 3-5 teammates. Asigna 5-6 tareas por teammate para mantener
la productividad. Tres teammates enfocados suelen superar a cinco dispersos.

Dónde vive un team. La configuración y el estado de cada team se guarda en tu directorio de usuario,
no en el proyecto. La estructura es:

   • ~/.claude/teams/{team-name}/config.json : configuración del team (líder, teammates,
    modo).
   • ~/.claude/tasks/{team-name}/ : lista de tareas compartida (con file locking para evitar
    carreras entre teammates).

Esto significa que no existe un equivalente a nivel proyecto: no puedes commitear un team al repo
para que todos los devs hereden la misma configuración. Si quieres reproducir un team en otra
máquina, copia esos directorios manualmente o documenta los comandos de creación.

Hooks específicos de agent teams
Los agent teams tienen tres hooks especiales que puedes configurar en settings.json :

   • TeammateIdle : se dispara cuando un teammate está a punto de quedar inactivo. Si tu script
    devuelve exit code 2, puedes enviar feedback al teammate para que siga trabajando en lugar de
    detenerse.
   • TaskCreated : se dispara cuando se crea una tarea en la lista compartida. Exit code 2 previene la
    creación de la tarea. Útil para validar o filtrar tareas.
   • TaskCompleted : se dispara cuando se marca una tarea como completada. Exit code 2 previene
    que se marque como completa. Útil para agregar pasos de verificación.


Plan approval para teammates
Puedes requerir que los teammates planifiquen antes de implementar. El teammate trabaja en modo
read-only hasta que el líder aprueba su plan.

Si el líder rechaza el plan, el teammate revisa su enfoque basándose en el feedback y re-envía. El líder
toma las decisiones de aprobación de forma autónoma.

La lista de tareas compartida soporta dependencias entre tareas. El sistema usa file locking para
prevenir race conditions cuando varios teammates reclaman tareas al mismo tiempo. Las tareas con
dependencias no resueltas no se pueden reclamar.

Agent view: panel central para sesiones en background

Hasta ahora hablamos de subagentes dentro de una sesión. Pero a veces necesitas varias sesiones
independientes trabajando en paralelo: una arreglando un test flaky, otra investigando un bug en
producción, otra refactorizando un módulo. ¿Cómo las despachas y monitoreas sin tener veinte
terminales abiertas?

Para eso existe agent view. Es una pantalla única donde puedes lanzar, ver y controlar todas tus
sesiones en background. Se abre con un comando:



   claude agents



Agent view es research preview y requiere Claude Code v2.1.139 o superior. Si tu claude agents te
lista subagentes en vez de abrir la vista, corre claude update .

Estados y filtros
Cada sesión en agent view tiene un estado visible:

   • Working: está ejecutando tareas activamente (animado).
   • Needs input: pidió tu intervención (amarillo).
   • Idle: está esperando sin trabajo (atenuado).
   • Completed: terminó con éxito (verde).
   • Failed: terminó con error (rojo).
   • Stopped: detenida manualmente (gris).

Y unos iconos al lado del nombre te dicen el estado del proceso:

   • ✻ o ✽: proceso vivo trabajando.
   • ∙: proceso terminado pero resumible.
   • ✢: /loop en sleep entre iteraciones.




                                                    542                                  @soyenriquerocha
                                                                              AGENTES Y SUBAGENTES




Si tienes muchas sesiones, filtra con un prefijo:

   • a:<name> : filtra por nombre. Ejemplo: a:flaky-test .
   • s:<state> : filtra por estado. Ejemplo: s:working .
   • #<number> : filtra por número de PR.


Despachar sesiones desde agent view
Dentro de agent view tienes un prompt para lanzar nuevas sesiones. La sintaxis es flexible:

   • <agent-name> <prompt> : la primera palabra se interpreta como nombre de subagente, el resto
    como prompt. Ejemplo: code-reviewer revisa los cambios del último commit .
   • @<agent-name> en cualquier parte: garantiza que ese subagente corra.
   • @<repo> : apunta la sesión a un directorio o repo específico.
   • /<skill> : invoca un skill como tarea.
   • #<number> : selecciona una sesión asociada al PR con ese número.

Si escribes algo muy corto (menos de 4 caracteres) el sistema lo rechaza con 'Too short'. Escribe
descripciones de tarea, no saludos.

Cada sesión despachada se ejecuta automáticamente en su propio worktree. No te tienes que
preocupar por que se pisen los archivos: cada una vive en su rama.


Atajos dentro de agent view
Atajos esenciales:

   • Enter: hace attach a la sesión seleccionada (te metes a su terminal).
   • Space: hace peek (vista rápida del estado sin attach completo).
   • Ctrl+X: detiene la sesión seleccionada. Si presionas Ctrl+X dos veces en menos de 2 segundos,
    elimina la sesión y su worktree (incluyendo cambios sin commit). Útil pero peligroso: haz git
    push antes si quieres preservar trabajo.

   • Flecha izquierda en prompt vacío: backgroundea la sesión actual y vuelve a agent view. Es el
    equivalente desde dentro a salir sin matar.

A veces no quieres abrir el panel, solo controlar una sesión específica desde la terminal o un script.
Para eso hay subcomandos:

   • claude attach <id> : conecta a una sesión en background. Desconectas con flecha izquierda
    en prompt vacío.

   • claude logs <id> : imprime el output reciente de la sesión sin entrar.
   • claude stop <id> (alias claude kill <id> ): detiene la sesión.
   • claude respawn <id> : reinicia una sesión detenida con su conversación intacta. claude
    respawn --all reinicia todas.

   • claude rm <id> : elimina la sesión del listado y limpia su worktree si no tiene cambios sin

Limitaciones de agent view
Agent view es research preview. Antes de depender de él para trabajo crítico, ten en mente:

   • Las sesiones corren localmente. No son procesos en la nube. Si pones tu laptop a dormir o lo
    apagas, las sesiones se interrumpen. Al volver, aparecen como failed. Solución: claude respawn

    --all o haz attach/peek/reply a cualquiera para que el supervisor las reinicie desde donde

   • Requieren workspace trust. Antes de poder usar --worktree o agent view en un directorio,

Controles globales: slash commands, atajos, variables y settings

Esta sección agrupa todos los controles que aplican fuera de la definición de cada subagente:

Slash commands para background
Dos comandos clave que aparecen junto con agent view:

   • /bg [prompt] (alias /background ): manda la conversación actual al background. Aceptas un
    prompt opcional como última instrucción antes de soltarla. Ejemplo: /bg run the test suite

    subagentes y monitors que estuvieran corriendo no se transfieren al background; arrancan
    limpios.
   • /tasks : lista todas las tareas en background de la sesión actual (subagentes, monitors,
    comandos bash con run_in_background ). Útil para entender qué tienes corriendo antes de salir
    o de despachar más trabajo. Para la vista global de todas tus sesiones en background usa claude
    agents .

   • Ctrl+B: manda al background la tarea actualmente corriendo (un Bash en ejecución, un

Variables de entorno
Las variables relevantes a agentes y subagentes:

   • CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 : deshabilita todas las tareas en background.

    tasks dejan de tener sentido.

   • CLAUDE_CODE_DISABLE_AGENT_VIEW=1 : deshabilita agent view y los background agents. Útil si
    quieres forzar a tu equipo a no depender de la función mientras esté en research preview.

    requieren v2.1.117+.

       SendMessage (necesaria para reanudar subagentes).

   • CLAUDE_CODE_SUBAGENT_MODEL=<modelo> : sobreescribe el modelo de todos los subagentes
    para controlar costos globalmente. Ejemplo: CLAUDE_CODE_SUBAGENT_MODEL=haiku .

Settings relevantes
En tu settings.json (proyecto o usuario) puedes configurar:

   • agent : nombre del subagente que actuará como agente principal por defecto en cada sesión del
    proyecto. Ejemplo: { "agent": "code-reviewer" } . El flag --agent en CLI lo sobreescribe.
   • teammateMode : modo de display de teammates en agent teams. Valores: in-process , auto ,
    tmux . El default cambió de auto a in-process en v2.1.179, así que ahora los split panes hay
    que pedirlos explícitamente.
   • worktree.baseRef : desde qué ref hace branch al crear worktrees. Valores: fresh (default,
    branch desde origin/HEAD ) o head (branch desde tu HEAD actual).
   • disableAgentView : si es true , desactiva agent view y los background agents. Equivalente al
    env var CLAUDE_CODE_DISABLE_AGENT_VIEW .
   • cleanupPeriodDays : días antes de que se limpien los transcripts de subagentes y worktrees
    huérfanos. Default 30. Bájalo si tu ~/.claude/ crece rápido; súbelo si quieres conservar historial
    más tiempo. Ejemplo: { "cleanupPeriodDays": 14 } .
   • permissions.deny : array para bloquear subagentes específicos con la sintaxis
    Agent(<name>) .




Errores comunes y soluciones

Aquí tienes los problemas más frecuentes al trabajar con subagentes:

   • El subagente no se encuentra: si creaste el archivo manualmente después de iniciar la sesión,
    reinicia Claude Code o usa /agents para cargarlo.
   • El subagente no puede crear más subagentes: desde v2.1.172 los subagentes sí pueden anidar
    otros subagentes, pero hay un tope fijo de 5 niveles de profundidad. Un subagente en el nivel 5 ya
    no recibe la herramienta Agent. Si tocaste el tope, reorganiza el trabajo para que la cadena de
    delegación sea menos profunda, o lanza más subagentes desde un nivel superior.
   • Subagente en background falla por permisos: los subagentes en background auto-deniegan
    permisos no pre-aprobados. Reanúdalo en foreground con resume o pre-aprueba los permisos
    antes de lanzar.

  • El contexto principal se llena rápido: si usas muchos subagentes, sus resultados consumen
   contexto. Usa agent teams para trabajo que excede la ventana de contexto.
  • Conflictos de archivos en paralelo: múltiples subagentes editando el mismo archivo causan
