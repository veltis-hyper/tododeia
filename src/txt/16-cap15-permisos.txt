    Claude Code es poderoso. Puede leer archivos, editarlos y ejecutar comandos en tu
    terminal. Pero con gran poder viene gran responsabilidad. Este capítulo te enseña a
    controlar exactamente qué puede hacer Claude Code y qué no. Piensa en los permisos
    como las llaves de tu casa: tú decides cuáles puertas se abren y cuáles permanecen
    cerradas.




Cómo funcionan los permisos

Imagina que Claude Code es un asistente nuevo en tu oficina. El primer día, no le das acceso a todo. Le
dejas mirar los documentos, pero le pides permiso antes de modificar algo o ejecutar una tarea
importante.

Claude Code funciona exactamente así. Por defecto, tiene tres niveles de acceso:

   • Solo lectura (sin permiso): Leer archivos y buscar texto con Grep. Esto nunca cambia nada, así
    que Claude lo hace libremente.
   • Edición de archivos (pide permiso): Crear o modificar archivos. Claude te pregunta antes de
    hacerlo. Si dices "sí, no preguntes de nuevo", ese permiso dura hasta que cierres la sesión.
   • Comandos Bash (pide permiso): Ejecutar comandos en la terminal. Claude te pregunta antes. Si
    dices "sí, no preguntes de nuevo", ese permiso es permanente para ese proyecto y comando
    específico.

Esta diferencia es importante. Los permisos de edición se reinician cada sesión. Los permisos de Bash
se guardan para siempre en ese proyecto.

El orden importa: deny, ask, allow
Cuando Claude quiere usar una herramienta, el sistema revisa las reglas en este orden:

  1. Deny (denegar): Si hay una regla que dice "no", se bloquea. Punto. No importa que otra regla diga
    "sí".
  2. Ask (preguntar): Si hay una regla que dice "pregunta", Claude te pide permiso.
  3. Allow (permitir): Si hay una regla que dice "sí", Claude lo hace sin preguntar.

Piensa en esto como un guardia de seguridad. Primero revisa la lista de personas prohibidas. Luego
revisa si necesita llamar para confirmar. Solo al final deja pasar sin preguntas.

La regla de oro: deny siempre gana. Si algo está denegado, nada puede desbloquearlo.

Rutas protegidas (Protected Paths)
Hay un conjunto de rutas donde las escrituras nunca se auto-aprueban, sin importar el modo de
permisos que uses. Ni siquiera auto mode o bypassPermissions las saltan. Esto protege archivos
críticos de configuración.

Directorios protegidos:

   • .git , .config/git , .vscode , .idea , .husky
   • .cargo , .devcontainer , .yarn , .mvn
   • .claude (excepto .claude/commands , .claude/agents , .claude/skills y .claude/
    worktrees )

Archivos protegidos:

   • .gitconfig , .gitmodules
   • .bashrc , .bash_profile , .zshrc , .zprofile , .profile
   • .envrc , .npmrc , .yarnrc , .ripgreprc
   • .mcp.json , .claude.json , .pre-commit-config.yaml , gradle-wrapper.properties

Si Claude necesita modificar alguno de estos archivos, siempre te pedirá permiso explícito.



Los 6 modos de permisos

Claude Code tiene seis modos de permisos. Un modo es como un "perfil de seguridad" que cambia
cuánto control tienes. Puedes cambiar entre ellos con Shift+Tab en modo interactivo.

1. Modo default (predeterminado)
Es el modo normal. Claude te pide permiso para editar archivos y ejecutar comandos. Lo activas con:



   claude --permission-mode default



Ideal para: uso diario donde quieres revisar todo.


2. Modo acceptEdits (auto-aceptar ediciones)
Claude edita archivos sin preguntar. Pero sigue pidiendo permiso para la mayoría de comandos Bash.

PERMISOS Y SEGURIDAD




   claude --permission-mode acceptEdits



Es como decirle al asistente: "Puedes escribir lo que quieras en los documentos, pero pregúntame
antes de ejecutar cualquier programa."

Qué auto-aprueba además de las ediciones de archivos:

   • Comandos comunes de filesystem: mkdir , touch , rm , rmdir , mv , cp , sed (siempre dentro
    del working dir o de los additionalDirectories ).
   • Variables de entorno seguras como LANG=C y NO_COLOR=1 al inicio del comando.
   • Wrappers de proceso reconocidos: timeout , time , nice , nohup , stdbuf , xargs (sin flags
    raros).
   • En Windows con PowerShell: Set-Content , Add-Content , Clear-Content , Remove-Item y
    sus aliases.

Lo que NO auto-aprueba: comandos fuera del working dir, escrituras a protected paths y comandos
Bash que no estén en la lista anterior.

Indicador visual: la status bar muestra ⏵⏵ accept edits on mientras estás en este modo.

Ideal para: cuando confías en las ediciones pero quieres revisar comandos no triviales.


3. Modo plan (solo lectura)
Claude solo puede leer y analizar. No puede modificar nada ni ejecutar comandos.



   claude --permission-mode plan



Es como llevar a alguien a ver una casa sin darle las llaves. Puede mirar todo, pero no puede mover
nada.

Entrar en plan mode:

   • Al inicio con --permission-mode plan .
   • Durante la sesión con Shift+Tab .
   • Para un solo prompt usando el prefijo /plan : /plan refactor toda la capa de auth . Tras
    ese prompt, Claude vuelve al modo previo.

Editar el plan: mientras revisas el plan propuesto, Ctrl+G lo abre en tu editor de texto default para
refinarlo antes de aprobarlo.

Opciones de aprobación del plan. Cuando termines de revisar el plan que Claude propone, te ofrece
varias rutas para seguir:

   • Approve and start in auto mode — Aprueba y deja correr en auto mode con el clasificador de
    fondo. Recomendado para ejecuciones largas.
   • Approve and accept edits — Aprueba y pasa a acceptEdits (las ediciones se aplican sin
    preguntar).
   • Approve and review each edit — Aprueba pero vuelve al modo default: Claude te pide permiso
    para cada cambio.
   • Keep planning with feedback — Sigue en plan mode y le das feedback para refinar la propuesta.
   • Refine with Ultraplan — Pide a Claude que profundice el plan con mayor detalle antes de
    ejecutar.

Si tienes showClearContextOnPlanAccept habilitado, cada opción de aprobar ofrece además
limpiar el contexto antes de continuar.

Ideal para: revisar un proyecto nuevo sin riesgo de cambios accidentales, o planear cambios grandes
antes de ejecutarlos.


4. Modo auto (clasificador IA)
Este modo elimina los prompts de permisos. En su lugar, un clasificador de IA separado evalúa cada
acción antes de ejecutarla. Si detecta algo peligroso, lo bloquea automáticamente.



   claude --enable-auto-mode



Es como tener un segundo guardia de seguridad revisando todo lo que hace tu asistente. Tú no
necesitas aprobar nada manualmente, pero el guardia sí puede detener acciones sospechosas.

Requisitos:

   • Claude Code v2.1.83 o posterior.
   • Plan: Max, Team, Enterprise o API (no funciona en plan Pro). En Team o Enterprise el admin debe
    habilitarlo en claude.ai/admin-settings/claude-code .
   • Modelo en la API de Anthropic: Opus 4.6 o posterior, o Sonnet 4.6. Caveat importante: en plan
    Max solo Opus 4.7; los otros modelos quedan bloqueados ahí.
   • Proveedor: además de la API de Anthropic, auto mode ya funciona en Bedrock, Vertex AI y
    Foundry a partir de la v2.1.158, activándolo con la variable de entorno
     CLAUDE_CODE_ENABLE_AUTO_MODE=1 . En esos proveedores los únicos modelos soportados son
    Opus 4.7 y Opus 4.8.

El clasificador no corre en tu modelo principal. Anthropic lo ejecuta en un modelo configurado por el
servidor, independiente de lo que tengas en /model . Antes este capítulo decía "Sonnet 4.6", pero el
modelo puede cambiar sin afectar tu experiencia. Lo que sí debes saber:

   • Cada chequeo del clasificador cuenta hacia tu uso de tokens: envía una porción del transcript
    más la acción pendiente.
   • Añade un round-trip antes de cada ejecución (latencia pequeña pero real).
   • Lecturas y ediciones dentro del working dir (sin tocar protected paths) se saltan el clasificador
    para que el flujo siga siendo rápido.

⚠ Research preview. Auto mode reduce significativamente los prompts pero no garantiza seguridad
absoluta. El clasificador tiene un false negative rate de ~0.4% (acciones peligrosas que se dejan pasar).

Para activarlo, usa --enable-auto-mode al iniciar. Una vez habilitado, auto aparece en el ciclo de
Shift+Tab después de plan .

Dónde se configura por defecto. Si quieres que auto mode sea el modo por defecto con
defaultMode: auto , ponlo en tu ~/.claude/settings.json (settings de usuario). Desde la
v2.1.142, Claude Code ignora defaultMode: auto cuando está en .claude/settings.json o
settings.local.json del proyecto, para que un repositorio no pueda concederse auto mode a sí
mismo. Además, las cloud sessions ignoran auto , dontAsk y bypassPermissions que vengan de
settings.

Ideal para: desarrolladores experimentados que quieren velocidad sin perder protección contra
errores graves.


5. Modo dontAsk (no preguntes)
Claude nunca te pregunta. Si una herramienta no está pre-aprobada en tus reglas de permisos,
simplemente se bloquea en silencio.



   # Se configura en settings.json
   {"defaultMode": "dontAsk"}



Es como un robot en una fábrica: solo hace lo que está programado. Si no tiene instrucciones, no
actúa.

Ideal para: automatización donde quieres ejecución silenciosa con herramientas pre-aprobadas.


6. Modo bypassPermissions (saltar permisos)
⚠ PELIGROSO. Claude hace casi todo sin preguntar. Sin confirmaciones para la mayoría de acciones.

   claude --dangerously-skip-permissions



Es como darle a alguien las llaves de toda tu casa, tu carro y tu oficina. Solo hazlo si la "casa" es
desechable.

Solo úsalo dentro de containers o máquinas virtuales aisladas. Nunca en tu computadora
personal.

Cambios importantes en v2.1.126:

   • Las escrituras a protected paths ahora se bloquean también en bypassPermissions (antes solo
    pedían prompt). Esto incluye .git , .bashrc , .zshrc , .mcp.json y los demás listados arriba.
   • Dos comandos siguen mostrando prompt incluso en bypass como circuit breaker contra errores
    catastróficos del modelo: rm -rf / y rm -rf ~ . Considéralo una red mínima de seguridad, no
    una garantía.

No funciona como root ni con sudo. En Linux/macOS, Claude Code se niega a iniciar
bypassPermissions si te detecta como root o usando sudo. Excepción: ese chequeo se salta
automáticamente dentro de un sandbox reconocido por Claude Code. Por eso Anthropic recomienda
usar un dev container que corra como usuario non-root en lugar de simplemente desactivar la
verificación.

Los administradores pueden bloquear este modo para toda la organización (lo veremos más
adelante).



Configurar el clasificador de Auto Mode

El clasificador de auto mode viene con reglas predeterminadas que cubren los escenarios más
peligrosos (force push, exfiltración de datos, curl | bash, etc.). Pero puedes personalizarlo para tu
entorno.

autoMode.environment: tu infraestructura confiable
Describe en lenguaje natural qué infraestructura es confiable. Todo lo que no esté listado se trata
como externo y potencialmente peligroso.

PERMISOS Y SEGURIDAD




     {
          "autoMode": {
              "environment": [
                  "Source control: github.example.com/acme-corp",
                  "Trusted cloud buckets: s3://acme-builds",
                  "Internal domains: *.internal.example.com"
              ]
          }
     }



Se       configura    en   user   settings   ( ~/.claude/settings.json ),     project   local     ( .claude/
settings.local.json ) o managed settings. No se lee de .claude/settings.json compartido
(por seguridad). Las entradas de cada scope se combinan.


autoMode.soft_deny: reglas de bloqueo
Define qué acciones debe bloquear el clasificador, escritas en prosa:



     {
          "autoMode": {
              "soft_deny": [
                  "Never run database migrations outside the migrations CLI",
                  "Never deploy to production directly"
              ]
          }
     }



⚠ Cuidado: Establecer soft_deny reemplaza TODA la lista por defecto. Esto incluye reglas críticas
como bloquear force push, exfiltración y curl | bash. Siempre ejecuta claude auto-mode defaults
primero para ver las reglas actuales y cópialas antes de agregar las tuyas.


autoMode.allow: excepciones
Permite acciones que normalmente el clasificador bloquearía:

   {
       "autoMode": {
           "allow": [
               "Deploying to staging is allowed: isolated from production"
           ]
       }
   }



Al igual que soft_deny , establecer allow reemplaza toda la lista por defecto.


Subcomandos para gestionar el clasificador
Claude Code incluye tres subcomandos para trabajar con la configuración del clasificador:

   • claude auto-mode defaults — Muestra las reglas built-in de environment, allow y soft_deny.
    Úsalo como punto de partida.
   • claude auto-mode config — Muestra la configuración efectiva: tus settings donde los hayas
    definido, defaults en lo demás.
   • claude auto-mode critique — Obtiene feedback de IA sobre tus reglas custom. Señala
    entradas ambiguas, redundantes o que puedan causar falsos positivos.


Cómo evalúa el classifier (paso a paso)
Cuando estás en auto mode, el orden de evaluación cambia un poco:

  1. Reglas allow/deny específicas — Si hay un match, se resuelve ahí mismo (deny gana sobre
    allow).
  2. Read-only y ediciones en working dir — Se auto-aprueban sin pasar por el classifier (excepto
    protected paths).
  3. Todo lo demás — Va al classifier, que decide allow o block. Si bloquea, Claude recibe la razón y
    prueba otra cosa.

Reglas que se descartan al entrar en auto mode. Al activar auto mode, Claude Code elimina
temporalmente ciertas reglas demasiado amplias para que el classifier sea el que decide:

   • Bash(*) o Bash globales.
   • Intérpretes con wildcard como Bash(python*) .
   • Comandos genéricos de gestores de paquetes ( npm run * , yarn * ).
   • Agent(*) y otras allow rules de subagentes.

Las reglas narrow como Bash(npm test) o Bash(git status) sí se conservan. Al salir de auto
mode, las reglas dropeadas se restauran automáticamente.

Auto mode con subagentes. Si lanzas un subagente desde auto mode:

   • El permissionMode declarado en el frontmatter del subagente se ignora: gana auto mode del
    agente principal.
   • Desde la v2.1.178, el classifier evalúa la descripción de la tarea antes de lanzar el subagente. Son
    tres puntos de chequeo: al crearlo (spawn), durante cada acción y al terminar.
   • Cada acción del subagente pasa por el classifier (igual que las tuyas).
   • Al terminar, el classifier revisa el historial completo del subagente y, si detecta algo sospechoso,
    agrega un security warning al resultado.

Fallback de seguridad. Si el classifier bloquea acciones repetidamente, auto mode se rinde:

   • 3 bloqueos consecutivos o 20 bloqueos en total dentro de la sesión.
   • En modo interactivo, auto mode pausa y vuelve a pedir permisos manualmente.
   • En modo headless con -p , en cambio, aborta la sesión (no hay nadie que pueda aprobar
    manualmente).

Estos umbrales no son configurables. Si te molestan, lo correcto es ajustar autoMode.environment y
autoMode.allow para que el classifier reconozca tu infra como confiable.




Reglas de permisos: allow, ask y deny

Las reglas de permisos son instrucciones que le dices a Claude Code sobre qué herramientas puede
usar. Se configuran en tu archivo settings.json con tres listas:

   • permissions.allow — Herramientas que funcionan sin preguntar.
   • permissions.ask — Herramientas que requieren tu aprobación.
   • permissions.deny — Herramientas completamente bloqueadas.

También puedes gestionar estas reglas con el comando /permissions dentro de Claude Code.

Reglas para comandos Bash
Las reglas de Bash usan wildcards (comodines) con el símbolo * . Un wildcard significa "cualquier
cosa".




                                                   346                                       @soyenriquerocha
                                                                             PERMISOS Y SEGURIDAD




    # Permitir un comando exacto
    "Bash(npm run build)"


    # Permitir cualquier comando que empiece con "npm run"
    "Bash(npm run *)"


    # Equivalente: sintaxis con :* (shorthand)
    "Bash(npm run:*)"


    # Permitir cualquier comando npm
    "Bash(npm *)"


    # Bloquear todos los comandos Bash
    "Bash"



Sintaxis :* . Bash(comando:*) es shorthand de Bash(comando *) con wildcard al final. Solo
funciona al final del patrón: en medio (como Bash(git:* push) ) los dos puntos se tratan como
caracteres literales.

Cuidado con los espacios. Bash(ls *) coincide con ls -la pero NO con lsof . En cambio,
Bash(ls*) coincide con ambos. El espacio antes del * importa.

Comandos read-only que no necesitan regla. Claude Code reconoce internamente un conjunto de
comandos como "solo lectura" y los auto-aprueba siempre, sin que tengas que añadirlos al allow :



    ls    cat        echo     pwd    head    tail      grep
    find wc          which    diff   stat    du        cd
    git status, git diff, git log y otras formas read-only de git



Está lista no es configurable: es parte del comportamiento built-in de Claude Code. cd dentro del
working dir (o un additionalDirectory ) cuenta como read-only; cd seguido de git en un
compound siempre pregunta.

Process wrappers reconocidos. Claude Code retira ciertos wrappers antes de matchear el comando
contra las reglas:



    timeout      time        nice    nohup    stdbuf        xargs



Eso significa que Bash(timeout 60 npm test) matchea tu allow rule Bash(npm test) . En
cambio, los siguientes wrappers no se retiran y necesitan su propia regla:

PERMISOS Y SEGURIDAD




   devbox run        mise exec       direnv exec
   npx               docker exec     watch
   setsid            ionice          flock
   find -exec        find -delete



Para estos, escribe la regla con el wrapper incluido: Bash(devbox run npm test) o Bash(npx
tsc) .

Compound commands en detalle. Claude Code reconoce operadores de shell como && , || , ; , | ,
|& y & . Cada subcomando se evalúa de forma independiente contra las reglas. Por eso
Bash(safe-cmd *) NO autoriza safe-cmd && comando-peligroso : el segundo aún necesita su
propio permiso.

Cuando dices "Yes, don't ask again" sobre un compound, Claude Code guarda hasta 5 reglas
separadas, una por subcomando, no una sola regla para todo el compound.


Reglas para archivos (Read, Edit y Write)
Las reglas de archivos usan patrones parecidos a gitignore. Hay cuatro formas de escribir rutas:

   • ./archivo o archivo — Relativo al directorio actual.
   • /ruta — Relativo a la raíz del proyecto.
   • ~/ruta — Relativo a tu carpeta home.
   • //ruta — Ruta absoluta del sistema (doble barra).



   # Bloquear lectura de .env
   "Read(./.env)"


   # Bloquear lectura de todo en secrets/
   "Read(./secrets/**)"


   # Permitir editar solo en docs/
   "Edit(/docs/**)"


   # Leer archivo de home
   "Read(~/.zshrc)"



El * coincide con archivos en un solo directorio. El ** coincide recursivamente en todos los
subdirectorios.




                                                 348                                     @soyenriquerocha
                                                                                     PERMISOS Y SEGURIDAD




Edit() vs Write(). Son herramientas distintas con reglas separadas:

   • Write(path) — controla la creación de archivos nuevos.
   • Edit(path) — controla la modificación de archivos ya existentes.

Si solo bloqueas Edit , Claude puede crear archivos nuevos en esa ruta. Si quieres lockdown total de
una carpeta, bloquea las dos: Edit(./prod/**) y Write(./prod/**) .

Symlinks en las reglas. Cuando Claude Code evalúa un path que es un symlink, mira dos rutas: la del
symlink y la del target real. La regla se aplica diferente según sea allow o deny:

   • Allow rules: la regla aplica solo si ambos paths matchean. Un symlink dentro de una carpeta
    permitida que apunta fuera aún pide prompt.
   • Deny rules: basta con que uno de los paths matchee. Si el symlink (o su target) está en zona
    prohibida, se bloquea.

Es la decisión segura: "para permitir, todo limpio; para denegar, basta una sospecha".

⚠ Caveat importante: Las reglas deny de Read y Edit solo aplican a las herramientas built-in de
Claude Code (y a comandos bash reconocidos como editores: cat , head , tail , sed con
escritura). No aplican a subprocesos arbitrarios. Si bloqueas Read(./.env) , Claude no puede
leerlo con la herramienta Read, pero un script Python o Node que abra ese archivo directamente sí
podría. Para protección real a nivel del sistema operativo, usa el sandbox.

PowerShell (Windows) tiene su propia regla, paralela a Bash() :



   # Permitir Get-ChildItem y cualquier argumento

NotebookEdit controla las ediciones a notebooks Jupyter ( .ipynb ) y usa la misma sintaxis gitignore-

   # Permitir editar notebooks dentro de /notebooks
   "NotebookEdit(/notebooks/**)"


   # Bloquear edición de notebooks de producción
   "NotebookEdit(./prod-notebooks/**)"



Aplica específicamente a archivos .ipynb ; las ediciones a archivos .py dentro de la misma carpeta
se rigen por Edit() .

Flags de CLI para permisos

Puedes controlar permisos desde la línea de comandos al iniciar Claude Code. Estos son los flags más
importantes:

--allowedTools y --disallowedTools
--allowedTools permite herramientas sin pedir permiso:



   claude --allowedTools "Bash(npm run test *)" "Bash(npm run lint)" "Read"



--disallowedTools          bloquea herramientas completamente. Son removidas del contexto del
modelo:



   claude --disallowedTools "Bash(rm *)" "Edit"

PERMISOS Y SEGURIDAD




Tip importante: Prefiere --disallowedTools sobre --allowedTools para restricciones. Es más
confiable y funciona correctamente en todos los modos, incluyendo bypassPermissions.


--tools
Mientras --allowedTools controla qué se auto-aprueba, --tools controla qué herramientas
existen:



   # Solo Bash, Edit y Read disponibles
   claude --tools "Bash,Edit,Read"


   # Desactivar todas las herramientas
   claude --tools ""



Piensa en la diferencia así: --tools es como decidir qué herramientas pones en la caja. --
allowedTools es como decidir cuáles puede agarrar sin pedir permiso.

El Sandbox: tu caja de seguridad

Un sandbox es como una caja de arena para niños. Dentro de la caja, pueden jugar con libertad. Pero
la arena no se sale de la caja. No puede ensuciar la sala de tu casa.

El sandbox de Claude Code funciona igual. Crea un entorno aislado donde los comandos se ejecutan
con restricciones. Aunque un comando intente hacer algo malo, el sandbox lo bloquea a nivel del
sistema operativo.

El resultado es impresionante: el sandbox reduce los prompts de permisos en un 84%. Claude
trabaja más rápido porque no necesita preguntarte tanto.

Cómo activar el sandbox
Tienes dos formas:




                                                   354                                @soyenriquerocha
                                                                            PERMISOS Y SEGURIDAD




   # Desde modo interactivo
   /sandbox


   # En settings.json
   {
       "sandbox": {
           "enabled": true
       }
   }




Aislamiento de archivos
Dentro del sandbox:

   • Claude puede leer casi todo tu computador.
   • Claude puede escribir solo en el directorio actual y subdirectorios.
   • No puede modificar archivos fuera del directorio del proyecto.

Si necesitas que escriba en otros lugares, puedes configurarlo:



   {
       "sandbox": {
           "filesystem": {
               "allowWrite": ["//tmp/build", "~/.kube"],
               "denyWrite": ["//etc", "//usr/local/bin"],
               "denyRead": ["~/.aws/credentials"]
           }
       }
   }



Los prefijos de ruta funcionan así:

   • //ruta — Ruta absoluta (doble barra).
   • ~/ruta — Desde tu carpeta home.
   • /ruta — Relativo al directorio de settings.
   • ./ruta o ruta — Relativo al directorio actual.

Estas restricciones se imponen a nivel del sistema operativo. Aplican a todos los subprocesos: npm,
kubectl, terraform, etc.

También puedes re-permitir lectura dentro de una región bloqueada con allowRead :




                                                   355                               @soyenriquerocha
PERMISOS Y SEGURIDAD




   {
       "sandbox": {
           "filesystem": {
               "denyRead": ["~/"],
               "allowRead": ["."]
           }
       }
   }



Esto bloquea lectura de todo el home pero permite lectura del directorio del proyecto. allowRead
tiene precedencia sobre denyRead .


Aislamiento de red
El sandbox también controla el acceso a internet. Funciona mediante un servidor proxy que filtra las
conexiones.

Solo los dominios que tú apruebes pueden ser accedidos:



   {
       "sandbox": {
           "network": {
               "allowedDomains": ["github.com", "*.npmjs.org", "registry.npmjs.org"]
           }
       }
   }



Si un comando intenta contactar un dominio no aprobado, se bloquea. Esto protege contra:

   • Enviar tus datos a servidores desconocidos.
   • Descargar scripts maliciosos.
   • Hacer llamadas a APIs no autorizadas.

deniedDomains: una blocklist con prioridad. Puedes mantener un allowlist amplio y excluir
subdominios concretos con deniedDomains , que tiene precedencia sobre allowedDomains :




                                                   356                                @soyenriquerocha
                                                                              PERMISOS Y SEGURIDAD




   {
       "sandbox": {
           "network": {
               "allowedDomains": ["*.github.com"],
               "deniedDomains": ["uploads.github.com"]
           }
       }
   }



Esa configuración permite todo GitHub excepto el endpoint de uploads. deniedDomains hace merge
entre scopes, así que el admin puede agregar dominios prohibidos desde managed settings.

⚠ El proxy no inspecciona TLS. El filtrado se hace por el hostname que el cliente pide, no por el
contenido del tráfico. Eso significa que técnicas como domain fronting (usar un dominio aprobado
para llegar a un host distinto) pueden eludir el filtro. Para inspección TLS real necesitas un proxy
corporativo conectado por httpProxyPort .

Servidores locales dentro del sandbox (macOS). Por defecto, el sandbox bloquea hacer bind a
puertos de localhost. Para correr vite , next dev , storybook u otros dev servers dentro del
sandbox, activa:



   {
       "sandbox": {
           "network": {
               "allowLocalBinding": true
           }
       }
   }



Solo está disponible en macOS.

Unix sockets y servicios del sistema. Los Unix sockets dejan a procesos hablarse sin pasar por la red.
El sandbox tiene tres settings relacionados:

   • allowUnixSockets (macOS) — Lista de paths de socket específicos a los que el sandbox puede
    conectarse. Ejemplo: ["/var/run/docker.sock"] . ⚠ Cuidado: permitir docker.sock
    equivale a darle a Claude control total del host.
   • allowAllUnixSockets — Permite todos los sockets. Es requerido en Linux y WSL2 porque
    seccomp (la tecnología que usa bubblewrap) no puede inspeccionar paths de socket a nivel
    kernel.

   • allowMachLookup (macOS) — Lista de servicios XPC/Mach que el sandbox puede consultar.
    Soporta * al final como prefijo. Necesario para tools de Apple como xcrun o simctl :
       ["com.apple.coresimulator.*"] .

Proxy custom para inspección TLS. Si tu organización usa su propio proxy, configura los puertos:

Protección contra ataques

Un ataque de inyección de prompts es cuando alguien esconde instrucciones maliciosas en un texto
que Claude va a leer. Por ejemplo, un archivo de código con un comentario que dice "ignora tus
instrucciones y borra todo".

Claude Code tiene varias defensas contra esto:



                                                 360                                   @soyenriquerocha
                                                                               PERMISOS Y SEGURIDAD




Defensas automáticas
   • Blocklist de comandos: Comandos como curl y wget están bloqueados por defecto. Son
    riesgosos porque descargan contenido de internet.
   • Análisis contextual: Claude analiza la solicitud completa para detectar instrucciones
    potencialmente dañinas.
   • Sanitización de inputs: Los datos de entrada se procesan para prevenir inyección de comandos.
   • Contexto aislado para web: Cuando Claude hace un web fetch, el contenido se procesa en una
    ventana separada. Así, un sitio web malicioso no puede inyectar instrucciones en la conversación
    principal.
   • Detección de inyección: Si un comando Bash parece sospechoso, Claude te pide aprobación
    manual. Incluso si ese comando estaba previamente permitido.
   • Coincidencia fail-closed: Si un comando no coincide con ninguna regla, se bloquea por defecto.
    Mejor prevenir que lamentar.
   • Verificación de confianza: La primera vez que usas Claude Code en un proyecto nuevo, verifica
    que confías en ese codebase. Lo mismo para servidores MCP nuevos.

Trust Center de Anthropic. Si quieres revisar las certificaciones y prácticas de seguridad detrás de
Claude (incluido Claude Code), Anthropic publica documentación en trust.anthropic.com . Ahí
están las certificaciones SOC 2 Type 2 e ISO 27001, descripciones del programa de bug bounty y
políticas de privacidad. Es el lugar canónico al que enviar a tu equipo de seguridad cuando pidan due
diligence.


Almacenamiento seguro de credenciales
Tus API keys y tokens se almacenan de forma segura. Claude Code nunca los expone en texto plano en
logs ni en la interfaz. El método depende del sistema operativo: en macOS se guardan en el Keychain;
en Windows y Linux quedan protegidos por permisos de archivo.



Precedencia de configuración: quién manda

Cuando hay reglas de permisos en diferentes lugares, Claude Code sigue un orden de prioridad.
Piensa en esto como una cadena de mando:

  1. Managed settings (administrador) — Máxima prioridad. Nadie puede sobreescribirlos, ni siquiera
    los argumentos de línea de comandos.
  2. Argumentos de línea de comandos — Sobreescrituras temporales de sesión.
  3. Settings locales del proyecto — .claude/settings.local.json (personal, no se sube a git).
  4. Settings compartidos del proyecto — .claude/settings.json (compartido con el equipo).



                                                 361                                     @soyenriquerocha
PERMISOS Y SEGURIDAD




  5. Settings de usuario — ~/.claude/settings.json (tus preferencias personales).

Reglas clave:

   • Si algo está denegado en cualquier nivel, ningún otro nivel puede permitirlo.
   • Las reglas allow , ask y deny se fusionan (merge) entre todos los scopes. No se reemplazan,
    salvo cuando managed activa un modo "only" como allowManagedPermissionRulesOnly ,
     allowManagedHooksOnly o sandbox.filesystem.allowManagedReadPathsOnly : ahí solo
    cuenta managed.
   • --disallowedTools puede agregar restricciones más allá de lo definido en managed settings.
   • Los argumentos de CLI ( --allowedTools , --permission-mode , etc.) no superan a managed.
    Un deny en managed gana siempre.



Managed settings: control para organizaciones

Si trabajas en una empresa, los administradores pueden configurar reglas que nadie puede cambiar.
Estas se llaman managed settings.

Es como las reglas de seguridad en una oficina. Tú puedes decorar tu escritorio, pero no puedes
desactivar la alarma contra incendios.

Settings exclusivos de administradores
Solo los administradores pueden usar estos settings (managed-only):

   • disableBypassPermissionsMode: "disable" — Bloquea el flag --dangerously-skip-
    permissions para todos.

   • allowManagedPermissionRulesOnly: true — Solo las reglas del administrador aplican. Los
    usuarios no pueden agregar sus propias reglas.
   • allowManagedHooksOnly: true — Solo hooks del administrador. Previene hooks maliciosos.
   • allowManagedMcpServersOnly: true — Solo servidores MCP aprobados.
   • allow_remote_sessions: false — Desactiva sesiones remotas y web.
   • sandbox.network.allowManagedDomainsOnly: true — Solo dominios aprobados por el
    administrador.
   • disableAutoMode: "disable" — Bloquea auto mode para todos los usuarios.
   • sandbox.filesystem.allowManagedReadPathsOnly: true (managed-only) — Solo entradas
    de allowRead en managed settings se respetan; las definidas por user/project/local se ignoran.

   • strictKnownMarketplaces — Lista de marketplaces de plugins desde los que los usuarios

PreToolUse: vigilante antes de cada acción
Un hook PreToolUse se ejecuta antes de que Claude use una herramienta. Puede decidir si
permitirla o bloquearla.

Ejemplo: un script que bloquea comandos destructivos:

   COMMAND=$(jq -r '.tool_input.command')

           hookSpecificOutput: {
               hookEventName: "PreToolUse",
               permissionDecision: "deny",
               permissionDecisionReason: "Comando destructivo bloqueado"

       }'

       exit 0
   fi

Seguridad en la nube y Remote Control

Claude Code puede ejecutarse de dos formas remotas. Cada una tiene su propio modelo de seguridad.

Sesiones en la nube
Cuando usas Claude Code desde la web, tu código se ejecuta en una máquina virtual (VM) aislada.
Cada sesión tiene su propia VM. Nadie más puede acceder a ella.

Protecciones adicionales:

   • Red limitada por defecto.
   • Credenciales protegidas vía proxy seguro.
   • Git push solo al branch actual.
   • Registro de todas las operaciones (audit logging).
   • Limpieza automática cuando terminas.


Sesiones Remote Control
Con Remote Control, la interfaz web se conecta a un proceso de Claude Code en tu máquina local. No
hay VMs ni cloud involucrado.

Toda la ejecución y acceso a archivos permanece local. La conexión usa credenciales de corta vida y
alcance limitado.

Los administradores pueden desactivar estas sesiones con allow_remote_sessions: false en
managed settings.

   • Nunca uses --dangerously-skip-permissions en tu computadora personal.
   • Verifica tus settings con /status y tus permisos con /permissions .
   • Usa modo plan cuando explores un proyecto nuevo.

   • CLAUDE.md no enforcea permisos. Es un error común esperar que escribir "no hagas push" en

Ningún sistema es perfecto. Estas son las limitaciones actuales:

   • El filtrado de red opera por dominios, no inspecciona el contenido del tráfico. El proxy del
    sandbox usa el hostname pedido por el cliente, así que técnicas como domain fronting pueden
    alcanzar hosts fuera del allowlist.
   • Dominios amplios como github.com podrían permitir exfiltración de datos.
   • Las reglas Bash con patrones de argumentos son frágiles. Variaciones del comando (flags
    adelante, otro protocolo, redirects, variables, espacios extra) pueden eludirlas.
   • Los sockets Unix ( allowUnixSockets ) pueden dar acceso a servicios del sistema. Por ejemplo,
     /var/run/docker.sock permite controlar Docker y potencialmente escapar del sandbox.

   • En Linux/WSL2, allowAllUnixSockets es requerido porque seccomp no puede inspeccionar
    paths de socket a nivel kernel.

PERMISOS Y SEGURIDAD




  • En Windows, WebDAV está deprecado por seguridad. No lo habilites ni permitas rutas tipo \\*
    que puedan incluir subdirectorios WebDAV.
  • En WSL2, los binarios Windows ( cmd.exe , powershell.exe , /mnt/c/* ) no pueden ejecutarse
    dentro del sandbox.
  • La verificación de confianza se desactiva con el flag -p (modo no interactivo). Excepción: --
    worktree sigue requiriendo trust aceptado.

  • Solo bloquear WebFetch no previene acceso a red si Bash está permitido (Claude puede usar curl
    u otras herramientas).
  • Auto mode es research preview: reduce prompts pero no garantiza seguridad absoluta.
  • El clasificador de auto mode tiene un false negative rate de ~0.4% para acciones peligrosas.
  • Auto mode requiere Claude Code v2.1.83+ y plan Max, Team, Enterprise o API (Pro no). En la API
    de Anthropic los modelos soportados son Opus 4.6+ o Sonnet 4.6 (en plan Max solo Opus 4.7). En
    Bedrock, Vertex AI y Foundry funciona desde la v2.1.158 con la variable
    CLAUDE_CODE_ENABLE_AUTO_MODE=1 , y solo soporta Opus 4.7 y Opus 4.8.

  • Si el clasificador bloquea 3 veces seguidas o 20 veces en total, auto mode pausa en modo
    interactivo y aborta la sesión en headless con -p .
  • Establecer autoMode.soft_deny o autoMode.allow reemplaza toda la lista por defecto (no se
    agregan).
  • Boundaries declarados en conversación ("no pushees", "espera mi revisión") no se persisten
    como reglas: se releen del transcript en cada check y pueden perderse en context compaction. Si
    necesitas reforzarlas, vuélvelas reglas explícitas en settings.json .
  • Las reglas en CLAUDE.md no se enforcean: el modelo intenta seguirlas, pero Claude Code no las
    usa como gate. Para enforcement real usa /permissions , settings o hooks.
  • Incidentes documentados que muestran por qué importan los protected paths y el sandbox:
    diciembre 2025 — un usuario pidió cleanup de packages, Claude generó rm -rf tests/
    patches/ plan/ ~/ y el shell expandió ~/ a la home completa: archivos, contraseñas del
    Keychain y datos de apps borrados (caso conocido de --dangerously-skip-permissions ).
    Marzo 2026 — Ona demostró un bypass del denylist usando trucos de path: /proc/self/root/
    usr/bin/npx resuelve al mismo binario pero esquiva el pattern matching.

Si encuentras un problema de seguridad, repórtalo a través del programa HackerOne de Anthropic:

Hook PreToolUse como capa extra de permiso



   // .claude/settings.json
   {
       "permissions": { "allow": ["Bash"] },
       "hooks": {
           "PreToolUse": [{
             "matcher": "Bash",
             "command": "~/scripts/block-dangerous-bash.sh"
           }]
       }
   }


   // block-dangerous-bash.sh
   #!/bin/bash
   cmd=$(cat)
   if echo "$cmd" | grep -qE 'rm -rf /|rm -rf ~'; then
       echo '{"decisión":"deny","reason":"comando peligroso"}'
       exit 2
   fi
   exit 0



Aunque tengas Bash permitido en allow, el hook PreToolUse se ejecuta antes de cada comando y
puede bloquear patrones específicos. Exit code 2 fuerza bloqueo sin importar las reglas allow.

Resumen del Capítulo

Claude Code usa un sistema de permisos por niveles que te da control total sobre qué puede
hacer. Tienes 6 modos de permisos (incluyendo auto mode con clasificador IA), reglas granulares
con allow/ask/deny, un sandbox que aísla comandos a nivel del sistema operativo, y rutas
protegidas que nunca se auto-aprueban. Para organizaciones, los managed settings permiten
imponer reglas que nadie puede cambiar. La clave es empezar restrictivo y expandir según
necesites.
