    Claude Code es muy poderoso por sí solo. Pero imagina que pudiera hablar con GitHub,
    Notion, tu base de datos, Slack y cientos de herramientas más. Eso es exactamente lo
    que hace MCP: el Model Context Protocol. En este capítulo vas a aprender qué es MCP,
    cómo conectar servidores a Claude Code, cuáles son los más populares y cómo crear el
    tuyo propio.




Qué es MCP (Model Context Protocol)

Piensa en tu teléfono. Tiene un puerto USB-C. Con ese único puerto puedes conectar cargadores,
audífonos, memorias USB y pantallas externas. No necesitas un puerto diferente para cada cosa.

MCP (Model Context Protocol) funciona igual, pero para aplicaciones de IA. Es un estándar abierto
que permite conectar Claude Code con sistemas externos. Un solo protocolo para conectarse a todo:
GitHub, bases de datos, Slack, Notion y más.

Sin MCP, cada integración necesitaría su propio conector especial. Con MCP, todos hablan el mismo
idioma.

Cómo funciona: la arquitectura
MCP tiene tres participantes principales. Piensa en un restaurante:

   • MCP Host: Es el restaurante completo. En nuestro caso, es Claude Code. Coordina todo.
   • MCP Client: Es el mesero. Claude Code crea un mesero dedicado para cada servicio externo. El
    mesero va y viene entre tú y la cocina.
   • MCP Server: Es la cocina. Es el programa externo que hace el trabajo real: consultar GitHub, leer
    archivos, buscar en Slack.

Cuando abres Claude Code y tienes 3 servidores MCP configurados, Claude Code crea 3 clientes
(meseros). Cada uno habla exclusivamente con su servidor (cocina).


Qué ofrecen los servidores MCP
Un servidor MCP puede ofrecer tres tipos de cosas:

  1. Tools (Herramientas): Acciones que Claude puede ejecutar. Ejemplo: "crear un issue en GitHub",
    "enviar un mensaje en Slack", "consultar la base de datos". Claude decide cuándo usarlas.
  2. Resources (Recursos): Datos de solo lectura. Ejemplo: el contenido de un archivo, un documento
    de Notion, un issue de GitHub. Se referencian con @servidor:recurso .

  3. Prompts: Plantillas de instrucciones reutilizables. Aparecen como comandos tipo /
    mcp__github__pr_review .

El camino también va al revés. El cliente (Claude Code) puede ofrecer sus propias primitivas para que
el servidor le pida cosas a él. Las tres principales son:

   • Sampling: el servidor le pide al cliente que ejecute una completion del LLM (vía sampling/
    createMessage ). Así un servidor puede usar un modelo de IA sin tener que cargar su propio SDK
    ni gestionar claves de API.
   • Elicitation: el servidor le pide información al usuario a mitad de una tarea. Lo cubrimos en detalle
    más adelante en este capítulo.
   • Logging: el servidor envía mensajes de log al cliente para debug y monitoreo.

También existe una primitiva utilitaria experimental llamada Tasks: permite ejecución durable, es
decir, lanzar una operación costosa o de varios pasos, seguir su estado y recuperar el resultado más
tarde sin tener que esperar bloqueado. Al ser experimental, puede cambiar.


Cómo se comunican: los transportes
El cliente y el servidor necesitan un canal para hablar. MCP ofrece dos opciones:

   • stdio (local): Claude Code lanza el servidor como un programa en tu computadora. Se comunican
    directamente, sin internet. Es rápido y seguro. Ideal para herramientas locales.
   • HTTP (remoto): El servidor vive en internet. Claude Code le envía peticiones HTTP. Ideal para
    servicios en la nube como GitHub o Notion.

Existe un tercer transporte llamado SSE, pero está deprecado (obsoleto). Si lo ves en algún tutorial
viejo, usa HTTP en su lugar.

Hay un cuarto transporte, WebSocket ( ws ), que Claude Code soporta pero es poco común. Tiene tres
limitaciones que conviene conocer: solo se configura a mano en                      .mcp.json     o con
claude mcp add-json (no funciona con el flag --transport ), y solo se autentica por headers (no
soporta OAuth). Para la mayoría de casos, stdio o HTTP son mejores opciones.



Configurar servidores MCP en Claude Code

Configurar un servidor MCP es como instalar una app en tu teléfono. Le dices a Claude Code: "quiero
conectarme a este servicio" y listo.

El comando principal es claude mcp add . Veamos cómo usarlo.

Agregar un servidor remoto (HTTP)
Para servicios en la nube como GitHub, Notion o Sentry. Es la opción más común:



   claude mcp add --transport http github https://api.githubcopilot.com/mcp/



Desglose del comando:

   • claude mcp add : agrega un nuevo servidor
   • --transport http : usa conexión por internet
   • github : el nombre que le das al servidor (tú eliges)
   • https://... : la dirección del servidor

Muchos servidores remotos necesitan autenticación. Después de agregar el servidor, escribe /mcp
dentro de Claude Code. Verás la opción de autenticarte con OAuth (login via navegador).


Agregar un servidor local (stdio)
Para herramientas que corren en tu propia computadora:



   claude mcp add --transport stdio filesystem -- npx -y @modelcontextprotocol/
   server-filesystem /ruta/al/directorio



Nota el doble guion ( -- ). Es muy importante. Todo lo que va antes del doble guion son opciones para
Claude Code. Todo lo que va después es el comando que arranca el servidor.

Otro ejemplo con variables de entorno:



   claude mcp add --transport stdio --env AIRTABLE_API_KEY=tu_clave airtable --
   npx -y airtable-mcp-server



Aquí --env le pasa la API key al servidor. Puedes usar --env varias veces si necesitas múltiples
variables.


Regla de oro: el orden importa
Este es un error muy común. Todas las opciones ( --transport , --env , --scope , --header ) van
antes del nombre del servidor. Mira la estructura:

    claude mcp add [opciones] nombre-servidor [-- comando args]



Correcto:



    claude mcp add --transport http --scope project paypal https://
    mcp.paypal.com/mcp



Incorrecto (va a fallar):



    claude mcp add paypal --transport http https://mcp.paypal.com/mcp




Dónde se guarda la configuración: scopes
Cuando agregas un servidor, Claude Code lo guarda en un archivo. Pero tienes tres opciones de dónde
guardarlo:

   • local (por defecto): Solo para ti, solo en este proyecto. Se guarda en ~/.claude.json . Perfecto
    para configuraciones personales.
   • project: Compartido con tu equipo via git. Se guarda en .mcp.json en la raíz del proyecto.
    Todos los miembros del equipo tendrán acceso.
   • user: Solo para ti, pero en todos tus proyectos. Se guarda en ~/.claude.json . Ideal para
    herramientas que usas siempre.

Para elegir el scope, usa --scope :



    claude mcp add --transport http --scope project paypal https://
    mcp.paypal.com/mcp



Si hay servidores con el mismo nombre en diferentes scopes, la prioridad es: local > project > user.

Headers dinámicos con headersHelper
Algunos entornos corporativos usan autenticación que no es OAuth: Kerberos, SSO interno o tokens
de corta vida. Para estos casos existe headersHelper .

En tu .mcp.json , en vez de poner headers estáticos, defines un comando shell que genera los
headers en tiempo real:



   {
       "mcpServers": {
           "api-interna": {
               "type": "http",
               "url": "https://mcp.internal.example.com",
               "headersHelper": "/opt/bin/get-mcp-auth-headers.sh"
           }
       }
   }



El script debe escribir un objeto JSON de pares clave-valor a stdout. Ejemplo de lo que debe imprimir:



   {"Authorization": "Bearer eyJhbG..."}



Reglas importantes:

   • El comando tiene un timeout de 10 segundos. Si tarda más, falla.
   • Los headers dinámicos sobreescriben headers estáticos con el mismo nombre.
   • Se ejecuta fresco en cada conexión (al iniciar sesión y al reconectar).
   • El script recibe las variables de entorno CLAUDE_CODE_MCP_SERVER_NAME y
       CLAUDE_CODE_MCP_SERVER_URL .

Cargar configuración MCP desde la línea de comandos
Puedes cargar servidores MCP desde archivos JSON al iniciar Claude Code, sin necesidad de
configurarlos previamente:



   claude --mcp-config ./mcp.json



Acepta múltiples archivos separados por espacio. Los servidores se agregan a los que ya tengas
configurados.

Si quieres que Claude Code use exclusivamente los servidores de ese archivo (ignorando cualquier
otra configuración MCP), usa --strict-mcp-config :



   claude --strict-mcp-config --mcp-config ./mcp.json



Esto es muy útil para entornos controlados, CI/CD o cuando quieres asegurarte de que solo se usen
servidores específicos.


Reconexión automática cuando un servidor se cae
Las conexiones de red fallan. Un servidor HTTP puede desconectarse por un reinicio, una caída
momentánea o un timeout. Claude Code intenta reconectarse solo, así que no tienes que estar
pendiente.

Cómo funciona la reconexión para servidores HTTP y SSE:

   • Hasta 5 intentos con backoff exponencial: 1s, 2s, 4s, 8s y 16s entre cada intento.
   • Mientras reconecta, el servidor aparece como pending en /mcp .
   • Si los 5 intentos fallan, queda marcado como failed y tienes que reintentar manualmente
    desde /mcp .

Desde v2.1.121, la conexión inicial también reintenta hasta 3 veces cuando hay errores transitorios
(códigos 5xx, connection refused, timeout). Antes, un fallo inicial significaba rendirse al primer intento.

Hay errores que no reintentan, porque indican un problema de configuración que ningún reintento va
a arreglar:

   • 401 o 403 (autenticación o permisos): hay que reautenticar o ampliar scopes.
   • Not found: la URL está mal.

Autenticación: conectarte de forma segura

Muchos servidores remotos necesitan saber quién eres antes de dejarte entrar. Hay varias formas de
autenticarte.

OAuth: login con tu navegador
La forma más común. Funciona así:

  1. Agregas el servidor: claude mcp add --transport http github https://
       api.githubcopilot.com/mcp/

  2. Dentro de Claude Code, escribes /mcp
  3. Seleccionas "Authenticate" junto al servidor
  4. Se abre tu navegador. Haces login como siempre.
  5. El navegador te redirige de vuelta. Listo.

Los tokens se guardan de forma segura. Se refrescan solos. No tienes que volver a autenticarte cada
vez.

Dos detalles útiles del flujo OAuth en Claude Code:

   • offline_access automático: si el servidor anuncia el scope offline_access en su
       scopes_supported , Claude Code lo añade solo a la petición. Eso permite obtener un refresh
       token y renovar credenciales sin que tengas que volver a hacer login cuando expira el access
       token.
   • Descubrimiento vía WWW-Authenticate: si el servidor responde con el header WWW-
       Authenticate apuntando al authorization server, Claude Code lo usa para descubrir
       automáticamente la metadata OAuth. No tienes que configurar authServerMetadataUrl a
       mano cuando el servidor lo soporta.

Excepción importante: algunos conectores hospedados por Anthropic —Microsoft 365, Gmail y
Google Calendar— no soportan el login OAuth local desde Claude Code. Para usarlos tienes que
conectarlos primero en claude.ai , en Settings → Connectors (disponible desde la v2.1.162). Una vez
conectados ahí, aparecen en Claude Code como servidores de claude.ai.


Bearer token o API key en headers
Algunos servidores usan tokens directos. Los pasas con --header :

   claude mcp add --transport http mi-api https://api.example.com/mcp --header
   "Authorization: Bearer tu-token-aqui"



O con una API key:



   claude mcp add --transport http privado https://api.company.com/mcp --header
   "X-API-Key: tu-clave"




OAuth avanzado: credenciales pre-configuradas
Algunos servidores no soportan registro automático de OAuth. Si ves el error "does not support
dynamic client registration", necesitas registrar tu app manualmente:

  1. Ve al portal del servicio y registra una app OAuth
  2. Obtendrás un client ID y un client secret
  3. Usa ambos al agregar el servidor:



   claude mcp add --transport http --client-id tu-id --client-secret --
   callback-port 8080 mi-server https://mcp.example.com/mcp



El flag --client-secret te pedirá el secreto de forma segura (no se muestra en pantalla). El secreto
se guarda en el keychain del sistema, no en archivos de texto.

Para automatización (CI/CD), pasa el secreto via variable de entorno:



   MCP_CLIENT_SECRET=tu-secreto claude mcp add --transport http --client-id tu-
   id --client-secret mi-server https://mcp.example.com/mcp




El archivo .mcp.json: compartir servidores con tu equipo

Cuando usas --scope project , la configuración se guarda en un archivo llamado .mcp.json en la
raíz de tu proyecto. Este archivo se puede subir a git para que todo tu equipo use los mismos
servidores.

Formato del archivo
Así se ve un .mcp.json típico:



   {
       "mcpServers": {
           "github": {
               "type": "http",
               "url": "https://api.githubcopilot.com/mcp/"
           },
           "db": {
               "command": "npx",
               "args": ["-y", "@bytebase/dbhub", "--dsn", "postgresql://
   user:pass@host:5432/db"],
               "env": {}
           }
       }
   }



Cada servidor tiene un nombre ("github", "db") y su configuración. Los servidores HTTP tienen type
y url . Los servidores stdio tienen command , args y opcionalmente env .

Nota: el valor type: "streamable-http" es un alias de type: "http" . Existe por compatibilidad
con la especificación oficial de MCP. Si ves cualquiera de los dos en un tutorial, hacen exactamente lo
mismo.

Cada servidor también acepta un campo timeout (en milisegundos): es el límite duro de tiempo
que puede tardar cada llamada a una herramienta de ese servidor antes de cortarse. Por ejemplo,
para darle 10 minutos a una tool pesada:



   {
       "mcpServers": {
           "reportes": {
               "type": "http",
               "url": "https://mcp.example.com/mcp",
               "timeout": 600000
           }
       }
   }



Detalles importantes del campo timeout :

   • Es por tool call, no por sesión. Mide tiempo de reloj real (wall-clock).

MCP SERVERS




   • Valores menores a 1000 ms se ignoran (se considera que es un error de configuración).
   • Las notificaciones de progreso que envíe el servidor no extienden el límite: si pasa el tiempo, se
    corta aunque el servidor siga reportando avance.
   • Sobreescribe, solo para ese servidor, el valor global de MCP_TOOL_TIMEOUT (ver más adelante).


Variables de entorno en .mcp.json
No quieres poner tus claves secretas en un archivo que va a git. Para eso existen las variables de
entorno:



   {
       "mcpServers": {
           "api-server": {
               "type": "http",
               "url": "${API_BASE_URL:-https://api.example.com}/mcp",
               "headers": {
                   "Authorization": "Bearer ${API_KEY}"
               }
           }
       }
   }



La sintaxis ${VAR} se reemplaza por el valor de la variable. Si agregas :-valor , ese es el valor por
defecto cuando la variable no existe.

Ejemplo: ${API_BASE_URL:-https://api.example.com} usa la variable API_BASE_URL si existe.
Si no, usa https://api.example.com .

Cuidado: si una variable no está definida y no tiene valor por defecto, Claude Code no podrá leer el
archivo y dará error.


alwaysLoad: forzar la carga al inicio
Por defecto, Tool Search difiere la carga de las herramientas de un servidor: solo aparecen cuando
Claude las busca. Eso ahorra contexto, pero a veces quieres que un servidor concreto esté siempre
disponible desde el primer turno.

Para eso existe alwaysLoad: true a nivel de servidor:




                                                  462                                      @soyenriquerocha
                                                                                          MCP SERVERS




   {
       "mcpServers": {
           "github": {
               "type": "http",
               "url": "https://api.githubcopilot.com/mcp/",
               "alwaysLoad": true
           }
       }
   }



Con esto, todas las herramientas de github se cargan al iniciar la sesión sin pasar por Tool Search.
Ideal para servidores con pocas herramientas que usas en cada turno.

Detalles importantes:

   • Requiere Claude Code v2.1.121+.
   • Bloquea el startup hasta que el servidor conecte (timeout de 5 segundos), incluso si tienes
    activado MCP_CONNECTION_NONBLOCKING=1 . Esto pasa porque las tools tienen que estar listas
    antes del primer prompt.
   • Si solo quieres que una herramienta específica se cargue siempre (y dejar las demás en Tool
    Search), el autor del servidor puede marcarla con _meta.anthropic/alwaysLoad: true en la
    definición de esa tool.


Bloque oauth en .mcp.json
Además de configurar OAuth con flags desde la línea de comandos, puedes ponerlo directamente en
.mcp.json con un objeto oauth :




                                                  463                                     @soyenriquerocha
MCP SERVERS




   {
       "mcpServers": {
           "slack": {
               "type": "http",
               "url": "https://mcp.slack.com/mcp",
               "oauth": {
                   "clientId": "tu-client-id",
                   "callbackPort": 8080,
                   "scopes": "channels:read chat:write",
                   "authServerMetadataUrl": "https://auth.example.com/.well-known/
   openid-configuration"
               }
           }
       }
   }



Subcampos disponibles:

   • clientId : el client ID OAuth pre-registrado en el portal del servicio. Útil para servidores que no
    soportan registro dinámico.
   • callbackPort : puerto fijo para el redirect ( http://localhost:PORT/callback ). Debe
    coincidir con el que registraste en el portal.
   • scopes : lista de scopes separados por espacios (formato RFC 6749). Ejemplo: "channels:read
    chat:write search:read" .

   • authServerMetadataUrl : URL https con la metadata del authorization server (típicamente
    termina en .well-known/openid-configuration ). Requiere Claude Code v2.1.64+.

Lo bueno de tenerlo en .mcp.json : la configuración OAuth se comparte con tu equipo via git. Cada
miembro hace su propio login con /mcp , pero no tienen que conocer los detalles de configuración.

Tool Search: carga inteligente de herramientas

Si tienes muchos servidores MCP, podrías tener cientos de herramientas disponibles. Cargar todas al
mismo tiempo desperdicia la ventana de contexto (la cantidad de texto que Claude puede procesar a
la vez).

Tool Search resuelve esto. Es como un índice en un libro: en vez de leer todo el libro para encontrar
algo, consultas el índice primero.

Cómo funciona
Tool Search está activado por defecto en Claude Code. Las herramientas MCP se difieren (solo se
cargan sus nombres al inicio) y Claude las busca cuando las necesita. Funciona así:

  1. Las herramientas MCP no se cargan todas al inicio
  2. Cuando Claude necesita una herramienta, busca en el índice
  3. Solo carga las herramientas que realmente necesita

Resultado: Claude usa su memoria de forma mucho más eficiente.




                                                  467                                  @soyenriquerocha
MCP SERVERS




Configurar Tool Search
Usa la variable de entorno ENABLE_TOOL_SEARCH :

   • true (por defecto en hosts first-party) — Siempre activado. Las herramientas se difieren y Claude
    las busca cuando las necesita.
   • auto — Se activa cuando las herramientas exceden el 10% del contexto

Anthropic. Si usas Claude via Vertex AI, el requisito sube a Sonnet 4.5+ u Opus 4.5+ (las versiones

Servidor MCP en Python paso a paso
Paso 1: Instala las herramientas necesarias.

   from mcp.server.fastmcp import FastMCP

   claude mcp add --transport stdio mi-clima -- uv run server.py

Regla crítica: nunca escribas a stdout
Si tu servidor usa transporte stdio, hay una regla que no puedes romper: nunca escribas a stdout.

¿Por qué? Porque stdout es el canal que MCP usa para enviar mensajes. Si tu código hace un
print("debug") en Python, ese texto se mezcla con los mensajes MCP y todo se rompe.

En Python, usa stderr :



   import sys
   print('mensaje de debug', file=sys.stderr)



O usa la librería logging , que escribe a stderr por defecto.

Variables de entorno para MCP

Claude Code tiene varias variables de entorno que controlan el comportamiento de MCP:

   • MCP_TIMEOUT=10000 — Timeout de arranque del servidor en milisegundos (ej: 10 segundos). Es
    cuánto espera Claude Code a que el servidor conecte al iniciar.
   • MCP_TOOL_TIMEOUT=600000 — Timeout de ejecución de herramientas en milisegundos: cuánto
    puede tardar una sola llamada a una tool MCP antes de cortarse. Por defecto es muy alto
    (alrededor de 28 horas), así que en la práctica casi nunca se alcanza. Ojo: no confundir con
     MCP_TIMEOUT , que es solo el arranque; este es por cada llamada. Puedes sobreescribirlo para un
    servidor concreto con el campo timeout de .mcp.json (ver la sección del archivo .mcp.json).
   • MAX_MCP_OUTPUT_TOKENS=50000 — Límite máximo de tokens en la salida de herramientas MCP
    (por defecto: 25,000)
   • ENABLE_TOOL_SEARCH=auto:5 — Controla Tool Search (ver sección anterior)
   • ENABLE_CLAUDEAI_MCP_SERVERS=false — Deshabilita servidores MCP que vienen de Claude.ai.
    Por defecto los servidores configurados en claude.ai/settings/connectors están
    disponibles automáticamente, pero solo si el método de autenticación activo es tu suscripción
    de Claude.ai. Si estás usando una ANTHROPIC_API_KEY , un ANTHROPIC_AUTH_TOKEN , un
     apiKeyHelper o un proveedor de terceros (Bedrock o Vertex), estos conectores no se cargan.

   • MCP_CLIENT_SECRET=secreto — Pasa el secreto OAuth en CI/CD sin prompt interactivo
   • MCP_CONNECTION_NONBLOCKING=1 — Por defecto está en 0 . Si lo pones en 1 , los servidores

MCP para empresas: control centralizado

Si eres administrador de IT, necesitas controlar qué servidores MCP pueden usar tus empleados. Hay
dos opciones:

Control exclusivo con managed-mcp.json
Creas un archivo managed-mcp.json en el directorio del sistema:

   • macOS: /Library/Application Support/ClaudeCode/managed-mcp.json
   • Linux/WSL: /etc/claude-code/managed-mcp.json
   • Windows: C:\Program Files\ClaudeCode\managed-mcp.json

Cuando este archivo existe, los usuarios no pueden agregar sus propios servidores. Solo pueden usar
los que tú defines. Es como poner un candado: tú eliges qué herramientas están disponibles.

El formato es idéntico al .mcp.json estándar.

Si quieres ser menos restrictivo, puedes dejar que los usuarios agreguen servidores pero limitar

   • deniedMcpServers — Lista de servidores prohibidos

Cada entrada puede restringir por nombre ( serverName ), comando exacto ( serverCommand ) o

Enterprise-Managed Authorization (EMA): OAuth centralizado
Conectar cada servicio uno por uno con OAuth funciona, pero en una empresa grande es un dolor de
cabeza: cada empleado tiene que hacer login en cada conector, y el equipo de IT no controla quién
accede a qué.

Enterprise-Managed Authorization (EMA) resuelve esto. Desde el 18 de junio de 2026 es una
funcionalidad estable para los planes Team y Enterprise. La idea es zero-touch OAuth: la autorización
se gestiona de forma centralizada desde tu identity provider (el sistema que ya usa tu empresa para
manejar identidades y accesos), en vez de que cada persona autorice los conectores a mano.

En la práctica, esto significa que un administrador define una sola vez qué conectores MCP puede usar
la organización, y los empleados los tienen disponibles sin tener que pasar por el flujo de login de
cada uno. Funciona igual en Claude chat, Claude Code y Cowork.

El primer identity provider soportado es Okta, a través de un estándar llamado Cross App Access (XAA).
Los conectores compatibles con EMA al momento del lanzamiento son: Asana, Atlassian, Canva,
Figma, Granola, Linear y Supabase. El soporte para Slack está en camino.

Si administras IT en una empresa que ya usa Okta, EMA es la forma recomendada de darle acceso
seguro a estos conectores a todo tu equipo sin que cada persona tenga que autenticarse por su
cuenta.

Seguridad: lo que debes saber

MCP es poderoso, pero con poder viene responsabilidad. Aquí van las reglas de seguridad:

   • Servidores de terceros no están verificados por Anthropic. Úsalos bajo tu propio riesgo.
   • Cuidado con prompt injection: servidores que obtienen contenido de internet pueden inyectar
    instrucciones maliciosas.
   • Aprobación de project-scoped: Claude Code te pide permiso antes de usar servidores definidos
    en .mcp.json de un proyecto.
   • Secretos seguros: los tokens OAuth se guardan en el keychain del sistema, nunca en texto plano.
   • Rota tokens cada 90 días como buena práctica.
   • Usa variables de entorno para claves, nunca las pongas directamente en archivos de
    configuración.

Errores comunes y cómo solucionarlos

Estos son los problemas que más aparecen al trabajar con MCP:

   • "Connection closed" en Windows: Los servidores stdio con npx necesitan el wrapper cmd /c .
    Solución: claude mcp add --transport stdio mi-server -- cmd /c npx -y @some/
    package

   • "spawn claude ENOENT": Al usar Claude Code como servidor, claude no está en el PATH.
    Solución: usa which claude para encontrar la ruta completa.
   • "does not support dynamic client registration": El servidor no permite OAuth automático.
    Solución: registra tu app manualmente y usa --client-id y --client-secret .
   • "Failed to parse .mcp.json": Una variable de entorno no está definida. Solución: define la
    variable o agrega un valor por defecto con ${VAR:-default} .
   • Timeout al arrancar servidor: El servidor tarda mucho en iniciar. Solución: MCP_TIMEOUT=10000
    claude

   • "stdout corruption": Tu servidor stdio escribe a stdout. Solución: usa stderr para logs y
    mensajes de debug.
   • Output excede límite de tokens: La respuesta del servidor es muy grande. Solución:
    MAX_MCP_OUTPUT_TOKENS=50000 claude o configura el servidor para paginar.

   • "Warning: server name workspace is reserved": Definiste un servidor MCP llamado
    workspace , pero ese nombre está reservado para uso interno de Claude Code. El servidor se
    ignora con ese warning. Solución: renómbralo en .mcp.json (o donde lo hayas definido) a
    cualquier otro nombre.
   • Descripciones de tools truncadas en la respuesta: Claude Code trunca a 2KB tanto las
    descripciones de cada tool como las server instructions. Si tu descripción es más larga, el final
    desaparece. Solución: pon los detalles críticos al principio del texto y deja los ejemplos extensos
    para el final (o para un recurso aparte).
   • La conexión falla en vez de caer a OAuth: configuraste un header Authorization (por ejemplo
    en headers de .mcp.json ) con un token que el servidor rechaza. Cuando hay un header de
    autorización presente, Claude Code lo usa y reporta la conexión como fallida en lugar de intentar
    el flujo OAuth. Solución: verifica que el token sea válido para ese endpoint MCP, o quita el header
    para que Claude Code use OAuth automáticamente.
   • No sé si el problema es de un servidor MCP o de otra cosa: arranca Claude Code con el flag --
    safe-mode . Desactiva todas las personalizaciones de golpe (CLAUDE.md, plugins, skills, hooks y
    servidores MCP) y te deja una sesión limpia. Si el problema desaparece en modo seguro, sabes
    que viene de alguna de tus personalizaciones; ve reactivándolas para encontrar la culpable. Es la
    herramienta más rápida para aislar problemas de MCP.
