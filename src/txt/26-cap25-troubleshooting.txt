Errores de la API: qué significan y cómo resolverlos

Cuando algo falla en la API de Claude, recibes un código de error HTTP. Piensa en estos códigos como
las luces del tablero de un carro. Cada luz te dice algo diferente.

Todos los errores vienen en formato JSON con esta estructura:



   {
       "type": "error",
       "error": {
         "type": "invalid_request_error",
         "message": "Descripción del problema"
       },
       "request_id": "req_abc123"
   }



El campo request_id es super importante. Es como el número de ticket en una tienda. Si necesitas
pedir ayuda al soporte de Anthropic, incluye este ID. Así encuentran tu caso al instante.

Errores del lado del cliente (tú los causas)
Estos errores significan que algo en tu solicitud está mal. Es como enviar una carta con la dirección
equivocada: el correo no la puede entregar.

   • 400 - invalid_request_error: Tu solicitud tiene algo mal. Puede ser un parámetro inválido, un
    JSON mal formado, o una función que el modelo no soporta. Por ejemplo, varios modelos ya no
    aceptan prefilled responses (respuestas pre-llenadas) en el último turno del asistente: Opus
    4.8/4.7/4.6, Sonnet 4.6, Fable 5 y Mythos 5.
   • 401 - authentication_error: Tu API key tiene un problema. Puede estar expirada, mal escrita, o
    simplemente no la configuraste. El 85% de los errores al empezar vienen de aquí.

   • 402 - billing_error: Hay un problema con tu facturación o pago. Puede ser que tus créditos se
    agotaron, tu tarjeta fue rechazada, o los datos de pago están vencidos. Revisa tus detalles de pago
    en la Console ( platform.claude.com ).
   • 403 - permission_error: Tu API key es válida, pero no tiene permiso para lo que intentas hacer.
    Revisa tu suscripción o el rol asignado en la Console.
   • 404 - not_found_error: El recurso no existe. Probablemente escribiste mal el nombre del modelo
    o el endpoint.
   • 413 - request_too_large: Tu solicitud pesa demasiado. Los límites son: Messages API 32 MB,
    Batch API 256 MB, Files API 500 MB.

Regla de oro: Estos errores (excepto el 429) NO se solucionan reintentando. Tienes que arreglar tu
solicitud primero.


Error 429: te pasaste del límite de velocidad
El error 429 es especial. Significa que estás enviando demasiadas solicitudes demasiado rápido. Es
como cuando un restaurante está lleno y te dicen "espera unos minutos".

Hay dos razones por las que puedes recibir un 429:

  1. Excediste tus límites de tasa: Mandaste más solicitudes por minuto (RPM), más tokens de
    entrada por minuto (ITPM), o más tokens de salida por minuto (OTPM) de lo que tu tier permite.
  2. Límites de aceleración: Aumentaste el tráfico muy de golpe. Aunque no hayas pasado tu límite, el
    cambio brusco puede disparar esta protección.

Cada respuesta 429 incluye un header retry-after . Este te dice exactamente cuántos segundos
esperar. Úsalo siempre que esté disponible.


Errores del lado del servidor (no es tu culpa)
A veces el problema no eres tú. Es Claude.

   • 500 - api_error: Algo falló internamente en los servidores de Anthropic. Reintenta con backoff
    exponencial.
   • 504 - timeout_error: El request expiró durante el procesamiento. Es típico en respuestas largas o
    con un max_tokens alto sin usar streaming: la conexión se mantiene abierta tanto tiempo que la
    red la corta antes de terminar. Ojo: este error NO se resuelve reintentando a ciegas (volver a
    mandar el mismo request largo lo más probable es que falle igual). La solución es usar el
    streaming del Messages API, y para procesos que pueden tardar más de 10 minutos, preferir el
    Message Batches API.

   • 529 - overloaded_error: Los servidores están saturados por alto tráfico general. Este código no es
    estándar de HTTP — es exclusivo de Anthropic. No tiene que ver con tus límites; es un problema
    de capacidad global.

Para el 500 y el 529: reintenta, pero hazlo con inteligencia (más sobre esto en la sección de estrategias
de reintento). Para el 504, no reintentes igual — cambia a streaming o Batches.



Estrategias de reintento: no martilles la puerta

Cuando un error es reintentable, no lo reintentes inmediatamente. Imagina que 100 personas tocan la
puerta al mismo tiempo. Si todas vuelven a tocar al segundo, el problema empeora.

La solución se llama exponential backoff con jitter. Suena complicado, pero es simple:

   • Exponential backoff: Cada reintento espera el doble que el anterior. Primero 1 segundo, luego 2,
    luego 4, luego 8...
   • Jitter: Agrega un poquito de tiempo aleatorio. Así, si 100 personas reintentaron al mismo tiempo,
    no vuelven todas juntas.

La fórmula es: delay = (2 ** intento) + random(0, delay * 0.1)

Qué errores reintentar y cuáles no
Esta tabla es tu guía rápida:

   • SÍ reintentar: 429 (rate limit), 500 (error interno), 529 (sobrecarga)
   • NO reintentar: 400 (solicitud inválida), 401 (autenticación), 402 (facturación), 403 (permisos), 404
    (no encontrado), 413 (muy grande)

Piensa en ello así: si el problema es del servidor o de la velocidad, reintenta. Si el problema es tuyo,
arregla la solicitud.


El patrón circuit breaker para producción
Si tu aplicación está en producción, necesitas algo más robusto. El circuit breaker funciona como un
interruptor eléctrico automático en tu casa.

Tiene tres estados:

  1. Cerrado (normal): Todo funciona. Las solicitudes pasan normalmente.
  2. Abierto (pausa): Demasiados errores seguidos. El circuito se abre y deja de enviar solicitudes por
    un rato. Esto evita que empeores el problema.
  3. Semi-abierto (prueba): Después de la pausa, envía una solicitud de prueba. Si funciona, vuelve
    al estado cerrado. Si falla, vuelve a abierto.

Límites de tasa: cuánto puedes pedir por minuto

Los rate limits (límites de tasa) controlan cuánto puedes usar la API en un período de tiempo. Piensa
en ellos como el límite de velocidad en una carretera. Existen para que todos los usuarios tengan
acceso justo.

Se miden en tres unidades:

   • RPM: Requests Per Minute. Cuántas solicitudes puedes hacer por minuto.
   • ITPM: Input Tokens Per Minute. Cuántos tokens de entrada puedes enviar por minuto.
   • OTPM: Output Tokens Per Minute. Cuántos tokens de salida puede generar Claude por minuto.

Anthropic usa un algoritmo llamado token bucket. Imagina un balde que se llena con gotas de agua
constantemente. Cada solicitud saca agua del balde. Si el balde se vacía, tienes que esperar a que se
vuelva a llenar. Pero no se llena de golpe — se va llenando gota a gota.

Para equipos que usan Claude Code, es útil planificar cuánta capacidad necesitas por persona. Estas
son las recomendaciones aproximadas de TPM (tokens por minuto) y RPM por usuario según el
tamaño del equipo:

   • 1-5 usuarios: 200K-300K TPM/usuario, 5-7 RPM/usuario
   • 5-20 usuarios: 100K-150K TPM/usuario, 2.5-3.5 RPM/usuario
   • 20-50 usuarios: 50K-75K TPM/usuario, 1.25-1.75 RPM/usuario
   • 50-100 usuarios: 25K-35K TPM/usuario, 0.62-0.87 RPM/usuario
   • 100-500 usuarios: 15K-20K TPM/usuario, 0.37-0.47 RPM/usuario

A medida que el equipo crece, la demanda simultánea se diluye. Los números más bajos por persona
son suficientes porque no todos están activos al mismo tiempo.

El avance de tier es automático. Cuando depositas lo suficiente, subes de nivel al instante. Los límites

    defecto, para empresas grandes.


Los headers que te dicen cuánto te queda
Cada respuesta de la API incluye headers que te dicen tu situación actual. Son como el medidor de
gasolina de tu carro:

   • anthropic-ratelimit-requests-remaining — Cuántas solicitudes te quedan.
   • anthropic-ratelimit-tokens-remaining — Cuántos tokens te quedan (redondeado al
    millar).
   • anthropic-ratelimit-requests-reset — Cuándo se repondrá tu límite de solicitudes.
   • anthropic-ratelimit-tokens-reset — Cuándo se repondrá tu límite de tokens.

También hay headers separados para input y output tokens: anthropic-ratelimit-input-tokens-
remaining y anthropic-ratelimit-output-tokens-remaining .

Monitorea estos valores en tu código. Si ves que te estás acercando al límite, reduce la velocidad antes
de recibir un 429.


El truco del cache: multiplica tus límites
Aquí va un secreto muy útil. Los tokens que Claude lee desde cache ( cache_read_input_tokens ) no
cuentan para tus límites de ITPM en la mayoría de los modelos.

¿Qué significa esto en la práctica? Si tu límite de ITPM es 2 millones y tienes un cache hit rate del 80%,
puedes procesar hasta 10 millones de tokens por minuto. Los 8 millones cacheados son "gratis" en
términos de rate limit.

Es como un carril exclusivo en la autopista. Los tokens cacheados viajan por ese carril y no causan
tráfico.

Google Vertex AI), así que en la práctica el truco del cache te beneficia en casi todos los casos.



Troubleshooting de Claude Code

Claude Code tiene sus propios problemas típicos. La buena noticia: la mayoría se resuelven rápido.
Empecemos con el comando mágico que diagnostica casi todo.

Escribe /doctor dentro de Claude Code. Este comando revisa automáticamente:

   • Tu versión y tipo de instalación
   • Si la búsqueda funciona bien
   • Si el auto-update está activo
   • Si hay errores en archivos de settings (JSON malformado)
   • Si hay problemas con servidores MCP
   • Si los keybindings están configurados correctamente
   • Si estás usando demasiado contexto

Es como llevar tu carro al mecánico para una revisión general. Ejecútalo siempre que algo no funcione
bien.

Otros comandos útiles para diagnosticar problemas:

   • /context — Te muestra qué está consumiendo espacio en tu ventana de contexto. Ideal para
    saber por qué Claude se está poniendo lento.
   • /stats — Muestra tus patrones de uso (disponible para suscriptores Pro/Max).
   • /feedback — Reporta problemas directamente a Anthropic sin salir de Claude Code.
   • /mcp — Lista los servidores MCP configurados. Útil para desactivar los que no estés usando.

Si necesitas más detalle, ejecuta Claude Code con el flag --debug . Esto habilita un output verbose
que muestra detalles de las solicitudes API, logs de hooks y diagnósticos internos. Es muy útil cuando
necesitas reportar un bug.

Errores de instalación
Los problemas de instalación son los más frustrantes porque ni siquiera puedes empezar a usar
Claude. Aquí van los más comunes:

"command not found: claude"

Claude se instaló, pero tu terminal no sabe dónde está. Necesitas agregar su ubicación al PATH:

   # En zsh (macOS default)
   echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc


   # En bash (Linux default)
   echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc



"Killed" durante instalación en Linux

Tu computadora no tiene suficiente memoria. Claude Code necesita al menos 4 GB de RAM. Solución:
agrega swap space (memoria virtual):



   sudo fallocate -l 2G /swapfile
   sudo chmod 600 /swapfile
   sudo mkswap /swapfile
   sudo swapon /swapfile



Error de TLS o SSL

Tus certificados de seguridad están viejos, o un proxy corporativo está interfiriendo:



   # Actualizar certificados
   sudo apt-get install ca-certificates


   # Para proxies corporativos
   export NODE_EXTRA_CA_CERTS=/ruta/al/certificado-corporativo.pem



Instalación colgada en Docker

Si instalas como root en el directorio raíz ( / ), el instalador escanea todo el sistema de archivos. Usa
WORKDIR /tmp en tu Dockerfile antes del instalador. Y aumenta la memoria: docker build --
memory=4g .

"Error loading shared library" (Linux)

Esto ocurre cuando hay un mismatch entre la variante del binario instalado y la libc de tu sistema
(musl vs glibc). Para verificar cuál usa tu sistema:



   # Ver qué libc tienes
   ldd /bin/ls



Si tu sistema usa glibc pero tienes el binario de musl (o viceversa), reinstala con el método correcto
para tu distribución. En Alpine Linux, instala las dependencias necesarias: apk add libgcc
libstdc++ ripgrep .

"Illegal instruction" (Linux)

El binario descargado no coincide con la arquitectura de tu CPU (por ejemplo, un binario x86 en un
procesador ARM, o una CPU antigua que no soporta las instrucciones requeridas). Verifica tu
arquitectura con uname -m . Si no coincide, reporta el problema en GitHub o prueba instalando con
Homebrew: brew install --cask claude-code .

Problemas de rendimiento
Alto uso de CPU o memoria

Si Claude Code se pone lento, probablemente el contexto está lleno. Usa /compact para comprimir la
conversación. Cierra y reinicia entre tareas grandes. Agrega carpetas de build pesadas a .gitignore .

Búsqueda lenta en WSL

Leer archivos entre el sistema de Windows y Linux es lento. Mueve tu proyecto al filesystem de Linux
( /home/ ) o usa Claude Code nativo en Windows.

Search, @file, agentes y skills no funcionan

Falta ripgrep, una herramienta de búsqueda rápida que Claude Code necesita:



   # macOS
   brew install ripgrep


   # Ubuntu/Debian
   sudo apt install ripgrep


   # Alpine
   apk add ripgrep




Optimización de costos: gasta menos, logra más

Usar la API de Claude cuesta dinero. Pero hay formas inteligentes de reducir la factura sin sacrificar
calidad. Piensa en esto como optimizar el consumo de gasolina de tu carro.

Prompt caching: ahorra hasta 90%
El prompt caching es la técnica más poderosa para ahorrar. Funciona así: si mandas el mismo
contenido repetidamente (un system prompt largo, un documento, definiciones de herramientas),
Claude lo guarda en cache. La segunda vez que lo lee, cuesta solo el 10% del precio original.

Hay dos tipos de cache:

   • Cache de 5 minutos: Escribir cuesta 1.25x del precio base. Se amortiza con una sola lectura.
   • Cache de 1 hora: Escribir cuesta 2x del precio base. Se amortiza con dos lecturas.

Es ideal para: system prompts, documentos grandes de contexto, definiciones de herramientas, e
historial de conversación.


Batch API: 50% de descuento
Si tu tarea no es urgente, usa la Batch API. Envías un lote de solicitudes y Claude las procesa dentro de
las siguientes 24 horas. A cambio, pagas la mitad.

Es perfecta para: evaluaciones masivas, procesamiento de datos, tareas de clasificación, y cualquier
cosa que no necesite respuesta inmediata.

Y lo mejor: puedes combinar Batch API con prompt caching para ahorrar aún más.


Elige el modelo correcto para cada tarea
No uses un camión para ir al supermercado. Cada modelo tiene su precio:

   • Haiku 4.5: $1/$5 por millón de tokens (input/output). Rápido y barato. Perfecto para clasificación,
    tareas simples, y alto volumen.
   • Sonnet 4.6: $3/$15 por millón de tokens. El equilibrio entre calidad y costo. Para la mayoría de
    tareas.
   • Opus 4.8: $5/$25 por millón de tokens. Máxima capacidad. Para tareas que realmente lo
    necesitan.

Un tip clave: si tus solicitudes superan los 200K tokens de entrada, el precio sube al doble para input y
1.5x para output. Intenta mantener tus solicitudes por debajo de ese límite.

Ojo con el fast mode de Opus 4.8. Si lo activas, los precios son $10/$50 por millón de tokens (input/
output). Eso es aproximadamente 2x el precio estándar de Opus (antes, en Opus 4.6 y 4.7, era 6x más
caro: $30/$150). Es útil cuando necesitas la máxima velocidad, pero asegúrate de que realmente lo
necesitas antes de habilitarlo.

Otros costos que debes conocer:

   • Web search: $10 por cada 1,000 búsquedas, más el costo normal de tokens por el contenido de
    los resultados.
   • Code execution: $0.05 por hora por container, después de 1,550 horas gratuitas al mes. Es gratis
    cuando se usa junto con web search o web fetch.

Controla cuánto piensa Claude
El parámetro effort controla cuánto "piensa" Claude antes de responder. Para tareas simples, no
necesita pensar tanto.

   • low: Piensa poco. Ideal para tareas de alto volumen o cuando la velocidad importa más.
   • medium: El punto medio. Bueno para la mayoría de aplicaciones con Sonnet.
   • high: Piensa mucho. Para problemas complejos de razonamiento.
   • max: Piensa al máximo. Para los problemas más difíciles.

Bajar el effort reduce los tokens de "thinking", lo que significa menos costo y menos latencia.


Gestión de contexto en Claude Code
En Claude Code, cada token que se acumula en la conversación cuesta dinero. Aquí van las prácticas
para mantener el contexto limpio:

   • /clear — Limpia todo entre tareas no relacionadas. Es gratis y te ahorra tokens.
   • /compact — Comprime la conversación sin perder lo importante. Puedes darle instrucciones
    específicas de qué conservar.
   • Subagentes — Delega investigaciones a subagentes. Ellos trabajan en su propio contexto y no
    llenan el tuyo.
   • /btw — Para preguntas rápidas que no necesitan quedarse en el historial.
   • CLAUDE.md conciso — Un CLAUDE.md de 200+ líneas gasta tokens en cada mensaje. Mantenlo
    corto y relevante.

Estrategias avanzadas para reducir contexto:

   • Hooks de preprocesamiento: Puedes configurar hooks que filtren output verboso antes de que
    Claude lo vea. Por ejemplo, un hook que filtre los logs de tests para mostrar solo los failures en vez
    de las 10,000 líneas completas. Esto puede reducir el contexto de decenas de miles de tokens a
    solo unos cientos.
   • Mover instrucciones a skills: CLAUDE.md se carga en cada sesión, pero las skills solo se cargan
    on-demand cuando las invocas. Si tienes instrucciones para workflows específicos, muévelas a
    skills y mantén CLAUDE.md bajo 200 líneas.
   • Preferir CLI tools sobre MCP servers: Herramientas como gh , aws , gcloud y sentry-cli
    son más eficientes en términos de contexto. Los MCP servers agregan definiciones de
    herramientas al contexto; las CLI tools no.

Anti-patrones: errores que todos cometen

Un anti-patrón es algo que parece buena idea pero en realidad te perjudica. Estos son los más
comunes al usar Claude.

Anti-patrones de sesión en Claude Code
La sesión "cocina" (kitchen sink)

Empiezas pidiendo que arregle un bug. Luego preguntas algo de otro proyecto. Luego vuelves al bug.
El contexto se llena de ruido irrelevante y Claude pierde el hilo.

Solución: Usa /clear entre tareas no relacionadas. Cada tarea merece una conversación limpia.

Corrección repetitiva

Claude hace algo mal. Lo corriges. Sigue mal. Lo corriges otra vez. El contexto se llena de intentos
fallidos y Claude se confunde más.

Solución: Después de dos correcciones fallidas, ejecuta /clear . Escribe un prompt mejor que
incorpore lo que aprendiste de los intentos anteriores.

Exploración infinita

Le pides a Claude que "investigue" algo sin delimitar el alcance. Claude lee cientos de archivos y llena
todo el contexto con información.

Solución: Delimita tus pedidos. O mejor aún, usa subagentes para investigar. Así el contexto principal
queda limpio.

CLAUDE.md sobre-especificado

Tu CLAUDE.md tiene 500 líneas de instrucciones. Claude ignora la mitad porque las reglas importantes
se pierden entre el ruido.

Solución: Poda sin piedad. Si Claude ya hace algo correctamente sin la instrucción, bórrala.

Enviar demasiado código

Los desarrolladores pegan 10-50x más código del que Claude necesita ver. Copian archivos enteros
cuando Claude solo necesita una función o una sección. Esto llena el contexto de ruido y hace que
Claude pierda el foco.

Solución: Extrae solo las secciones relevantes. Sé específico sobre qué archivo y qué función necesita
atención. Usa @archivo:línea para referenciar puntos exactos.

Anti-patrones de código y prompts
La brecha de confianza

Claude genera código que se ve razonable, pero no maneja casos extremos. Tú lo aceptas sin verificar.

Solución: Siempre proporciona formas de verificación: tests, scripts, screenshots. Si no puedes
verificarlo, no lo despliegues.

Sobre-ingeniería

Claude (especialmente Opus) tiende a crear archivos extra, abstracciones innecesarias, y flexibilidad
que nadie pidió.

Solución: Agrega esta instrucción: "Avoid over-engineering. Only make changes that are directly
requested or clearly necessary."

Hard-coding para pasar tests

Claude puede enfocarse demasiado en hacer pasar los tests, usando workarounds en lugar de
soluciones generales.

Solución: Especifica: "Write a high-quality, general-purpose solution. Do not hard-code values that
only work for specific test inputs."

Alucinaciones en código

Claude puede hablar sobre código que no ha leído, inventando funciones o estructuras.

Solución: Instrucción clave: "Never speculate about code you have not opened. If the user references a
file, read it before answering."


Anti-patrones al usar la API
Reintentar errores de cliente

Reintentar un error 400 o 401 es como golpear una puerta cerrada con llave. Por más que insistas, no
se va a abrir. Solo reintenta errores 429, 500 y 529.

Thundering herd (manada estampida)




                                                    722                                 @soyenriquerocha
                                                            TROUBLESHOOTING Y MEJORES PRÁCTICAS




Cuando múltiples clientes reciben un error al mismo tiempo y todos reintentan juntos, crean una
avalancha que empeora todo.

Solución: El jitter. Agrega tiempo aleatorio a cada reintento para que no todos lleguen al mismo
tiempo.

Solicitudes largas sin streaming

Si configuras max_tokens alto sin usar streaming, la red puede cortar la conexión antes de que
Claude termine.

Solución: Usa la API de streaming o la Batch API para solicitudes que puedan tardar más de 10
minutos.

Prefilled responses en los modelos nuevos

Si intentas usar respuestas pre-llenadas del asistente con Opus 4.8/4.7/4.6, Sonnet 4.6, Fable 5 o
Mythos 5, recibirás un error 400. Estos modelos ya no las soportan.

Solución: Usa structured outputs, instrucciones en el system prompt, o output_config.format .



Mejores prácticas: lo que hacen los expertos

Estas prácticas vienen directamente de los equipos de Anthropic y de desarrolladores con miles de
horas usando Claude. No son teóricas — están probadas en producción.

Mejores prácticas de prompting
1. Sé claro y directo

Claude es como un empleado brillante pero nuevo. No tiene tu contexto. En vez de "Crea un
dashboard", di "Crea un dashboard de analytics con gráficos de línea para ventas diarias y una tabla de
los 10 productos más vendidos".

2. Da contexto y motivación

En vez de "NUNCA uses elipsis", di "Tu respuesta será leída por un motor de texto a voz que no sabe
pronunciar elipsis".

3. Usa ejemplos (few-shot)

3 a 5 ejemplos bien hechos mejoran drásticamente la precisión. Envuélvelos en tags <examples> y
<example> .

4. Estructura con tags XML




                                                 723                                     @soyenriquerocha
TROUBLESHOOTING Y MEJORES PRÁCTICAS




Los tags XML eliminan ambigüedad. Usa tags como <instructions> , <context> , <input> .
Claude los entiende perfectamente.

5. Dale un rol

Una sola línea en el system prompt cambia el tono y enfoque: "You are a helpful coding
assistant specializing in Python."

6. Pon los datos largos al inicio

Coloca documentos grandes arriba, instrucciones en medio, y tu pregunta al final. Esto puede mejorar
el rendimiento hasta un 30%.

7. Di qué hacer, no qué NO hacer

En vez de "No uses markdown", di "Tu respuesta debe ser prosa fluida en párrafos". Las instrucciones
positivas funcionan mejor que las negativas.


Mejores prácticas de Claude Code
1. Da formas de verificación

Esta es LA práctica más importante. Proporciona tests, outputs esperados, o pide screenshots. Sin
verificación, tú te conviertes en el único control de calidad.

2. Explora, planifica, luego codifica

Usa el flujo de 4 pasos:

  1. Explorar (Plan Mode, Ctrl+G): Lee el código existente sin cambiar nada.
  2. Planificar (Plan Mode): Diseña la solución antes de implementar.
  3. Implementar (Normal Mode): Ahora sí, escribe código.
  4. Commit: Guarda los cambios.

3. Proporciona contexto específico

Usa @ para referenciar archivos. Pega errores directamente. Pasa datos con pipe: cat error.log |
claude .

4. Escribe un CLAUDE.md efectivo

Ejecuta /init para generar uno. Mantenlo bajo 200 líneas. Incluye solo lo que Claude no puede
adivinar del código: comandos de build, reglas de estilo no estándar, y convenciones del repo.

5. Corrige el rumbo temprano

                                                              TROUBLESHOOTING Y MEJORES PRÁCTICAS




Los mejores resultados vienen de feedback rápido. Presiona Esc para detener. Usa /rewind para
restaurar. Si has corregido a Claude más de 2 veces en el mismo problema, haz /clear y empieza de

6. Usa el patrón Writer/Reviewer

Abre dos sesiones. Una escribe código. La otra lo revisa con contexto fresco. Claude no estará sesgado

   Retry con exponential backoff y jitter en Python



       import time
       import random
       import anthropic


       def retry_with_backoff(func, max_retries=5):
             for attempt in range(max_retries):
                  try:
                       return func()
                  except anthropic.RateLimitError as e:
                       if attempt == max_retries - 1:
                             raise
                       # Usar retry-after si disponible
                       retry_after = getattr(e, 'retry_after', None)
                       if retry_after:
                             delay = retry_after
                       else:
                             delay = (2 ** attempt) + random.uniform(0, 0.5)
                       print(f"Rate limited. Esperando {delay:.1f}s...")
                       time.sleep(delay)



   Esta función reintenta automáticamente cuando recibes un error 429. Primero intenta usar el
   header retry-after (que dice exactamente cuánto esperar). Si no está disponible, usa exponential
   backoff: 1s, 2s, 4s, 8s, 16s. El jitter (random) evita que múltiples clientes reintenten al mismo
   tiempo.
