    Claude Code se adapta a ti, no al revés. Puedes cambiar cómo se comporta usando
    archivos de configuración simples. En este capítulo vas a aprender dónde viven esos

    volante, espejos, asiento. Todo se ajusta para que tú manejes cómodo.




La Jerarquía de Configuración: Quién Manda Aquí

Claude Code no tiene un solo archivo de configuración. Tiene cinco niveles, organizados como una
pirámide. Los de arriba mandan sobre los de abajo.

Imagina una empresa. El CEO da una orden. El gerente puede agregar detalles, pero no puede
contradecir al CEO. El empleado puede personalizar su escritorio, pero no puede cambiar las reglas de
la empresa.

Así funciona la configuración de Claude Code:

  1. Managed (administrador) — El nivel más alto. Lo configura el equipo de IT de tu empresa. Nadie
    puede sobreescribirlo.
  2. Argumentos de línea de comandos — Overrides temporales que pasas al ejecutar Claude. Solo
    duran esa sesión.
  3. Local — Tu configuración personal para un proyecto. No se comparte con nadie.
  4. Project — La configuración del proyecto. Se comparte con todo el equipo vía git.
  5. User — Tu configuración global. Aplica a todos tus proyectos.

Hay una regla importante: las listas (como permisos) se combinan entre niveles. No se reemplazan. Si
tu configuración de usuario permite npm run test y la de proyecto permite npm run lint , ambas
quedan permitidas.

Cómo ver qué configuración está activa
Escribe /status dentro de Claude Code. Te muestra todas las fuentes de configuración activas y de
dónde vienen.

Esto es muy útil cuando algo no funciona como esperas. Siempre revisa /status primero.

Los Archivos de Configuración y Dónde Viven

Cada nivel de configuración tiene su propio archivo. Es como tener cajones diferentes para cosas
diferentes.

Settings de usuario (global)
Archivo: ~/.claude/settings.json

Este archivo aplica a todo lo que hagas con Claude Code. No importa en qué proyecto estés. Es tu
configuración base.

Ejemplo básico:



   {
       "$schema": "https://json.schemastore.org/claude-code-settings.json",
       "permissions": {
         "allow": ["Bash(npm run *)", "Bash(git commit *)"],
         "deny": ["Bash(curl *)", "Read(./.env)"]
       },
       "model": "claude-sonnet-4-6"
   }



El campo $schema es opcional pero muy recomendado. Le dice a tu editor (VS Code, Cursor) que te
ayude con autocompletado.


Settings de proyecto (compartido)
Archivo: .claude/settings.json (dentro de tu proyecto)

Este archivo va dentro de git. Todos los del equipo lo comparten. Sirve para que todos trabajen con las
mismas reglas.

Ejemplo:

CONFIGURACIÓN Y SETTINGS




   {
       "permissions": {
           "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
           "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"],
           "additionalDirectories": ["../docs/"]
       },
       "env": {
           "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
       }
   }



Con env puedes definir variables de entorno que se aplican a todo el equipo. Así no cada persona
tiene que configurarlas manualmente.

Con additionalDirectories puedes dar acceso a carpetas fuera del directorio del proyecto.
También puedes agregar directorios con --add-dir al iniciar o /add-dir durante la sesión. Los
archivos de directorios adicionales siguen las mismas reglas de permisos.


Settings locales (solo para ti)
Archivo: .claude/settings.local.json

Este archivo está en el proyecto pero no se sube a git. Es solo tuyo. Perfecto para preferencias
personales que no quieres imponer al equipo.

Ejemplo:



   {
       "permissions": {
           "defaultMode": "acceptEdits"
       },
       "language": "japanese",
       "prefersReducedMotion": true
   }




Settings administrados (para empresas)
Estos los configura el equipo de IT. El usuario normal no los toca.

Hay tres mecanismos para entregar managed settings, cada uno con su propia precedencia:

  1. Server-managed settings — Se configuran desde la web en Claude.ai (Admin Settings > Claude
    Code > Managed settings). Tienen la mayor precedencia de todos.

  2. MDM / Políticas del sistema operativo — Para empresas que usan herramientas de gestión de
    dispositivos:
       ◦ macOS: Dominio com.anthropic.claudecode . Se despliega con Jamf, Kandji u otro MDM.
       ◦ Windows: Registro en HKLM\SOFTWARE\Policies\ClaudeCode con valor Settings (tipo
        REG_SZ con JSON). Se despliega con Group Policy o Intune.
       ◦ Windows (usuario): HKCU\SOFTWARE\Policies\ClaudeCode — tiene la menor
        precedencia de los mecanismos managed.

  3. File-based — Archivos JSON en ubicaciones del sistema operativo:
       ◦ macOS: /Library/Application Support/ClaudeCode/managed-settings.json
       ◦ Linux/WSL: /etc/claude-code/managed-settings.json
       ◦ Windows: C:\Program Files\ClaudeCode\managed-settings.json

La precedencia dentro de managed es: server-managed > MDM/OS-level > file-based > HKCU
registry (Windows).

Los settings administrados son como las reglas del edificio. Tú puedes decorar tu oficina, pero no
puedes tirar una pared.


Otros archivos importantes
Además de los settings, Claude Code usa estos archivos:

   • ~/.claude.json — Preferencias de usuario, tokens OAuth y estado interno. No lo edites
    manualmente. Importante: algunos settings viven aquí y no en settings.json (ver nota abajo).
   • .mcp.json — Servidores MCP del proyecto (ver capítulo de MCP).
   • ~/.claude/CLAUDE.md — Tu memoria global. Instrucciones que Claude sigue en todos los
    proyectos.
   • CLAUDE.md o .claude/CLAUDE.md — Memoria del proyecto. Instrucciones específicas para ese
    proyecto.
   • ~/.claude/agents/ — Subagentes personales.
   • .claude/agents/ — Subagentes del proyecto.

Settings que van en ~/.claude.json , NO en settings.json:

   • editorMode — Modo de key binding: "normal" o "vim" .
   • autoConnectIde — Conectar automáticamente al IDE al iniciar.
   • autoInstallIdeExtension — Instalar extensión IDE automáticamente.
   • showTurnDuration — Mostrar duración de cada respuesta.
   • terminalProgressBarEnabled — Barra de progreso visual.

Control de actualizaciones y versión mínima
Por defecto, Claude Code se actualiza automáticamente a la última versión disponible. Puedes
controlar este comportamiento con dos settings:



   {
        "autoUpdatesChannel": "stable",
        "minimumVersion": "2.1.100"
   }



   • autoUpdatesChannel — Acepta "latest" (default) o "stable" . El canal stable retrasa una
    semana las nuevas versiones para evitar regresiones. Si una versión tiene problemas reportados,
    no llega al canal stable.
   • minimumVersion — Bloquea cualquier ejecución y el comando claude update si la versión
    instalada está por debajo de este valor. Útil para empresas que necesitan asegurar features de
    seguridad recientes. Lo fija el cambio de canal en /config y actúa como suelo que impide
    downgrades.

Suelos y techos duros para administradores (v2.1.163): en managed settings hay dos claves que
van un paso más allá que minimumVersion porque bloquean el arranque de Claude Code:

   • requiredMinimumVersion — Suelo duro. Si la versión instalada es menor, Claude Code no
    arranca.
   • requiredMaximumVersion — Techo. Si la versión instalada es mayor, Claude Code tampoco
    arranca.

La diferencia con minimumVersion : este último es una preferencia que evita downgrades, mientras
que los required* son políticas managed que IT impone como límites infranqueables para
mantener a toda la organización en una ventana de versiones concreta.

En entornos enterprise, los administradores suelen poner autoUpdatesChannel: "stable" en
managed settings y un minimumVersion coherente con su política de soporte.


Cambiar settings al vuelo con /config
No siempre quieres abrir un archivo JSON para cambiar un setting. Desde la v2.1.181 puedes fijar
cualquier setting directo desde el prompt con /config key=value :



   /config thinking=false
   /config editorMode=vim
   /config verbose=true



Funciona en sesión interactiva, en modo -p (print) y en Remote Control. Para ver la lista de claves
cortas disponibles, usa /config --help (v2.1.183).

Si escribes /config sin argumentos, se abre la interfaz de Settings con pestañas, donde puedes
navegar y ajustar opciones visualmente (incluido el tema claro/oscuro, que también se gestiona con /
theme ).

Diagnóstico de la jerarquía con claude doctor : además de /status , el comando claude
doctor revisa toda la jerarquía de configuración y te muestra las entradas inválidas junto con el
archivo de donde vienen. Es la mejor herramienta cuando un setting no surte efecto o cuando todo un
archivo dejó de aplicarse por un error de JSON.



El Sistema de Permisos: Qué Puede y Qué No Puede Hacer Claude

Los permisos son como las llaves de tu casa. Tú decides qué puertas puede abrir Claude y cuáles están
cerradas con llave.

Hay tres tipos de reglas:

   • allow — Claude puede hacerlo sin preguntar. Es como darle una llave.
   • ask — Claude te pregunta cada vez. Es como un timbre: pide permiso para entrar.
   • deny — Claude NO puede hacerlo. Punto. Es como un candado que nadie abre.

Las reglas se evalúan en este orden: primero deny , luego ask , luego allow . La primera que
coincida, gana. Si algo está en deny , ningún otro nivel puede permitirlo.

Tipos de herramientas y cuándo piden permiso
No todas las herramientas de Claude necesitan tu aprobación:

   • Solo lectura (leer archivos, buscar con Grep) — No pide permiso. Solo mira, no toca.
   • Comandos Bash (ejecutar en terminal) — Pide permiso. Si dices "no preguntes más", se guarda
    permanentemente para ese directorio y comando.
   • Editar archivos — Pide permiso. Si dices "no preguntes más", solo dura hasta que cierres la
    sesión.

Para ver todas tus reglas activas, escribe /permissions en Claude Code.


Cómo escribir reglas de permisos
Las reglas siguen un formato simple: Herramienta(especificador) .

Ejemplos claros:

   • Bash(npm run build) — Permite exactamente ese comando.
   • Bash(npm run test *) — Permite cualquier comando que empiece con npm run test . El *
    significa "cualquier cosa después".
   • Bash(* --version) — Permite cualquier comando que termine en --version .
   • Read(./.env) — Controla la lectura del archivo .env .
   • Read(./secrets/**) — Controla todos los archivos dentro de la carpeta secrets , incluyendo
    subcarpetas.

Un detalle importante sobre los wildcards (los asteriscos): el espacio antes del * importa.

   • Bash(ls *) — Coincide con ls -la pero no con lsof .
   • Bash(ls*) — Coincide con ls -la y también con lsof .

Claude Code es inteligente con los operadores del shell. Si permites Bash(safe-cmd *) , Claude no
podrá ejecutar safe-cmd && rm -rf / . Detecta el && y lo bloquea.


Reglas específicas por tipo de herramienta
Para archivos (Read/Edit): Los patrones siguen las reglas de gitignore.

   • //path — Ruta absoluta desde la raíz del sistema. Ejemplo: //tmp/build .
   • ~/path — Relativo a tu carpeta home. Ejemplo: ~/.kube .
   • /path — Relativo a la raíz del proyecto. Ejemplo: /src/**/*.ts .
   • path o ./path — Relativo al directorio actual.

Para WebFetch: Filtra por dominio.

   • WebFetch(domain:example.com) — Solo permite ese dominio.

Para MCP servers:

   • mcp__servername — Cualquier herramienta de ese servidor.
   • mcp__servername__toolname — Una herramienta específica.

Para subagentes:

   • Agent(Explore) , Agent(Plan) , Agent(mi-agente-custom) .

Para skills: Skill es una tool más a efectos de permisos.

   • Skill(commit) — Invocaciones exactas del skill commit .
   • Skill(review-pr *) — El skill review-pr con cualquier argumento.
   • Skill — Cualquier skill.

principal arranque con el system prompt, restricciones de tool y modelo de un subagente concreto.
Útil para sesiones especializadas (ej. revisión de seguridad).

       "agent": "code-reviewer"

Matching por parámetros de herramienta
Desde la versión v2.1.178, las reglas de permisos pueden mirar dentro de los parámetros de cada
herramienta, no solo su nombre. El formato es Herramienta(parametro:valor) .

Esto te da un control mucho más fino:

   • Agent(model:opus) — Bloquea (o permite) que se lancen subagentes con el modelo Opus. Útil
    para controlar costes.
   • WebFetch(domain:*.example.com) — Aplica la regla solo a las peticiones web hacia
    subdominios de example.com .
   • Edit(src/**) — Aplica la regla solo a las ediciones dentro de la carpeta src .

Ejemplo: para impedir que ningún subagente use Opus pero permitir el resto:

   {
       "permissions": {

Glob en la posición del nombre de la herramienta (v2.1.166): las reglas deny ahora aceptan

de bloquear todo y luego ir abriendo con allow .

Read deny oculta archivos de la búsqueda (v2.1.162): cuando un archivo está cubierto por una
regla Read en deny , ya no solo se bloquea su lectura: además queda oculto en los resultados de
Glob y Grep. Así un secreto bloqueado tampoco aparece listado por accidente.



Modos de Permisos: Seis Velocidades

Claude Code tiene seis modos de permisos. Son como las marchas de un coche: cada una te da un
nivel diferente de control.

  1. default — El modo normal. Claude pide permiso la primera vez que usa cada herramienta.
  2. acceptEdits — Acepta automáticamente las ediciones de archivos. Ya no te pregunta antes de
    cambiar código.
  3. plan — Modo solo lectura. Claude puede analizar tu código pero no puede modificar nada. Útil
    para explorar sin riesgo.
  4. auto — El piloto automático. Usa un clasificador de seguridad en segundo plano para decidir si
    una acción es segura. Si lo es, la ejecuta sin preguntar. Si tiene dudas, te pregunta. Es un research
    preview: funciona bien pero sigue mejorando.
  5. dontAsk — Rechaza automáticamente todo lo que no esté pre-aprobado en tus reglas de
    permisos.
  6. bypassPermissions — Salta todos los permisos. Solo úsalo dentro de containers o máquinas
    virtuales aisladas. Nunca en tu máquina personal.

Para cambiar de modo durante una sesión, presiona Shift+Tab . Cicla entre los modos disponibles.

Para configurar el modo por defecto al iniciar:

Auto Mode: El Piloto Automático

El modo auto es como tener un copiloto que conoce las reglas de tráfico. En vez de preguntarte cada
vez que quiere girar, evalúa si es seguro y lo hace. Solo te consulta cuando hay duda.

Por dentro, un clasificador de seguridad analiza cada acción que Claude quiere ejecutar. Si la acción es
rutinaria y segura (como leer un archivo o correr tests), la aprueba automáticamente. Si es
potencialmente peligrosa (como borrar archivos o hacer push a producción), te pregunta.

Configurar Auto Mode
Puedes personalizar el comportamiento del clasificador con el setting autoMode :



   {
       "autoMode": {
           "environment": [
               "Organization: Acme Corp. Primary use: software development",
               "Source control: github.example.com/acme-corp",
               "Trusted cloud buckets: s3://acme-build-artifacts",
               "Trusted internal domains: *.corp.example.com"
           ]
       }
   }



El campo environment describe en prosa tu infraestructura de confianza. Esto le dice al clasificador
qué repos, dominios y recursos son seguros en tu contexto.

También puedes definir excepciones con allow y soft_deny :

   • allow — Acciones que siempre se permiten (excepciones a bloqueos).
   • soft_deny — Acciones que siempre se bloquean.


Advertencia crítica sobre allow y soft_deny
CUIDADO: Si defines allow o soft_deny en tu configuración, reemplazan completamente la lista
default. No se combinan. Esto puede desactivar reglas de seguridad importantes que vienen por
defecto.

Para ver las reglas default antes de modificarlas:



   # Ver reglas integradas por defecto
   claude auto-mode defaults


   # Ver configuración efectiva (default + tus cambios)
   claude auto-mode config


   # Pedir feedback del clasificador AI sobre tu config
   claude auto-mode critique



Nota de seguridad: autoMode NO se lee desde .claude/settings.json compartido del proyecto.
Solo se lee desde user settings, local settings y managed settings. Esto previene que un repositorio
malicioso inyecte reglas de auto-aprobación.



Niveles de Esfuerzo: Cuánto Piensa Claude

Los niveles de esfuerzo controlan cuántos recursos de razonamiento dedica Claude a cada respuesta.
Es como elegir entre una respuesta rápida en el pasillo y una reunión formal de análisis.

Hay cuatro niveles:

  1. low — Respuestas rápidas y directas. Ideal para preguntas simples o tareas rutinarias.
  2. medium — El balance. Es el nivel por defecto para Sonnet 4.6.
  3. high — Razonamiento profundo. Para problemas complejos que necesitan análisis detallado. Es el
    nivel por defecto del modelo global actual, Opus 4.8.
  4. xhigh — El máximo poder de razonamiento. Solo disponible en Opus 4.8. No persiste entre
    sesiones (excepto vía variable de entorno).

Como referencia: a junio de 2026 el modelo por defecto de Claude Code es Opus 4.8 con esfuerzo
high .

Nota importante: el nivel máximo se llama xhigh , no max . Si pones max en tu configuración, no se
aplicará y caerás en el nivel por defecto. Es el error más común al copiar configuraciones viejas.

Cómo configurar el nivel de esfuerzo
Tienes varias formas de cambiar el esfuerzo:

   • /effort low|medium|high|xhigh — Slash command durante la sesión.
   • Flechas izquierda/derecha en /model — Ajusta el esfuerzo visualmente.
   • claude --effort high — Flag al iniciar Claude Code.
   • export CLAUDE_CODE_EFFORT_LEVEL=xhigh — Variable de entorno (tiene la mayor
    precedencia). Valores válidos: low , medium , high , xhigh .
   • "effortLevel": "xhigh" — En settings.json para que persista entre sesiones.
   • Frontmatter en skills/subagentes — Para controlar el esfuerzo de agentes específicos.

Un truco útil: escribe ultrathink en tu prompt y Claude activará el nivel high para ese turno
específico.

Para desactivar completamente el razonamiento adaptativo:



   export CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1




Contexto Extendido (1M Tokens)

Opus 4.8, Opus 4.7 y Sonnet 4.6 soportan una ventana de contexto de 1 millón de tokens. Eso es como
poder leer un libro entero de una sola vez, en vez de leerlo por capítulos. A diferencia de antes, esta
ventana de 1M está disponible a tarifa plana, sin recargo por superar los 200K tokens.

Cómo activar el contexto de 1M
Usa el sufijo [1m] al seleccionar el modelo:



   /model opus[1m]
   /model sonnet[1m]

Variables de Entorno: Los Interruptores Secretos

Las variables de entorno son como interruptores escondidos detrás del panel de tu coche. No los ves,
pero cambian cómo funciona todo por dentro.

Se configuran en tu terminal con export . También puedes ponerlas en tu .bashrc o .zshrc para
que se apliquen siempre.

Autenticación y API
Estas son las variables más básicas para conectarte:

   • ANTHROPIC_API_KEY — Tu clave API. La más importante de todas.
   • ANTHROPIC_AUTH_TOKEN — Token Bearer personalizado (uso avanzado).
   • ANTHROPIC_CUSTOM_HEADERS — Headers extra para las peticiones HTTP.



   export ANTHROPIC_API_KEY=sk-ant-tu-clave-aqui




Selección de modelo
Puedes cambiar qué modelo de Claude se usa:

   • ANTHROPIC_MODEL — El modelo principal. Ejemplo: claude-sonnet-4-6 .
   • ANTHROPIC_DEFAULT_HAIKU_MODEL — Override para el modelo Haiku (rápido y barato).
   • ANTHROPIC_DEFAULT_SONNET_MODEL — Override para Sonnet.
   • ANTHROPIC_DEFAULT_OPUS_MODEL — Override para Opus (el más potente).
   • ANTHROPIC_SMALL_FAST_MODEL — Modelo para operaciones pequeñas y rápidas (resúmenes,
    títulos, etc.).
   • CLAUDE_CODE_SUBAGENT_MODEL — Modelo que usan los subagentes.

También puedes configurar el modelo en el settings.json con la propiedad model .

URLs base de la API: útil si necesitas apuntar a un endpoint distinto (gateway interno, región
específica, etc.):

   • ANTHROPIC_BASE_URL — URL base para la API de Anthropic. Default: https://
    api.anthropic.com .

   • ANTHROPIC_BEDROCK_BASE_URL — URL base para AWS Bedrock.
   • ANTHROPIC_VERTEX_BASE_URL — URL base para Google Vertex AI.

Autenticación específica por proveedor:

   • AWS_BEARER_TOKEN_BEDROCK — Bearer token para autenticar contra Bedrock (alternativa a las
    credenciales AWS estándar).
   • CLAUDE_CODE_SKIP_BEDROCK_AUTH — Salta el flujo de auth de Bedrock cuando ya tienes
    credenciales externas listas.
   • CLAUDE_CODE_SKIP_VERTEX_AUTH — Salta el flujo de auth de Vertex.
   • VERTEX_REGION_<MODEL> — Región específica de Vertex por modelo. Ejemplo:
        VERTEX_REGION_CLAUDE_SONNET=us-east5 .

Configuración de Red y Proxy (Empresas)

Si trabajas en una oficina con red corporativa, probablemente tienes un proxy. Un proxy es como un
guardia de seguridad entre tu computadora e internet. Todo el tráfico pasa por él.

Claude Code necesita conectarse a internet para funcionar. Si hay un proxy de por medio, tienes que
decirle dónde está.

Configuración básica de proxy
Configura estas variables de entorno:



   export HTTPS_PROXY=http://proxy.empresa.com:8080
   export HTTP_PROXY=http://proxy.empresa.com:8080
   export NO_PROXY="localhost,192.168.1.0/24,.empresa.com"



NO_PROXY lista los hosts que no deben pasar por el proxy. Puedes separar con comas o espacios. Usa
* para bypasear todo.

Si tu proxy necesita usuario y contraseña:



   export HTTPS_PROXY=http://usuario:password@proxy.empresa.com:8080



Nota: Claude Code no soporta proxies SOCKS. Solo HTTP y HTTPS.


Certificados personalizados y mTLS
Muchas empresas tienen sus propios certificados de seguridad. Es como una credencial que tu
empresa le da a tu computadora para que los servidores confíen en ella.

Si ves errores de SSL al conectar, necesitas esto:



   export NODE_EXTRA_CA_CERTS=/ruta/al/certificado-ca.pem



Si tu CA corporativa solo está en el almacén del sistema, también puede ayudar:



   export CLAUDE_CODE_CERT_STORE=bundled,system

El Sandbox: Una Jaula de Seguridad

El sandbox es como una jaula transparente. Claude puede trabajar dentro, pero no puede tocar nada
fuera de ella. Restringe el acceso al sistema de archivos y a la red a nivel del sistema operativo.

Para activarlo:



   {
       "sandbox": {
           "enabled": true,
           "failIfUnavailable": true
       }
   }



Cuando el sandbox está activo, los comandos Bash se aprueban automáticamente. Tiene sentido: si
Claude está encerrado en una jaula, no puede hacer daño.




                                                    291                                      @soyenriquerocha
CONFIGURACIÓN Y SETTINGS




El setting failIfUnavailable hace que Claude Code se niegue a arrancar si pides sandbox pero el
sistema no puede ofrecerlo. Es la forma segura de evitar caer en un entorno sin protección por
accidente.

Por sistema operativo:

   • macOS: usa sandbox-exec nativo.
   • Linux y WSL2: usa bwrap + socat . Si tu IT empaqueta estos binarios en una ruta no estándar,
    indícalo con sandbox.bwrapPath y sandbox.socatPath (ambos solo managed).
   • Windows: no hay sandbox para Bash. Si tu política requiere sandbox, no uses Bash en Windows
    nativo; trabaja desde WSL2.

Restricciones de archivos
Controla dónde puede escribir y leer Claude:



   {
       "sandbox": {
           "enabled": true,
           "filesystem": {
               "allowWrite": ["//tmp/build", "~/.kube"],
               "denyWrite": ["//etc", "//usr/local/bin"],
               "denyRead": ["~/.aws/credentials"],
               "allowRead": ["."]
           }
       }
   }



Los prefijos de ruta son importantes:

   • // — Ruta absoluta desde la raíz del sistema. Ejemplo: //tmp es /tmp .
   • ~/ — Relativo a tu carpeta home.
   • / — Relativo al directorio del archivo de settings.
   • ./ o sin prefijo — Relativo al directorio actual.

El campo allowRead sirve para re-permitir lectura dentro de regiones bloqueadas por denyRead . Es
útil cuando quieres bloquear un directorio amplio pero permitir acceso al workspace actual.

Para administradores, sandbox.filesystem.allowManagedReadPathsOnly en managed settings
restringe a que solo se respeten las rutas de allowRead definidas por IT.

Restricciones de red
Controla a qué sitios web puede acceder Claude desde dentro del sandbox:



    {
        "sandbox": {
            "enabled": true,
            "network": {
                "allowedDomains": ["github.com", "*.npmjs.org"],
                "deniedDomains": ["sensitive.cloud.example.com"],
                "allowLocalBinding": true,
                "allowUnixSockets": ["/var/run/docker.sock"],
                "allowAllUnixSockets": false,
                "allowMachLookup": ["com.apple.coresimulator.*"]
            }
        }
    }



allowedDomains acepta wildcards con * . deniedDomains tiene precedencia: aunque un dominio
esté en la lista permitida, si también aparece en denegados se bloquea.

Si necesitas que Claude inicie un servidor local de desarrollo, activa allowLocalBinding (solo
macOS).

allowUnixSockets           permite    acceso        a    sockets     Unix     específicos   (útil   para   Docker).
allowAllUnixSockets permite todos los sockets Unix sin restricción.

allowMachLookup (solo macOS) lista los nombres de servicio XPC/Mach que el sandbox puede
consultar. Útil para herramientas Apple como Core Simulator.

Apple Events (solo macOS, v2.1.181): por defecto los comandos dentro del sandbox no pueden
enviar Apple Events (la forma en que las apps de macOS se comunican entre sí, como pedirle a Finder
o   a       una   app   que   haga   algo).    Si       lo    necesitas,    actívalo   de   forma   explícita   con
sandbox.allowAppleEvents :



    {
        "sandbox": {
            "enabled": true,
            "allowAppleEvents": true
        }
    }



Es opt-in: solo se abre esta vía si tú lo pides.

Configuración de Skills
Los skills son extensiones de Claude Code (ver capítulo 16). Hay cuatro settings para afinar cómo se
descubren y se ejecutan:

   • maxSkillDescriptionChars (v2.1.105+) — Tope de caracteres combinados de description +
       when_to_use por skill. Default: 1536 . Subirlo si tus skills tienen descripciones largas y se
    truncan.
   • skillListingBudgetFraction (v2.1.105+) — Fracción del contexto reservada para el listado de
    skills. Default: 0.01 (1%). Subirlo si tienes muchos skills y los menos prioritarios no aparecen.
   • skillOverrides (v2.1.129+) — Visibilidad por skill. Valores: "on" (visible y ejecutable),
       "name-only" (solo el nombre, sin description), "user-invocable-only" (solo cuando el
    usuario lo invoca explícitamente), "off" (desactivado).
   • disableSkillShellExecution — Si vale true , los skills no pueden ejecutar shell inline; se
    sustituye por el mensaje [shell command execution disabled by policy] .

Ejemplo combinando los cuatro:



   {
        "maxSkillDescriptionChars": 2048,
        "skillListingBudgetFraction": 0.02,
        "skillOverrides": {
          "legacy-context": "name-only",
          "deploy": "off",
          "sensitive-action": "user-invocable-only"
        },
        "disableSkillShellExecution": false
   }



Permisos para skills: Skill es una tool más en permissions.allow / deny / ask :

   • Skill(commit) — Invocación exacta.
   • Skill(review-pr *) — Con cualquier argumento.

Variable de entorno relacionada: SLASH_COMMAND_TOOL_CHAR_BUDGET override directo del
presupuesto de caracteres del listing (sobrescribe skillListingBudgetFraction ).

Scripts auxiliares de autenticación
Claude Code puede ejecutar scripts cortos para generar o refrescar credenciales en tiempo de
ejecución. Útil para entornos enterprise con tokens de corta duración.

   • apiKeyHelper — Script (ejecutado con /bin/sh ) que devuelve el valor de autenticación. Se
    envía como X-Api-Key y Authorization: Bearer . Útil para integraciones con vaults internos.



         {
             "apiKeyHelper": "/bin/generate_temp_api_key.sh"
         }



    Variable relacionada: CLAUDE_CODE_API_KEY_HELPER_TTL_MS controla cada cuánto se refresca.
   • awsAuthRefresh — Script que modifica el directorio .aws para refrescar credenciales AWS (ej:
       aws sso login ). Útil cuando trabajas contra Bedrock.

   • awsCredentialExport — Alternativa: script que devuelve JSON con credenciales AWS, sin tocar
    el directorio .aws .
   • gcpAuthRefresh — Script que refresca las Application Default Credentials de GCP. Ejemplo

   • otelHeadersHelper — Script para generar headers OTEL dinámicos (ver subsección de
    telemetría OTEL).

Plugins y Marketplaces

Claude Code soporta plugins: extensiones que agregan funcionalidad. Los plugins vienen de
marketplaces, que son como tiendas de aplicaciones.

Habilitar y deshabilitar plugins


   {
       "enabledPlugins": {
           "formatter@acme-tools": true,
           "analyzer@security-plugins": false
       }
   }



El formato es nombre@marketplace . Pon true para activar, false para desactivar.


Agregar marketplaces
Puedes agregar fuentes de plugins adicionales. Los marketplaces soportan siete tipos de fuentes:

  1. github — Un repositorio de GitHub.
  2. git — Cualquier repositorio Git (GitLab, Bitbucket, etc.).
  3. url — Un JSON remoto con headers opcionales.
  4. npm — Un paquete de NPM.
  5. file — Un archivo local.
  6. directory — Un directorio local.
  7. hostPattern — Un patrón regex para matching de hosts.

Los administradores pueden restringir qué marketplaces se usan con strictKnownMarketplaces y
bloquear fuentes con blockedMarketplaces .

   Resumen del Capítulo

   Claude Code se configura con archivos JSON en tres ubicaciones principales: usuario (~/.claude/
   settings.json), proyecto (.claude/settings.json) y local (.claude/settings.local.json), más managed
   settings para empresas. Los permisos controlan qué puede hacer Claude usando reglas allow, ask
   y deny (incluyendo Skill() y Agent()), donde deny siempre gana. Hay seis modos de permisos,
   incluyendo el modo auto que usa un clasificador de seguridad. Los niveles de esfuerzo (low/
   medium/high/xhigh — xhigh, NO 'max') controlan cuánto razona Claude, y los aliases de modelo
   con sufijo [1m] activan el contexto extendido de 1 millón de tokens. Las variables de entorno
   cubren autenticación, modelo, proxy, TLS/certificados (CLAUDE_CODE_CERT_STORE), telemetría
   OTEL y comportamiento avanzado. El sandbox aísla a nivel de SO (sandbox-exec en macOS,
   bwrap+socat en Linux/WSL2; sin sandbox en Windows). Para entornos empresariales hay una
   receta de lockdown que combina allowManaged*Only + sandbox.*.allowManaged*Only +
   disableBypassPermissionsMode. Los managed settings avanzados incluyen policyHelper,
   parentSettingsBehavior y disableRemoteControl. Settings nuevos cubren skills, voice, worktree,
   hooks, MCP, scripts de auth y control de actualizaciones (autoUpdatesChannel, minimumVersion).
   includeCoAuthoredBy está deprecated en favor de attribution.commit / attribution.pr.
